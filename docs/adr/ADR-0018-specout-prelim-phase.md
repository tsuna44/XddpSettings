# ADR-0018: specout に下調べ（Step A-Prelim）とシード確認（Step A-Seed）を新設し、資料を成長型で確定する理由

Status: Accepted
Date: 2026-10-01

> **注記（2026-10-04）:** MODULE-LEVEL・`record-module`・`finish` は [ADR-0019](ADR-0019-specout-static-slicer.md) と
> [PLAN-20261004-specout-module-level-cleanup](../../plans/PLAN-20261004-specout-module-level-cleanup.md) で無くなった。本文のうち、累積観察メモの「MODULE-LEVEL 行の除去」、
> 「配置判定の『MODULE-LEVEL があれば分割パス』という条件を変えずに残す」、付随「`record-module`・`finish --mode complete` の
> ルート直下モジュール（`_root`）の欠陥修正」、SPO §8 の MODULE-LEVEL 行の説明は、現状と異なる（記録として残す）。

## Context

工程4a（specout）の波紋調査（Discovery BFS）は Wave 0 のシードを起点に grep で参照元を辿る。
シードの質が低いと、以降の全波・SPO・設計が誤った起点の上に積み上がる。議論資料
`plans/redesign_docs/specout-wave0-seed-gap-review.md`（以下「資料」）の段階1（未結線の解消・未ヒット警告・
シード提示）と段階1延長（シード採用基準・ヒット過多検知・由来記録）は実装済みであり、本 ADR は資料の
**段階3** を実装したプラン `plans/PLAN-20260927-specout-prelim-phase.md` の設計判断を記録する。

- U1 評価パイロット（`u1-eval/RESULTS.md`）で、成功例はいずれも母体を読んでから波紋調査に入り、
  失敗例は母体を読まずに CRS 中の一般語をシードにしていた。見落としの原因はシードの作り方か設計依存のみだった。
- 母体調査を discovery-setup に明文化するだけでは、読んだ内容が資料化されず、document フェーズ
  （`xddp-specout-document-agent`）で同じファイルを再び読む重複が残る。
- 変更前の document-agent は、document フェーズ開始時に一度だけ統合パス／分割パスを決めて一括で書いており
  （閾値 `SPECOUT_MAX_FILES_PER_MODULE`）、観察メモ `work/_observation-memo.md` は1回の実行の中間ファイルとして
  実行の冒頭と末尾で削除していた。

## Decision

工程4a（初回実行時。`work/bfs-state.json` が無い repo）を次の順に再構成した。

```
① 下調べ（Step A-Prelim・新設） : CRS から関係する処理を推論し、母体を読んで SPO-{CR}.md・modules/ を書く
② シード候補の整理（discovery-setup） : 下調べの候補 ∪ CRS のコード表記 ∪ ENTRY_POINTS を候補表 work/seed-candidates.md にする
③ シード確認（Step A-Seed・新設） : seed-preview でヒット数を試算し、人が採用／除外／追加を確定する
                                     （SPECOUT_SEED_GATE=false なら通知のみで続行）。「下調べ資料で止める」も選べる
④ 波紋調査（既存） : SKILL が init を実行し、波ループを回す
⑤ 資料の確定（document-agent） : 波紋調査で新たに見つかったファイルだけを読んで追記し、依存節を埋める
```

個々の判断と理由は次のとおり。

### 1. 下調べフェーズを新設する（U1）

U1 評価で、成功例はいずれも母体を読んでから波紋調査に入っていた。シードの質を上げる最も直接的な手段は
「波紋調査の前に母体を読む」ことであり、段階1の結線・警告だけでは一般語シードを予防できない。

### 2. `xddp-survey-agent` を再利用せず、新規エージェント `xddp-specout-prelim-agent` を作る（U2）

survey-agent は調査範囲を自ら決めず（`TARGET_FILES` を呼び出し元スキルが 1 hop grep で確定して渡す）、
CR 依存の入力（CRS・ENTRY_POINTS 等）も持たない。再利用で得られるのは「テンプレート全節を使う」指示程度であり、
一方で survey の「CR 非依存」「1 hop 固定（多段の波及展開は工程4a の役割）」という責務分界を崩す。
このため survey は変更しない。

### 3. 下調べで資料そのものを作り、資料の確定で読み直さない（追加1）

下調べで読んだ内容を資料化しなければ、document フェーズで同じファイルを再び読む重複が残る。
下調べが最終的な置き場所（`SPO-{CR}.md`・`modules/`）に直接書き、資料の確定は文書化済みファイル台帳に無い
ファイルだけを読む。資料の確定が読む範囲は `specout_bfs.py doc-targets` が台帳と `bfs-state.json` の集合演算で決める
（集合演算は決定的処理であり LLM に数えさせない）。

### 4. 資料は最終の置き場所に直接書き、索引・台帳・観察メモは `work/` に置く

人が読む資料を下調べ版と確定版の2部にしないため。機械が読むファイル（`work/prelim-index.md`・
`work/documented-files.md`・`work/observation-memo.md`・`work/seed-candidates.md`・`work/seed-unsupported.json`・
`work/module-assignments.json`）は `work/` に置く。Step A3 の `ARTIFACTS_TEXT` は変えない（U5）。

### 5. 下調べ時点では波紋調査に依存する節のプレースホルダーを残す

document-agent の Step 10・Step 10.5 は、テンプレートのプレースホルダー（`{SIDE_EFFECTS_DFD_PLACEHOLDER}`、
§4.1・§5.6・§5.7・§4.5 のプレースホルダー行）を Edit の置換アンカーに使い、DFD は「プレースホルダーが存在しない場合は
スキップ」と規定されている。下調べがこれらを別の文言で置き換えると DFD が黙って生成されなくなるため、
下調べは依存節（§4〜§7・§9〜§10）に一切触れない。止めた状態の資料でも、未記入の節がテンプレートと同じ形で
残るため、未記入であることが一目でわかる。

### 6. 資料の確定は `SPO-{CR}.md` を部分更新せずテンプレートから作り直し、下調べの節だけを引き継ぐ

変更前の document-agent は、§4.3・§4.4・§5.1〜§5.5・§6・§7 本文・§10 を「テンプレートから SPO 全体を書く」処理の中で
生成しており、これらの節にはプレースホルダーを Edit で置き換える規則がない。既存の SPO をその場で部分更新する方式に
すると、これらの節の書き方と再実行時の上書き規則を新たに作る必要がある。作り直す方式なら依存節はすべて既存の規則で書かれ、
再実行時の冪等性も変更前と同じになる。依存節の入力（discovery-log・累積観察メモ・モジュール資料）は資料の確定の時点で
すべて揃っており、ソースを読み直す必要はない。下調べが書く §1〜§3（統合パスの §2.A… を含む）と §11 の版 0.1 の行だけを
引き継ぎ、§8 は配置と全モジュールから毎回作る。人が依存節を直接編集した後に資料の確定を再実行すると、その編集は失われる
（変更前と同じ）。

### 7. 観察メモを累積・非削除にする（`work/_observation-memo.md` を廃止し `work/observation-memo.md` に一本化）

新方式では文書化済みのファイルを読み直さないため、観察を1回の実行の中だけに持つと次の2経路で観察が失われる。
(1) 資料の確定を再実行したとき（Step A-cross-propagate の再ドキュメント化、Phase 3 の未記録ヒット後の再実施、
`--re-discover` 後）、前回観察したファイルは文書化対象から外れるため、§4.1/§5.6/§5.7/DFD を節単位で置き換えると前回の観察行が消える。
(2) 下調べの観察を引き継いだ後に資料の確定が同ファイルを新規作成すると、引き継いだ行が上書きされる。
「ファイルを文書化した時点で累積ファイルへ書き、削除しない」形にすれば、どの経路でも集約の入力は常に全観察になる。
前回の中断で台帳に記録される前に書かれた行と MODULE-LEVEL 行は `doc-targets --memo` が決定的に除去する。

### 8. 資料の配置を成長型にする（追加4）

下調べは自分が文書化したファイル数で統合／分割を判定して書き、資料の確定は台帳と今回の文書化対象の和集合で数え直して、
閾値を超えた単位だけを分割へ移す。

- **統合パスを廃止しない理由:** 統合パスは波及10ファイル以下の CR で普通に起き、architect-agent（funcmap 備考列の解釈）・
  funcmap テンプレートが統合パスを前提にしている。廃止すると影響が工程5以降に及ぶ。統合パスの §2.A… はモジュールテンプレートの
  §2〜§4 と同じ構成にし、分割へ移る際に節をそのまま `modules/{module}-spo.md` へ移せるようにした。
- **一方向のみ（統合→分割、単一→サブディレクトリ分割）の理由:** 台帳は追記のみで、文書化ファイル数は増える方向にしか変わらないため。
- **配置判定の「MODULE-LEVEL があれば分割パス」という条件を変えずに残す:** MODULE-LEVEL のモジュールヘッダは
  モジュール資料ではなく SPO §8 の行に書くようにしたため、この条件の根拠は変わりうる。変更前にこの条件を置いた理由は
  記録が無く確認できていないため、挙動を変えず、見直しは別のプランで扱う。

### 9. モジュールの決め方: 台帳を正本とし、前方一致はスクリプト、新しいモジュールの切り方はエージェント

モジュールは「モジュール名」と「モジュールディレクトリ」の組で台帳に記録し、一度記録した組は変えない。
記録済みモジュールディレクトリへのディレクトリ境界での最長前方一致はスクリプト（`doc-targets`）が行い、
どれにも一致しないファイルの新しいモジュールはエージェントが決める（新しい組は `work/module-assignments.json` に書く）。
第1階層ディレクトリ等の固定規則にしないのは、変更前の粒度（機能ディレクトリ単位）を保ち、特定のディレクトリ構成
（`src/` 配下に複数の機能ディレクトリがある構成、`src/main/java/...` のように直下が1つの構成、組み込みの
`Drivers/uart/` 等）を前提にしないため。台帳内の組の矛盾は exit 1 で検出し、再実行のたびにモジュールがぶれるのを防ぐ。

リポジトリ直下のファイルのモジュールディレクトリは `.` と書き、`.` はディレクトリを持たないファイルにだけ一致させる
（実装時に決定。プランの 8.1 I1）。前方一致の規則のままでは直下のファイルに一致するディレクトリが無く、新しいモジュールを
決めても割り当てられないため。`.` を全ファイルの受け皿にしないのは、台帳にリポジトリ直下のモジュールが1つあるだけで
全ファイルがそのモジュールに入り、新しいモジュールが決められなくなるため。

### 10. 下調べ時点の配置判定の件数はエージェントが数えることを許容する

下調べエージェントには Process に外部コマンド実行の手順が無いため `Bash` を付与しない（最小権限原則）。
このため下調べ時点の件数はエージェントが一覧から数える。数え誤りで分割パスを選んでも、情報は失われず配置が細かくなる
だけである。資料の確定では件数を `doc-targets` の `module_file_counts` から得る。

### 11. シード確認を `init` の前に置き、`init` を SKILL へ移す（追加2）

確認を `init` の前に置くことで、訂正が「状態を作る前の候補表の編集」で済む（`init` 後の訂正は discovery-log の
初期シンボル一覧・由来テーブルとの整合を別途取る必要がある）。`init` を SKILL が実行することで、状態ファイルを作るのは
スクリプトだけになり（U13＝エージェントが状態ファイルを独自形式で自作する事象の構造的な予防）、由来テーブル
「## 投入シンボルの由来」の全9行も `init --seed-candidates` が候補表から決定的に書く。discovery-setup は候補表の作成までに
縮小され、変更前に SKILL の pass ブロックには無く specout-agent の Inputs にだけあった `DISCOVERY_LOG` の不整合も解消する。

### 12. シード確認の既定を「あり」（`SPECOUT_SEED_GATE: true`）とする

シード候補の質は使うモデルと母体コードに依存する。Claude 以外のモデルでの運用（U1 評価は GitHub Copilot Chat で実施）を
考慮し、既定は確認ありとした。`false` でも、採用が0件または採用した全候補がヒット過多（一般語の疑い）の repo がある場合は
確認を求める。`metrics.jsonl` の `prelim_summary`（`human_added_count`・`human_removed_count`・`bfs_only_file_count`）が
継続して小さい場合に `false` を検討できるよう、計測を `prelim-metrics` で決定的に記録する（U6）。
CR 単位の上書き引数は設けない（必要になったら追加する）。

### 13. 「下調べ資料で止める」を CR 単位とし、工程4b へ進ませない（追加3）

コストを抑えて全体像だけ掴みたい場合のために、確認で波紋調査を行わずに終了できるようにした。repo ごとには選べない。
1 repo でも影響範囲が未調査なら工程4b（CRS 更新）へ進めないため。進捗は ⏸ 中断として記録し、再実行すると
下調べ資料と候補表をそのまま使って Step A-Seed から再開する。

### 14. 波紋調査を自動でスキップしない

波及が実際に少ない変更なら Wave 1 で自然収束し安価に完了するため、「省略」と実質的に同じ効果が結果として得られる
（`CR_PROFILE=quick` でも探索深さを削らない既存方針とも整合する）。スキップ判定は `bfs_only_file_count` の計測が
蓄積してから別途検討する。

### 15. 文書化手順をスキルローカルの `module-documentation.md` に移設し、document-agent が毎回読む

観察手順・累積観察メモの書式・モジュール資料の記載要件・必須図・配置判定・§8 の書き方・資料の状態・モジュールの決め方を
`skills/xddp-04-specout/module-documentation.md` に移設し、下調べエージェントと document-agent が共有する。
document-agent は文書化するファイルが無い実行でもフラグ定義・配置判定・§8 の書き方等を使うため毎回読む。
毎回使う規則だけを document-agent 本体に残して読み分ける方式にすると、同じ規則が2か所に書かれ片方だけが更新される危険がある。
規則を1か所に保つことを、指示文の読み込み量の削減より優先した。参照元は単一スキル（xddp-04-specout とそれが起動する
エージェント）に限られるため `xddp-common/procedures/` ではなくスキルローカルに置き、CLAUDE.md のファイル構成表の
`skills/<skill-name>/*.md` 行を「SKILL.md 本体または当該スキルが起動するエージェントから Read される」に改めた。

### 16. 下調べ時点（版 0.1）のスナップショットを残さない

台帳・索引・観察メモで U6 の計測（下調べが文書化したファイル数・波紋調査だけが見つけたファイル数等）が成立し、
資料の差分が必要なら VCS で追えるため。

### 17. 中断した下調べの部分成果を再利用しない

下調べの調査範囲に上限は設けないため、大規模な母体ではコンテキスト溢れで完了しないおそれがある。下調べはシード候補になる
識別子を含むファイルから順に文書化し、ファイルごとに資料・観察メモ・台帳を書く。失敗時は残骸を削除して下調べなしで続行する
（CRS 抽出＋ENTRY_POINTS で波紋調査は成立し、document-agent は全ファイルを読んで作る経路になる）。部分成果の再利用は、
`4a-prelim-{repo}` の所要時間と失敗の発生状況を見て別途検討する。

### 付随: `record-module`・`finish --mode complete` のルート直下モジュール（`_root`）の欠陥修正

ルート直下のファイルのモジュールは `_root` になるが、`_glob_module_files` は `{REPO_PATH}/_root` を探すため空を返し、
discovery-log には「一括記録」とあるのに確定ファイル一覧に現れなかった。資料の確定が discovery-log のパスを MODULE-LEVEL の
単位として使うため、この欠陥は §8 と観察メモに実体の無いモジュールとして現れる。`_root` はリポジトリ直下のファイル
（`{REPO_PATH}/_root/` が実在すればその配下も。両者を区別できないため、影響範囲を広めに取る MODULE-LEVEL では両方を含める）を
返すようにし、ファイルが0件のモジュールは一括記録せず、その残存シンボルを `unresolved` に加える。

## Consequences

- 初回の工程4a で下調べエージェントが repo ごとに1回起動する（コスト増）。`seed-preview` の grep は LLM コストなし。
  一方、document フェーズでの下調べ済みファイルの読み直しと、discovery-setup の母体調査（下調べがある場合）は減る。
  document-agent が1回の実行で読む指示文は `module-documentation.md` の分だけ増えるため、差し引きの効果は
  `prelim_summary`（`prelim_file_count`・`bfs_only_file_count`）と `4a-prelim-{repo}` の所要時間で事後に検証する。
- `SPECOUT_SEED_GATE: true`（既定）では、初回の工程4a で1回（全 repo まとめて）人の確認のため停止する。
  無人実行のスモーク fixture（`test-fixtures/scratch-workspace-min/seeds/phase04-*`・`single/`）は `false` にしている。
- `bfs-state.json` が既にある repo の再開・`--re-discover` では下調べ・シード確認は行われない（U3）。台帳が無いため
  `doc-targets` は確定ファイルの HIGH・MEDIUM の全件を返し、document-agent は全ファイルを読んで作る（変更前と同等）。
- 統合パスから分割パスへの移動を LLM が行う。移動元の §2.A… の削除漏れは `module-documentation.md` の配置判定の手順
  （`modules/` と §2.A… の併存確認）で確認する。
- MODULE-LEVEL のモジュールはモジュール資料を持たず、SPO §8 の個別資料列が「なし（…）」の行で表される。
  SPO レビューのチェックリスト（`reviewer-checklists/SPO.md` 項目6）はこの行を指摘しないよう改めた。
- 再検討条件: `prelim_summary` の蓄積により、(1) `SPECOUT_SEED_GATE` の既定を `false` にできるか、(2) 波紋調査の自動スキップが
  妥当か、(3) 下調べの部分成果の再利用が必要か、を判断する。配置判定の MODULE-LEVEL 条件の見直しは別プランで扱う。
