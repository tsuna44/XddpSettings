# ADR-0028: 工程4a 波紋調査で、C++ の受け手のクラスを言語の規則・名前空間・式の型から決める理由

Status: Accepted（承認済み）
Date: 2026-10-17

- プラン: [plans/PLAN-20261016-specout-cpp-receiver-resolution.md](../../plans/PLAN-20261016-specout-cpp-receiver-resolution.md)
- 前提 ADR: [ADR-0022](ADR-0022-specout-cpp-class-identity.md)（C++ のメソッド・メンバー変数を `name[CLASS:X]` で追う）
- 調査記録: [docs/specout-redesign-study-2026-10.md](../specout-redesign-study-2026-10.md)（§5.7 の内訳・§5.8 の計測）
- 試作・計測のスクリプト: [plans/redesign_docs/cpp-receiver-resolution/](../../plans/redesign_docs/cpp-receiver-resolution/README.md)

## Context

ADR-0022 は、C++ のメソッド・メンバー変数を `name[CLASS:X]` で送り、ヒットの受け手のクラスを修飾・含むメソッドのクラス・宣言の型から決めて、
別のクラスの同名を偽陽性（`other-class`）にした。決められない出現は `name-only` で残す。Consequences の「限界」に、型の推論（`auto`・戻り値）と
名前空間の区別を挙げ、Decision §2 で「クラス名は素の名前で、名前空間は区別しない」とした。

2026-10-16 に残った `name-only` の原因を数えた（調査記録 §5.7）。spdlog の2つの PR で `name-only` の `[CLASS:…]` のヒット行は 1,992 行・2,303 行あり、
最も多いのは「出現が名前空間・列挙・自由関数で、言語の規則でメソッドになりえない」もの（約3割・約4.6割）、型の推論で決まるものは1割強だった。
外れるべきファイルの多くは、`fmt_lib::format(…)`（名前空間の別名で修飾した自由関数）・`std::swap(…)`・`tcp_client` 自身の `close()`（同じ名前空間の
条件コンパイル別の同名クラス）を関係ありとした雑音の経路だけで届いていた。

**ADR-0022 の再検討の条件との関係:** ADR-0022 は「実開発のサブ機能の粒度の正解を作って評価し、`name-only` の雑音が判断の妨げになる場合」に
名前空間の修飾・型の推論を検討するとした。本 ADR はこの条件を満たしていない。2026-10-16 にユーザーが §5.7 の内訳を見て進めると判断した（評価は後で行う）。

## Decision

決められない出現は今どおり `name-only` で残す（見落としを増やさない）。次を加える。

### 0. 構文解析の誤りの中・誤りのあるファイルでは決めない

tree-sitter のエラー回復の中では、節の種類と名前空間・クラスの入れ子が誤りうる（fmt で、同じクラス `formatter` が名前空間の経路の違う3つに分かれた）。

- 出現の祖先に ERROR 節があれば、受け手を決めない（`name-only`）。
- 出現のファイルに構文解析の誤りがあれば、自由関数の規則（§2）と、名前空間・クラスの経路を使う探索を使わない（修飾だけで決める）。
- 素の名前が同じクラスが複数あり、1つでも定義のファイルに誤りがあれば、§3・§4 の対象にしない（今どおり決めない）。

決めない向きは届く範囲を広げるだけで、見落としにならない。

### 1. 名前空間・列挙・`::` の修飾と、修飾子・名前空間・列挙子の名前はメソッドではない（A）

次の出現は、言語の規則でクラスのメソッド・メンバー変数になりえないため `other-class` にする。

- 修飾名の修飾子の位置・名前空間の定義・別名の定義・列挙子の宣言・`using` 宣言の名前・tree-sitter が名前空間名と判断した出現。
- 修飾子の無い `::foo`。
- 修飾子 Y がクラスの索引に無く、名前空間の名前・列挙型の名前・`std` のどれかで、かつ除外したファイルを含むテキストに `class Y`・`struct Y` が無いもの。
  テキストを見るのは、除外したディレクトリにだけ定義のあるクラスの修飾を名前空間の修飾と取り違えないため。`enum class Y`・`enum struct Y` の `class Y` は
  クラスではないため、テキストのクラス名に数えない。

修飾子 Y がクラスの索引にあれば（名前空間と同じ名前のクラスがあっても）、今どおりクラスとして扱う。テンプレート引数・索引に無い型なら今どおり決めない。

### 2. 自由関数の宣言・定義の名前と、メソッドでない関数の中の修飾なしの名前はメソッドではない（B）

メソッドでない関数の中には暗黙の `this` が無い。「メソッドでない」は、メソッドとして解析されないか、名前空間で修飾した自由関数（`void detail::f()`。
修飾子が名前空間名で、索引のクラスでなく、テキストにも `class`・`struct` として現れない）。含む関数の無いファイルスコープの出現には当てない
（構文解析の誤りで関数を取り損ねた場合に見落としにしないため）。

### 3. 名前空間をまたいで素の名前が同じクラスだけ、鍵を `名前空間::名前` にする（C）

- クラスごとに囲む名前空間・クラスの経路を持つ（関数は数えない。inline 名前空間は数えない。無名名前空間はファイルごとの名前）。
- 素の名前のクラスが名前空間をまたいで重なるときだけ、鍵を `名前空間::名前`（名前空間に属さないクラスは `::名前`）にする。
  重ならないクラスの鍵は今どおり素の名前にし、既存のエントリ・要約の鍵を変えない。
- 型の名前からクラスの鍵を決めるときは、修飾（引数・ローカル変数・メンバー変数・基底クラスの宣言の型の修飾）があれば経路の末尾との照合、
  無ければ参照した場所の名前空間の内側から外側へ照合する。決まらなければ素の名前（今どおり決めない）。
- 名前空間の名前がオブジェクト形式のマクロ（`#define NS real`）で、すべての定義の本体が同じ識別子なら、経路の比較でその識別子に置き換える。
- エントリの `[CLASS:a::X]` は、途中の経路（`[CLASS:inner::X]`）でも経路の末尾との照合で1つに決まれば、そのクラスとして判定する。

### 4. 同じ名前空間の同名クラスは1つのクラスにまとめる（D）

条件コンパイル・プラットフォーム別の定義（`tcp_client.h` と `tcp_client-windows.h`）は、どの版がビルドされても同じ名前で参照される。
基底クラス・メソッドは和（virtual はどれかが真なら真）、メンバー変数の型・戻り値の型は一致すればその型、違えば決めない。
一部の版にしか無いメソッド・メンバー変数は、それを宣言したクラスに当たったら「決まらない」とする（ある版の基底クラスのものに結び付く呼び出しを、
まとめたクラスのものとして偽陽性にしないため）。和で扱う向きは関係ありを増やすだけで見落としにならない。

### 5. 受け手の式の型は、決められる形だけ求める（E）

識別子の宣言の型に加え、`this`・括弧・`*p`・`p[i]`・`new T`・`make_shared<T>`・`T(…)`・メンバー変数の型・メソッドと自由関数の戻り値の型・範囲 for の要素
（`vector` 等の1つ目のテンプレート引数、`map` 等の `first`／`second`）・基底クラスで修飾したメンバー変数（`Base<M>::m`）を求める。たどる深さは8まで。
戻り値が `auto`・テンプレート引数の場合と、オーバーロードで戻り値が違う場合は決めない。

関数の本体の中で宣言した名前は、出現から見える宣言のうち最も内側のスコープのものを使う（ブロック・`if`・`while`・`switch` の初期化と条件・`for` の初期化・
範囲 for・lambda と catch 自身の引数）。構造化束縛の名前は決めない。見える宣言が無ければ、引数ならその型、引数でもなければ決めない。
上書きの表（同じ名前は最後の宣言）では、同じ関数で使い回す範囲 for の変数名・lambda の引数を外側の同名の変数の型で決めて偽陽性にしうるため。

### 6. テンプレートの包みを上って修飾・メンバーを判定する

`T::template create<int>()`・`obj.template foo<int>()` は、包み（`template_function`・`dependent_name`・`template_method`）を上った節で修飾名・メンバーとして扱う。
上らないと修飾なしの名前として §2 に当たり、テンプレート引数で修飾した呼び出しを偽陽性にする。

## Consequences

- **計測（オフライン。LLM 分類0件。spdlog の2つの PR・fmt #4679・frr）:** 増えたファイル 0。正解（PR の変更ファイルのうち既存のコードの変更）は全実行で基準と同じ波で確定した。
  外れたファイルは雑音の経路だけで届いていた（本当の依存 0 件）。frr（C）はヒット表が基準と同一。
  name-only の `[CLASS:…]` の行は spdlog で 1,992 → 748・2,303 → 453 行。数値は調査記録 §5.8 の「実装後の計測」。
- **増える向きの変化:** 構文解析の誤りの多い母体（fmt）では、誤りの中の出現を決めなくしたため name-only の行・訪れたシンボル・ヒット数が増え、波ループの時間が延びる。
- **名前空間の区別（C）の効果は計測した母体で確かめられなかった:** 名前空間をまたぐ同名クラスがいずれも構文解析の誤りのあるファイルを含み、§0 で対象外になった。fixture のテストで確かめている。
- **範囲外:** テンプレートの依存型・テンプレート引数の型の変数の受け手、オーバーロードの解決・ADL・`using namespace`・`using` 宣言による名前の探索・関数ポインタと `std::function`・
  演算子オーバーロード、マクロの本体の中の出現、条件コンパイルで定義が分かれる型の別名、規則2（リポジトリの外の型の受け手。`outside_receiver`）の型の決め方。
  無名名前空間のクラスを名前空間の外から参照した出現は、同名のクラスが他のファイルにもあれば決めない。
- **エントリの書き方の違い:** `[CLASS:sinks::base_sink]` と `[CLASS:spdlog::sinks::base_sink]` は同じクラスとして判定するが、visited・要約の鍵はエントリ文字列のため
  別のエントリになり、同じ名前を検索し直す（結果は同じ）。スクリプトが送るエントリは常に鍵の形。
- **進行中の調査:** 素の名前の `[CLASS:X]` と鍵の `[CLASS:a::X]` が別のエントリになる。後方互換性は保証しない（進行中の調査は取り除いて作り直す）。
- **再検討の条件:** 実開発のサブ機能の粒度の正解で評価して、`other-class` にした出現に本当の依存が見つかった場合は、該当する規則を外す。
  構文解析の誤りの無いファイルで節の種類が誤る場合は、行単位の確認（規則の分類ごとに無作為に4行ずつ）では見つかっていない。
