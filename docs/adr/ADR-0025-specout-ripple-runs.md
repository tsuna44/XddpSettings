# ADR-0025: 波紋調査を1回＝1フォルダの記録にし、SPO を採用した調査の合算で作る理由

Status: Accepted（承認済み）
Date: 2026-10-13

- プラン: [plans/PLAN-20261013-specout-ripple-runs.md](../../plans/PLAN-20261013-specout-ripple-runs.md)（P4a）。
  PLAN-20261012-specout-standalone-ripple（承認前）は本 ADR の決定で置き換える
- 前提 ADR: [ADR-0019](ADR-0019-specout-static-slicer.md)（判定エンジン・予算・state に固定する設定）、
  [ADR-0023](ADR-0023-specout-two-layer-output.md)（出力の2層化・追加下調べ・波紋調査なしの経路）、
  [ADR-0024](ADR-0024-specout-ripple-trace.md)（伝播グラフ・階層表）、[ADR-0016](ADR-0016-common-procedures-split.md)（共通プロシージャ）
- 調査記録: [docs/specout-redesign-study-2026-10.md](../specout-redesign-study-2026-10.md)（§4.3・§6 の P4a・§7.1 の G1〜G7）

## Context

- 方式の案ごとの波紋調査の結果を SPO に取り込む方法が無く、採用案の影響が回帰テスト（SPO §5.2 から作る）と変更設計の参照から漏れていた。
- 波紋調査は工程4a の中でしか実行できず、`--re-discover` で足すと SPO の仕上げ・AI レビュー・人のレビュー・工程4b まで続いた。
  工程5の方式検討エージェントには波紋調査を使う手順が無かった。
- `re-discover` は工程4a の状態に新しいシンボルを混ぜ込む（frontier を置き換え、訪問済みの集合を引き継ぐ）ため、
  どのファイルがどのシンボル由来かを後から分けられず、一度足した調査を取り消せなかった。
- 影響範囲は「狭める誤り」の方が重い（影響漏れは後工程で気付きにくい。調査記録 §4.3）。調査の取り消しを LLM の判断で行うと危うい。

## Decision

### 1. 波紋調査は1回＝1フォルダの独立した記録（G1・G2）

- 置き場所は「どの工程から実行したか」ではなく内容（母体調査）で決め、常に `04_specout/{repo}/ripple/{名前}/` に置く。
  工程4a の初回は `initial`、人が足した調査は `run-{n}` 等、工程5の方式の案ごとの調査は `arch-{案}`、クロスリポジトリ伝播は `cross-{提供 repo}-{n}`。
- 調査ごとに独立した state・discovery-log・波ファイル・要約を持つ。調査の記録 `ripple/runs.json`（名前・由来・シード・採用の有無）は
  `specout_bfs.py` の `run-add`／`run-adopt`／`run-unadopt`／`run-remove`／`run-list` だけが書く（SKILL・エージェントは直接書き換えない）。
- 下調べ・シード確認・SPO の仕上げの成果物は repo で1つ（`{repo}/work/`）のまま。

### 2. 「追加」と「新たに」の区別をやめ、採用の有無だけで区別する（G3）

- `--re-discover`・`specout_bfs.py re-discover`・`merge-frontier --reset-wave-origin` を廃止した。シンボルを足して調べるのは新しい調査で、
  第0波から上限の波数まで調べる。
- 調査どうしは訪問済みの集合を共有しない（H4）。同じ所を調べ直すが、スクリプトだけで軽く、調査ごとに取り消せる。
- 調査の設定（予算・判定エンジン・波数上限）は、調査を始めたときの `xddp.config.md` の値で state に固定する（H5）。

### 3. SPO の波紋調査の欄は採用した調査の合算で作る（G4）

- `doc-targets`・`ripple-summary`・`funcmap-counts`・`assemble-spo` に `--repo-dir` を加え、採用した調査の合算を使う。
  確定ファイルは和集合（波＝調査ごとの波の最小〔H3〕、同一性＝どれかで `resolved` なら `resolved`、確信度＝高い方）、
  シードの直接参照は和集合（ヒット行数は最大）、打ち切りは調査の名前を付けて連結する。
- 採用した調査の状態ファイルが無い・壊れている場合は黙って除かずに止まる（影響範囲が狭まるため）。
- 採用した調査が0件は「波紋調査なし」として扱い、`work/no-ripple.json`（人が初回の調査を作らないと決めた）の有無で文言を書き分ける。
  `assemble-spo --no-ripple` は廃止した。
- モジュールの自動の割り当ては `"auto": true` を付け、SPO の仕上げのたびに外してから合算で割り当て直す（取り消した調査の割り当てを残さない）。
  調査ごとの出力は調査のディレクトリの写しに割り当てを書き、repo の割り当てを変えない。
- document agent に渡す ENTRY_POINTS は、人の指定の累積と採用した調査のシードの和集合。累積に書き戻すのは人の指定だけ。
- 伝播グラフ・階層表は調査ごとに作り、合算は作らない（必要になれば後から）。

### 4. 採用・取り消しを決めるのは人（自動は3つだけ）

- 自動で採用するのは、工程4a の初回の調査・工程5の採用案の調査（Step C）・クロスリポジトリ伝播の調査だけ。それ以外は人が `/xddp-investigate` で決める。
  LLM は根拠を添えて取り消し等を提案できるが、実行しない（誤りの重さが非対称なため）。
- 人が初回の調査を取り消した場合（`unadopted_by` がある）は、工程4a の再実行で採用し直さない。
- 人が「波紋調査なし」と決めた repo へのクロスリポジトリ伝播は自動で調査を作らず、`/xddp-investigate ... ripple --adopt` を案内する（H9）。

### 5. 新しいスキル `xddp-investigate`（H1・H2）

- 動詞 `ripple`・`adopt`・`unadopt`・`remove`・`list`・`finish`。調査の名前は `--name`（シンボルと区別する）。
  P4b の追加調査も同じスキルで受けるため、波紋調査に限らない名前にした。
- 下調べの完了後から実行できる。工程4a の完了前の採用・取り消しは記録だけを行い、SPO への反映は工程4a の SPO の仕上げに任せる（H6）。
- 工程4a の完了後に採用が変わると、SPO を `work/spo-backup/` に退避してから仕上げ直し、書き直した節を報告する。SPO の AI レビュー・人のレビューは行わない（H8）。
- CRS への反映は工程5の状態で分ける（H7）: 未着手なら工程5で DSN を通じて、進行中なら DSN の更新を経て Step C で、それ以外は人に確認して更新する。

### 6. 工程5: 申告 → 人の許可 → 案ごとの調査 → DSN への反映 → Step C での採用

- 方式検討エージェントは Bash を持たないため、波紋調査を申告ファイルに書く（`tools:` は変えない）。SKILL が人の許可を得て調査を実行し、
  エージェントを反映モードで1回だけ再起動して、上限つきの要約 `ripple-digest.md` を DSN の影響範囲・QCD に反映させる（1ラウンド）。
- Step C で採用案の最新の調査を採用し、前に採用していた別の案の調査を取り消す（`adopted_by: step5` のものだけ。人の採用は変えない）。
  `finish-needed` が真の repo（採用が変わった・前回の仕上げが途中で止まった）で SPO を仕上げ直してから CRS へ反映する。
- SPO の仕上げで止まった場合は `/xddp-05-arch {CR} --from-step-c` で再開する（H10）。採用・取り消しは冪等で、`finish-needed` は
  `work/specout-finish.json`（開始・成功と採用した調査の集合）から決まるため、再開で仕上げ直しが漏れない。

### 7. クロスリポジトリ伝播は消費側の新しい調査

- 消費 repo に、提供 repo ごとに1つの調査 `cross-{提供 repo}-{n}` を作る。伝播の記録の状態は `deferred` → `running`（調査を作った。調査の名前を持つ）→
  `propagated`（完了・採用）。途中で止まっても `running` の組が同じ調査を再開し、2つ目の調査を作らない。
- 調査を取り除くと（`run-remove`・手で削除）、伝播の記録の組を `deferred` に戻す（その伝播が二度と実行されなくなるのを防ぐ）。

### 8. 共通プロシージャへの切り出し

- 波ループ・判定エンジンの決定と照合・件数一致検証・手で復旧する手順・初回以外の調査の実行・調査ごとの出力・資料の記載量・SPO の仕上げを
  `xddp-common/procedures/` に移し（`ripple-*.md`・`specout-doc-levels.md`・`specout-finish.md`）、工程4a・`xddp-investigate`・工程5で共有する。
  単一スキル専用の参照ファイルを他スキルから読まない規則（CLAUDE.md）に従うため。`xddp-04-specout/recovery-procedures.md` は削除した。
- 停止時の案内はすべて呼び出し元が渡す `RERUN_COMMAND` で書く。

### 9. 追加下調べの対象を採用した全調査のシードに広げる（ADR-0023 の E5 の改訂）

- シードが直接参照するのに資料の無いファイルの自動の追加下調べ（ADR-0023）の対象を、初回の調査のシードから採用した全調査のシードに広げた。
  上限（`SPECOUT_MAX_AFFECTED_FILES`。repo ごとの累計）は変えない。

## Consequences

- SPO §1 の「調査起点」は調査ごとのシード、§1.x は採用した調査ごとの1行になった（表の形が変わる）。§5.0 の表の直後に「最も浅い到達波は調査ごとの波の最小」の注記が付く。
- 初回の調査だけを採用した SPO のスクリプトが書く欄（§5.0〜§5.2・§5.5・§9）は、変更前と同じ値になる（unittest で合算と単独の要約の一致を確かめる）。
  ただし §9 には、検証スイープを行っていない採用した調査があれば「検証スイープ未実施」が加わる。
- 工程4a の状態ファイルの置き場所が変わるため、工程4a の途中の CR はやり直しが必要（後方互換は保証しない）。
- 方式の案ごとの調査は工程5で人の許可を要し、Step C で追加下調べと document agent が動きうる（トークンが増えうる）。
- 調査どうしが訪問済みの集合を共有しないため、重なりの大きい調査を複数足すと検索の時間は増える（LLM 分類は C / C++ / Python 以外の言語のヒットだけ）。
- 人が直した SPO の欄は、採用・取り消しの後の SPO の仕上げで書き直されうる。退避した SPO との差分で確かめる。

## 対象外（後続）

- 人の依頼による追加調査・資料化（P4b）。ADR-0023 の E4（人は選ばない）の改訂は P4b の ADR に書く。
- 採用した調査を合わせた伝播グラフ・階層表、`xddp-status` での一覧表示、スモークハーネスへの新スキルの追加。
