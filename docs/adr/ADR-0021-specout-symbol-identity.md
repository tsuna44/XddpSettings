# ADR-0021: 工程4a 波紋調査で、名前が同じだけの別物をリンケージの規則で区別し、区別できないものは「名前の一致のみ」として残す理由

- 調査記録: [docs/specout-redesign-study-2026-10.md](../specout-redesign-study-2026-10.md)（§4.3・§5.2・§6 の P2）

## Context

工程4a の見直しの調査で、波紋調査の確定ファイルの大半が「名前が同じだけの別物」への到達だと分かった。

- M2（u1-eval frr・CR-2026-803）の確定 832 ファイルから層別抽出した 30 件のうち 24 件（80%）が名前の一致のみの到達だった（M-a）。
  原因は、送り手が static のグローバル変数 10 件、送り手が関数のローカル変数 6 件、`false-positive` だけのファイルの確定 8 件（M-b）。
  最後の 8 件は P2a（PLAN-20261010）で直した。
- ローカル変数が送られた仕組み（2026-10-11 に今のスクリプトで再現）: 次の波のシンボルの `global` の出口は、書き込み先の名前が
  「リポジトリのどこかにファイルスコープの宣言がある名前」（`GLOBAL_NAMES`）なら `global` になっていた。frr の `bgp_clear` は
  `node`・`nnode` をマクロ（`VTY_BGP_GR_DEFINE_LOOP_VARIABLE`）で宣言しており、ローカル変数と認識できない。一方 `bgpd/bgpd.c` は
  tree-sitter のエラー回復で関数の本体の一部がトップレベルに出て、そのローカル宣言 `struct listnode *node, *nnode;` が
  ファイルスコープの宣言に見えていた。別ファイルの誤った解析の宣言が、ローカル変数を `global` にしていた。
- `GLOBAL_NAMES` は static かどうか・どのファイルの宣言かを持たず、次の波のシンボルは修飾の無い名前でリポジトリ全体を検索していた。
  M-b の `master`・`nodes`・`state` はいずれも static だった。
- ファイルスコープの宣言の走査はトップレベルの子だけで、`#ifdef __cplusplus` / `extern "C" {` の中の `extern` 宣言（frr の
  `extern struct bgp_master *bm;` 等）を見落としていた。
- 呼び出し先の要約は同名の全定義の和で、他のファイルの static 関数・別プログラムの同名関数も混ざっていた。
- C++ の母体（fmt・spdlog）では構文解析の誤りが多く（誤りを含むファイルが fmt 20 中 19、spdlog 114 中 98）、索引そのものが弱い。

調査資料 §4.3 は、誤りの重さが非対称（見落としは影響漏れ、別物の到達は資料の水増し）であることを踏まえて、三段構え
（① 機械的に区別する ② 区別できなかったものは残す ③ LLM の関与を限定する）を提案した。

## Decision

### 1. 名前の解決は C/C++ の翻訳単位の規則（リンケージ）に限る

`specout_slice.py` の `Repo.build_index` が、ファイルごとにファイルスコープの宣言を `#ifdef`・`extern "C"`・名前空間の中まで走査し、
内部リンケージ（ヘッダ以外の static・無名名前空間・そのファイルで定義したマクロ）、外部から見える名前（`extern` の変数の宣言・ヘッダの
ファイルスコープの変数の宣言とマクロ・関数の中のブロックスコープの `extern`）、ファイル内の宣言を記録する。外部から見える名前に関数の宣言を
入れないのは、書き込み先の解決にだけ使うためである（関数名への書き込みは誤った解析でしか起きない。spdlog では、トップレベルに出たメソッドの
プロトタイプ〔`logger.h` の `err_handler_` 等〕を入れると、次の波へ送るシンボルが今より増えた。2026-10-11 計測）。

書き込み先の名前は、書き込んだ関数のファイルから見て次の順に解決する（`Repo.resolve_global`）。

1. そのファイルの内部リンケージ → `name[FILE:path]`（言語の規則で決まる）
2. 外部から見える → `name`（今どおり全域）
3. そのファイルの static でない定義（`extern` の宣言が見えない） → `name[FILE:path]`、ただし `name-only`
4. 見える宣言が無い → `unknown`（呼び出し元へ。ローカル変数を送らない）

手順3を `resolved` にしないのは、`extern` がマクロで宣言されている・除外ディレクトリにだけある場合と、誤った解析の宣言とを構文木から
区別できないためである。呼び出し先の要約も、呼び出し元のファイルから呼べる定義（そのファイルの static、無ければ static でない定義と
ヘッダの定義）だけで作る。0件になる場合（`#include "x.c"`・誤った解析）は全定義の和に戻す（呼び出し先の影響を消さない）。

### 2. `[FILE:…]` は `[MEDIUM:…]` と別のエントリにする

`[MEDIUM:…]` は LLM 分類の「引数として伝播」で確信度の低いエントリであり、ケースA/B/C・HIGH/MEDIUM の交差ルールの対象になる。
`[FILE:…]` は「そのファイルの中でしか参照できない名前」で、確信度は HIGH、交差ルール・ケースA/B/C の対象外とする。
同じファイルの検索でも別のコマンド（種別 `FILE`）にし、dedup の鍵も分ける。

### 3. ヒット側の除外は構文上の位置と言語の規則に限り、型の推測はしない

変数のシンボルに対するメンバー名（C と Python）・同名のローカル変数／引数・引数の宣言子の名前、修飾なしのエントリに対する
ヒットしたファイル自身の static を `false-positive`（`member-name`・`shadowed-local`・`param-name`・`other-static`）にする。
種類（`next_symbol_kinds`）を限るのは、関数のシンボルを同名のローカル変数で消さないためである。人が入れたシードには
`other-static` を適用しない。C++ のファイルには `member-name` を適用しない（`this->x_` のつながりを切らないため）。

### 4. 区別できなかったものは捨てずに `name-only` の印を付ける

ヒット・エントリ（`entry_identity`）・確定ファイル（`identity`）に `resolved` / `name-only` を付ける。到達は削除しない。
経路の同一性は「ヒット1件の値」と「検索したエントリの値」がともに `resolved` のときだけ `resolved` とし、`resolved` は下げない。
資料の確定の材料に印を出し、document agent は `name-only` のファイルを「同一性は未確定（名前の一致のみ）」と書いて残す。

### 5. LLM に同一性を判定させない

LLM 分類のヒットと規則判定のヒットは常に `name-only` とする。Step A-cross-propagate（cross SPO で LLM が識別した共有インタフェース）で
入れたシンボルも `name-only` とする（`re-discover --entry-identity name-only`）。材料に同名の定義の位置は入れない。

### 6. C++ の構文解析の改善・クラス修飾・型による構造体メンバーの追跡は分ける（P2b）

M-b でこれらが単独で必要になった件は0件で（frr は C）、C++ ではまず構文解析の誤りを直す必要があり、型の推論と新しいエントリ表記が
要って規模が大きいため、別プラン（PLAN-20261011-specout-cpp-identity）で扱う（2026-10-11 ユーザー判断）。本 ADR の範囲では、
C++ のメソッドが書く解決できない名前は今どおり `unknown` ＋ `out(this)` とし、同名の定義が複数ある名前に `name-only` を付けるまでとする。
C++ のメソッドが書く名前は、解決できた場合（外部から見える・`[FILE:…]`）でも暗黙の `this` のメンバーと区別できないため `name-only` とする
（到達は変えず、印だけ。spdlog のヘッダの誤った解析で外部から見える `last_log_secs_` 等が `resolved` にならないようにする）。

## Consequences

- 別物を追わない方向の変更のため、本当の依存を切ると影響漏れになる。切る判断を static・`extern` と構文上の位置に限ったが、
  次は見落としになりうる（`resolved` と表示されるものを含む）:
  - `extern` がマクロで宣言されている・除外ディレクトリにだけある変数（手順3・4。手順3は `name-only`、手順4は呼び出し元へは伝播する）
  - `#include "x.c"` で `.c` を取り込む書き方の static（定義したファイルの中だけを検索する）
  - `shadowed-local` は関数単位の近似（ブロックの中だけのローカル変数が、同じ関数の別の場所の参照まで偽陽性にしうる）
- 区別できず `name-only` に落ちるもの: 関数ポインタ・マクロによる宣言・`void*`・テンプレート・動的ディスパッチ・C++ の修飾・別プログラムの
  同名の定義。C / C++ / Python 以外の言語（LLM 分類）と tree-sitter の無い環境（規則判定）では、すべての確定ファイルが `name-only` になり、
  印は情報を持たない。
- 同一性の印は探索の順序に依存する。`name-only` として検索済みのエントリに後から `resolved` の経路が届いても再検索しない
  （広い側〔未確定〕に倒れる）。`symbol_kinds`・`symbol_summaries` は素名で持つため、別ファイルの同名の static 関数の要約は混ざる。
- C++ の母体では構文解析の誤りで索引が欠け・誤り、static・無名名前空間・定義の数の判定が正しくない場合がある（P2b で改善する）。
- 要約（影響機能一覧）に「確定 n 件／名前の一致のみ m 件」を出すのは P1 で行う。再検討の条件: M2・redis の評価で正解モジュールが
  出そろう波が遅くなった場合は、どの除外・解決で切れたかを特定して判断し直す。
