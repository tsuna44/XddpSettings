# ADR-0011: VCS（バージョン管理システム）抽象層の設計判断

Status: Accepted
Date: 2026-08-26

## Context

XDDP 工程7（コーディング）・工程8（静的検証）・工程10（テスト実行）・`xddp.close`（クローズ）で
ブランチ作成・コミット・差し戻し時の巻き戻しが未定義だった（`docs/xddp-tool-analysis-2026-08.md` §3 #2）。
`PLAN-20260813-vcs-abstraction-branch-commit.md` はこの課題に対し、CR 単位の作業ブランチ自動生成・
工程完了時の自動コミット・差し戻し時の安全な巻き戻しを提供する VCS 抽象層（`xddp_vcs.py`）を導入した。
Git 以外の VCS（Subversion 等）を使う環境や VCS を使わない環境もあるため、VCS 種別ごとの処理を
関数群に分離し、将来 Git 以外の VCS へ拡張可能な構成にする。本 ADR はそのプラン策定過程（18回超の
プランレビューを含む）で確定した設計判断を記録する。

## Decision

### Decision 1（SVN 非対応）

Git のブランチ作成はローカルで即時・無コストなのに対し、SVN の標準的な運用は `svn copy` による
サーバー側リビジョン作成＋`svn switch` を伴いネットワーク往復が必要な上、一度作成すると軽くは
取り消せない。この非対称な実装を実績のないまま UI に露出させるのは時期尚早と判断し、本フェーズでは
Git/None のみ実装し SVN を `--vcs-type` の `choices` に含めない。`VCS_TYPE: auto` 選択時に `.git` が
見つからないリポジトリ（SVN 管理下を含む）は `none` 相当にフォールバックし、VCS 統合機能（自動
ブランチ作成・自動コミット）を利用しない運用とする。

### Decision 2（関数ベースディスパッチ、クラス階層不採用）

対象が Git/None の2種類のみである現時点では、抽象基底クラス・レジストリ辞書のようなクラスベースの
間接化を導入せず、VCS 種別ごとの実処理を種別プレフィックス付きの関数群（`git_detect`/`git_branch`/
`git_commit`/`git_revert`/`git_status`）に分離し、CLI のサブコマンド処理（`cmd_*`）は
`resolve_vcs_type()` が解決した種別文字列を見て対応する関数へ委譲するだけの薄いディスパッチ層とする
構成を採用した。将来 SVN 等の新規種別を追加する場合、(1) 新規関数群1組（5関数）を追加し、
(2) `resolve_vcs_type()` の auto 判定・各 `cmd_*` のディスパッチ分岐に1 case を追加し、
(3) `--vcs-type` の `choices` に値を追加するだけで対応でき、CLI ディスパッチ層・呼び出し元 SKILL.md
は一切変更不要になる。この局所化はコード側に限られ、`xddp.config.md`／README／CLAUDE.md 等の
人可読ドキュメントは種別ごとに人が読む説明文を書く必要があるため自動的には追従しない（新種別追加時に
手動更新が必要）。本リポジトリの後方互換性ポリシー（既存 CR・成果物の互換性を保証しない）により、
将来 SVN 対応時にこの構成自体を書き換える判断も許容されるため、今の時点で汎用的な差し替え機構を
先取りして作り込む必要は薄いと判断した。

### Decision 3（新規ブランチの起点 ref を明示的に解決する）

新規ブランチ作成時、現在の HEAD からそのまま分岐する素朴な実装は、`xddp.close/SKILL.md`「Step C0:
Pre-close Sync (Parallel-CR Support)」が示す通り複数 CR の並行運用を正式サポートする本ツールの
運用下で、別 CR の作業ブランチにチェックアウトしたまま新しい CR を開始すると、新しい CR のブランチが
前の CR の未マージ内容を土台にしてエラーなく作成されてしまう回帰を生む（ブランチ分離による CR 間の
変更隔離という主目的を無効化しうる）。これを避けるため `VCS_BASE_BRANCH`（デフォルト `auto`）を
導入し、`git_branch()` が新規作成時のみ以下の順序で起点を解決してから分岐する構成にした:
(a) `origin/HEAD` が指す先（例: `origin/main`。`origin/` プレフィックスは除去しない——除去すると
ローカルに同名ブランチが存在しない構成で解決に失敗しうるため）、(b) `main`、(c) `master`、
(d) いずれも無ければ現在の HEAD（警告付き）。ただしコミット0件のリポジトリ（unborn HEAD。例:
`DEVELOPMENT_MODE: new` で `git init` 直後）ではいかなる ref も有効なコミットに解決できないため、
この起点解決自体をスキップし、開始点引数を省略した `git switch -c {branch}` で作成する特別分岐を
設けた。

### Decision 4（作業ツリーの dirty チェック）

対策なしでは、新規ブランチ作成（手順1.5）・既存ブランチ切替（手順3）のいずれも、別 CR（あるいは
同一 CR の未コミットの実装バグ修正）の未コミット変更が新しいブランチへ静かに引き継がれ、無関係な
CR のコミットメッセージの下に混入しうる。これを避けるため、現在の HEAD が対象ブランチ自身である
場合（真の冪等ケース——同一 CR を同一ブランチ上で再実行する通常のフロー）を除き、`git status
--porcelain` が非空（dirty）な状態でのブランチ作成・切替を拒否する構成を採用した。当初は「切替先が
当該 CR 自身のブランチかどうか」を判定軸にしていたが、Step -1 は常に実行中 CR 自身の名前でブランチを
解決するため、真の判定軸は「切替**元**（現在の HEAD）に別ブランチの未コミット変更が残っているか」
であるべきと判明し、上記の構成に修正した。判定粒度は `git status --porcelain` が非空か否かのみとし、
「どの変更がどの CR に属するか」の精緻な判定は採らない（ツールが機械的に判定できないため）。結果として
無関係な未追跡ファイル1件でもブロックされる保守的な挙動になることを許容し、`.gitignore` の整備で
回避する運用を案内する（Decision 8 参照）。

### Decision 5（VCS 副作用の対象リポジトリを SPO の存在で CR スコープへ限定する）

VCS の副作用（ブランチ作成/切替・コミット・revert 案内）の対象を `REPOS_KEYS`（全リポジトリ）に
すると、`xddp.close` が明示的に前提とする Parallel-CR 運用環境で、本 CR と無関係な他 CR・他開発者の
未コミット変更まで `"{CR} 完了"` 等のメッセージで巻き込んでコミットする不可逆なリスクがある。
「status 確認等の読み取り専用処理は広いスコープでよいが、commit/branch/revert 等の副作用を伴う処理は
CR の対象範囲に限定する」という原則を、本抽象層の全呼び出しに一貫適用した。

当初案はこの限定を工程7・工程8・工程10 では `AFFECTED_REPOS`、`xddp.close` では
`CR_TOUCHED_REPOS`（CODING メモの存在）という異なる材料で表現していたが、いずれも成立していなかった。
前者は `xddp.common/SKILL.md`「## Resolve Affected Repos」が `FILTER_BY_SPO = false`（これら3スキルは
いずれも false 指定）のとき `REPOS_KEYS` のコピー——全リポジトリと同一——を返すため限定になっておらず、
後者は CODING メモが `xddp-coder-agent` の生成物であり `xddp.08.verify/SKILL.md` が明記する通り人手
実装フローでは存在しないため、コミット漏れが最も起きやすい経路で最終コミットが機能しなかった。

判定材料を**当該リポジトリのスペックアウト成果物（`{CR_PATH}/04_specout/{repo}/SPO-{CR}.md`）の存在**に
統一し、共通プロシージャ `## Resolve VCS Target Repos`（`xddp.common/SKILL.md`）として工程7・8・10・
close の全副作用呼び出しから再利用する構成を採用した。検討過程では CHD インデックスの存在も候補と
したが、`xddp.06.design/SKILL.md` が CHD インデックスを `For each {repo} in AFFECTED_REPOS:` で
条件なしに全リポジトリ分生成するため限定にならないことが判明し採らなかった。SPO は
`xddp.04.specout/SKILL.md`「## Step 0.5 (confirmation gate)」で人が対象リポジトリを絞り込んだ結果に
対してのみ生成されるため、「本 CR が母体調査の対象としたリポジトリ」を表す、人の意思が反映されうる
唯一の決定的な材料である。

**残る限界:** SPO の存在が示すのは「調査対象にした」ことであり「調査の結果、影響ありと確定した」こと
ではない。`xddp.04.specout` は全リポジトリの調査を推奨しており、人が Step 0.5 で絞り込まない既定
フローでは `VCS_TARGET_REPOS` が `REPOS_KEYS` と一致し、限定効果が生じないことがある。本 Decision が
保証するのは「限定できる手段と経路の提供」であって「あらゆる構成での限定」ではない。完全な解消には
工程4成果物への影響有無フラグの導入が必要であり、本フェーズのスコープ外とした。

既存の `## Resolve Affected Repos`（`FILTER_BY_SPO = true`）をそのまま再利用しなかったのは、同分岐が
cross CHD の文書読解（非決定的判定）を含み、かつ `HAS_CROSS` の契約が `xddp.close` と一致しないため
である。`DEVELOPMENT_MODE: new` では工程4がスキップされ SPO が原理的に存在しないため、この場合に限り
CHD インデックスへフォールバックする。

### Decision 6（自動ブランチ作成・自動コミットを opt-out（デフォルト有効）とする）

`VCS_AUTO_BRANCH: true` / `VCS_COMMIT_ON_STEP: 7,10` をテンプレート既定とすることは、既存 Git
ユーザーに対して確認なしの挙動変化になる。opt-in（既定無効）にする代替案も検討したが、本機能の目的
（AI 支援開発でのブランチ・コミット漏れ防止）に対しては有効な状態が本来あるべき姿であり、opt-in では
大半のユーザーが有効化しないまま機能が使われない。コミット前の対象ファイル一覧表示（監査ログ）・
`.gitignore` 整備の案内・**正しいオプトアウト経路の明示**（自動コミットは `VCS_COMMIT_ON_STEP: none`、
すべて止めるなら `VCS_TYPE: none`）で実害リスクを軽減できると判断し、opt-out を採用した。

当初案はオプトアウト経路を `VCS_AUTO_BRANCH: false` 単独と記述していたが、同キーは自動コミットを
制御しないため既定有効化の根拠が成立していなかった（`## VCS Auto-Commit` は `VCS_TYPE` と
`VCS_COMMIT_ON_STEP` のみを参照し `VCS_AUTO_BRANCH` を参照しない）。正しい経路へ修正済み
（Decision 16 も参照）。

### Decision 7（`xddp.close` Step C0 のリモート追従確認で `VCS_TYPE: auto` を `git` と同一に扱う）

`xddp.close/SKILL.md`「Step C0: Pre-close Sync」の「1. Source Code Sync Check」はリポジトリループを
持たず `WORKSPACE_ROOT` に対して直接 `git fetch`/`git log` を実行する既存仕様のため、Step -1 と同じく
`xddp_vcs.py detect` で事前解決すると、標準的なマルチリポジトリ構成（CLAUDE.md「想定するプロジェクト
構成」の通り `WORKSPACE_ROOT` は各リポジトリの親ディレクトリであり `.git` は各サブディレクトリ側に
ある）では `WORKSPACE_ROOT` 自体が git 管理下にないと判定され、`auto`（デフォルト）を使う大多数の
マルチリポジトリユーザーに対してこのチェックが静かにスキップされる回帰になる。`none`（明示設定）の
場合のみスキップし、`auto`/`git` はいずれも試行して失敗時は既存の `git fetch` 失敗ハンドリング
（エラー表示＋続行/中止確認）に委ねる構成を採用した——これは本プラン適用前の無条件実行時の挙動と
同一の失敗時体験であり、デグレードにならない。

あわせて、本プランの既定動作（`VCS_AUTO_BRANCH: true`）により HEAD が作業ブランチになる構成では、
既存の `git log HEAD..origin/main --oneline` →「未マージのリモートコミットがあれば `git pull` を
促す」という案内が誤誘導になる（作業ブランチには upstream が無いため `git pull` 自体が失敗する、
または `git pull origin main` への読み替えで意図しないマージを招く）。検出ロジック自体は変更せず、
案内文のみを現在の HEAD が本ツールの作業ブランチ（`{VCS_BRANCH_PREFIX}{CR}`）かどうかで切り替える
構成にした（作業ブランチ上では `git pull` を促さず rebase/merge の検討案内に変える）。

### Decision 8（破壊的・不可逆な操作には監査可視性を持たせる）

本抽象層は `git add -A`・`git clean -fd`・ブランチ切替という、無関係な変更を巻き込む／不可逆に
削除する操作を自動実行する。これらを人の確認プロンプトで都度止める案は自動化の利点（工程完了時の
記録漏れ防止）を損なうため採らず、**処理は止めずに実行内容を可視化する**方針を採用した:
`git_commit()` は対象ファイル一覧（`git status --short`）を実行前に標準出力し、
`git_revert(untracked=True)` は `git clean -fdn`（dry-run）の結果を `git clean -fd` の実行前に
標準出力し、ブランチ作成/切替は成功時にユーザー通知する。コミット対象からの除外は `.gitignore` の
整備という利用者側の責務とする。

### Decision 9（ブランチのライフサイクル終端をスコープ外とし、CR 間依存は利用者の明示指定に委ねる）

マージ・PR 作成・ブランチ削除は組織ごとの運用差が大きく自動化の前提を置けないため本フェーズでは
扱わない（CR 破棄時のブランチ削除案内は別プラン `PLAN-20260822-cr-abort-flow.md` の `/xddp.abort` が
担当する）。その帰結として、先行 CR が未マージのまま後続 CR を開始すると、後続ブランチは
`VCS_BASE_BRANCH: auto`（既定。`origin/main` 等を起点に解決）により先行 CR の成果を含まない起点から
静かに分岐し、工程7・工程10 で初めて依存先の不在に気付く手戻りになりうる。CR 間の依存関係はツールが
機械的に判定できないため自動追従は行わず、`VCS_BASE_BRANCH` の明示指定（先行 CR の作業ブランチを
指定するか、先行 CR をマージしてから開始する）という利用者操作に委ね、テンプレート注記で案内する。

### Decision 10（`VCS_TYPE` の不正値正規化を `## Load Config` に一元化）

不正値の検出を各呼び出しスキル側で行うと、Step -1 相当の事前検証を持たない `xddp.10.test-run`/
`xddp.close` で生の不正値が `xddp_vcs.py` に渡り `argparse` の `choices` エラーで失敗する抜けが生じる。
`CR_PROFILE` が `full`/`quick` 以外の値のときに `full` へフォールバックする既存パターン
（`## CR Resolution`「### Step 1.X」）に倣い、`## Load Config` の読み込み時点で `auto`/`git`/`none`
以外の値を検出したら警告のうえ `none` へ正規化する構成を採用した。これにより `## Load Config` を
経由する全スキルの `{VCS_TYPE}` は常に3値のいずれかであることが保証され、各呼び出し箇所で個別の
不正値ハンドリングを複製する必要がなくなる。

### Decision 11（呼び出し元 SKILL.md は解決済み種別を引き回さず生の `VCS_TYPE` を毎回渡す）

Step -1 で `detect` した `REPO_VCS_TYPE` を後続ステップ（コミット・status・revert）まで引き回す案は、
差し戻し後の再実行を含む運用で「どの時点の解決結果か」の取り違えを招く。`resolve_vcs_type()` の
再解決コストが `.git` の存在確認1回のみで軽微なことを踏まえ、後続の呼び出しには生の `{VCS_TYPE}` を
渡して `xddp_vcs.py` 側に都度再解決させる構成を採用した。

### Decision 12（dirty 判定から XDDP 成果物ディレクトリを除外する）

`XDDP_DIR`（および `DOCS_DIR`）をリポジトリ内に置く構成（`xddp.config.md` テンプレートが正式サポート
する `XDDP_DIR: repo-A/xddp` 等）では、工程1〜6 が生成する成果物により工程7開始時点でリポジトリが
必ず dirty になり、Decision 4 の dirty ゲートが毎 CR の冒頭で工程7を停止させてしまう。`.gitignore` に
よる回避は、XDDP 成果物がバージョン管理対象であるべきファイルであるため採れない。「工程7前に手動
コミットするのは利用者の責務」と割り切る案・ブランチ作成前に XDDP 成果物を自動コミットする案も
検討したが、前者は毎 CR の手作業を強いる後退であり、後者は工程7開始前に CR 完了前の中間成果物を
コミットする副作用を生む。dirty ゲートの目的が「無関係な**コード**変更の混入防止」であることに
立ち返り、`--ignore-path`（`resolve_ignore_pathspecs()`）によりこれらの成果物ディレクトリを判定対象
から除外する構成を採用した。除外判定はスクリプト側で行い、ディレクトリがリポジトリ外にある一般的な
構成では従来と同一挙動になる。

この除外は**dirty 判定専用**であり、`commit` サブコマンドの `git add -A` には適用しない（意図的な
非対称）。XDDP 成果物はバージョン管理対象であるべきファイルであり、コミットから排除する理由がない
ためである。したがって `XDDP_DIR` をリポジトリ内に置く構成では、工程7・工程10・close の自動コミットに
CR 成果物が含まれる。

### Decision 13（`none` 種別を全サブコマンド no-op「成功」とする）

VCS 非使用時にエラーや専用の戻り値を返す案ではなく、`branch`/`commit`/`revert` は成功（exit 0）、
`status` は常に `clean` を返す no-op とした。呼び出し元 SKILL.md の「If status is dirty: commit」
分岐が自然にスキップされ、各スキルに VCS 有無の分岐を重複実装せずに済むため。

### Decision 14（コミット処理を `## VCS Commit If Dirty` と `## VCS Auto-Commit` の2段に分割）

per-repo の status→commit ループ本体と、`VCS_COMMIT_ON_STEP` によるゲート判定を別プロシージャに
分けた。`xddp.close` の最終コミットは工程番号ゲートを持たないため、1段構成ではループ本体が4箇所目
（工程7・工程10 の2箇所・close）として複製される。2段に分けることでループ本体を3スキル4箇所
すべてで再利用できる。

### Decision 15（VCS 状態が `unknown` のときの停止/続行を処理の副作用有無で分ける）

読み取り専用の確認処理（`xddp.close` Step C-Pre の status チェック）は警告表示のみで続行を許容し、
副作用を伴う処理（`## VCS Commit If Dirty` の commit、Step -1 の branch、revert 案内）は安全側に
倒して停止・中断する。状態不明のまま副作用を実行すると、コミット漏れや意図しない巻き込みに気付けない
まま進行するためである。

**例外ではなく第3の選択肢として `ON_FAILURE: ask` を設ける:** 副作用を伴う処理のうち、停止することで
下流の重要処理が丸ごと失われる呼び出し元（`xddp.close` の最終コミット——下流に成果物昇格・Human
Review Gate・CR 完了記録がある）については、`## VCS Commit If Dirty` の `ON_FAILURE: ask` により
「エラー表示＋続行/中止の確認」を行い、判断を人に委ねる。これは本原則の例外ではない——原則の核は
「状態不明のまま AI が黙って副作用を進めない／黙って先へ進まない」ことであり、人が明示的に選んだ
続行はこれを損なわないためである。既定は `stop` のままとし、`ask` は上記の条件を満たす呼び出し元
にのみ適用する（Decision 20 も参照）。

### Decision 16（`VCS_AUTO_BRANCH` と `VCS_COMMIT_ON_STEP` を直交した独立キーとして維持する）

`VCS_AUTO_BRANCH: false` のとき自動コミットも連動して無効化する案（1キーで「自動化オフ」を表現する
案）も検討したが、採らなかった。ブランチ作成とコミットは分離可能な関心事であり、「自分で切った
ブランチ上で作業しつつ、工程完了時のコミットは自動化したい」という運用は正当なユースケースである。
連動させるとこの組み合わせが表現できなくなり、かつキー名（`VCS_AUTO_BRANCH` ＝ブランチ設定）から
挙動を推測できない隠れた副作用を生む。代わりに、直交していることを利用者が誤解しないよう
`xddp.config.md` テンプレートに「止めたいもの → 設定」の対応表を明示する方針を採った。

### Decision 17（コードを変更しない工程では VCS ゲートで工程を停止させない）

`xddp.08.verify` は静的検証のみを行う読み取り専用スキルであり、Step -1 のブランチ作成/切替に
`xddp.07.code` と同じ「失敗したら停止」を適用すると、作業ブランチ未作成かつ作業ツリーが dirty な
状態（人が手実装した直後——まさに本スキルの主要ユースケース）で検証が1件も実行されずに止まる。
さらにその際の案内（「先にコミットするか `git stash` で退避」）は、検証対象そのものを退避せよという
誤った誘導になる。静的検証の結果は VCS 状態に依存しないため、失敗時は警告のみで検証を続行する構成を
採用した。Step -1 自体を削除しなかったのは、作業ツリーが clean なケースではブランチを整えられる利点が
あり、`xddp.07.code` との構造的対称性も保てるためである。

### Decision 18（dirty ゲートの適用範囲を「CR がコードを変更しうるリポジトリ × コードを変更する工程」に限定する）

Decision 4 の dirty ゲートは、適用範囲を定義しないまま個別に拡張してきた結果、「工程の起動自体を
止める」失敗を複数回（`--ignore-path` 導入前・`AFFECTED_REPOS` の誤用・`xddp.08.verify` への単純
横展開）繰り返した。原因はいずれも、ゲートが守ろうとしている対象（＝**別 CR のコード変更の混入**）
より広い範囲にゲートが掛かっていたことである。そこで適用範囲を次の2軸で定義する: (1) **対象
リポジトリ** — `VCS_TARGET_REPOS`（Decision 5 の判定＝スペックアウト対象になったリポジトリ）に限る。
CR が触れないリポジトリの dirty 状態は本 CR のブランチ分離と無関係である。(2) **対象工程** —
コードを変更する工程（工程7）でのみ停止させ、コードを変更しない工程（工程8）では警告に留める
（Decision 17）。さらに判定対象パスからは XDDP 成果物ディレクトリを除外する（Decision 12）。今後
dirty ゲートを新しい呼び出し箇所へ広げる際は、この2軸に照らして「止めるべきか警告に留めるべきか」を
先に判断すること。

### Decision 19（CLI をサブコマンド先頭形に揃え、開発ハーネスの機械検査を効かせる）

当初案の `xddp_vcs.py --repo REPO --vcs-type TYPE {subcommand}`（グローバルオプション先行形）は、
`tools/harness/refcheck.py` の検査D（CLI 結線照合）がサブコマンドを認識できない形だった。同検査の
`_extract_script_calls()` はトークン列を先頭から走査し、まだフラグが1つも出現していない位置に現れた
語のみをサブコマンドとして認識するため、グローバルオプション先行形ではサブコマンドが `None` のまま
抽出され、`DETERMINISTIC_SCRIPTS` に登録しても1件も照合されない（登録が無意味になる）。さらに仮に
認識されても、トップレベル定義の `--repo`／`--vcs-type` がサブコマンドの有効フラグ集合に含まれず
偽陽性エラーになる。

`--repo`／`--vcs-type` を共通の親パーサ（`argparse.ArgumentParser(add_help=False)`）経由で各サブ
パーサに定義してサブコマンド先頭形（`xddp_vcs.py {subcommand} --repo ... --vcs-type ...`）に揃え、
既存の慣行に合わせた。`DETERMINISTIC_SCRIPTS` の8本のうちサブコマンドを持つのは `xddp_progress.py`・
`xddp_gate_snapshot.py`・`xddp_review_brief.py`・`specout_bfs.py` の4本で（残る4本はフラグのみで
この論点の対象外）、その4本はすべてサブコマンド先頭形である。検査器側を拡張してグローバルオプション
先行形に対応させる案は、サブコマンドを持つ既存スクリプトがすべてサブコマンド先頭形である以上、新規
スクリプト1本のために解析仕様を複雑化することになるため採らなかった。共通の親パーサを
`add_help=False` で生成しなかった場合、`-h/--help` がサブパーサ側の既定 help オプションと衝突して
`argparse.ArgumentError` となり `--help` の実行自体が失敗する点に注意が必要（この場合 `refcheck.py`
の検査Dは「`--help` 解析に失敗し結線照合をスキップ」の警告に落ち、機械検査が無効化される）。

### Decision 20（工程完了時の自動コミットは progress.md 更新の「後」に置く／`xddp.close` は `ON_FAILURE: ask` で解決する）

工程7・工程10の `## VCS Auto-Commit` 呼び出しを、完了を記録する `## Progress Update` の前に置く案
（当初案）と後に置く案を比較し、後を採った。`## VCS Commit If Dirty` は commit 失敗時に停止する契約
（Decision 15）であり、`git commit` の失敗は `user.email` 未設定・pre-commit フックによる拒否・GPG
署名設定の不備等で日常的に起こりうる。前に置くと、コード変更・静的検証・テストがすべて成功している
のに工程の完了が progress.md に記録されないまま停止し、VCS レイヤの都合で XDDP の工程台帳が後退する
（利用者は工程の全再実行か progress.md の手動修正を強いられる）。後に置けば完了記録は保持されたまま
停止し、利用者は VCS 側の問題を解消して再実行するか手動コミットで先へ進むかを選べる。工程7・工程10
ではこの配置により停止契約をそのまま維持できる——失って困る台帳更新がコミットより先に済んでいるため、
契約を分岐させる必要がない。

一方 `xddp.close` の最終コミットには同じ配置規約を適用できない。close の最終コミットは Step A/B/C の
後・Step C0 の前に置かれ、その下流には Step C0（Parallel-CR 同期）・Step C2〜C7（成果物の
`{DOCS_DIR}` 昇格）・Step D（Human Review Gate）・Step E（`## CR クローズ` の progress.md 追記）が
並ぶ。「コミットを台帳更新の後に置く」という位置の付け替えでは、下流工程が丸ごと失われる問題を解消
できない（コミットを Step E の後まで下げると、今度は「昇格前にコードのコミットを保証する」という
最終コミットの主目的が失われる）。そこで close については位置ではなく失敗時の扱いで解決し、
`## VCS Commit If Dirty` に `ON_FAILURE`（既定 `stop` / close のみ `ask`）を追加した（Decision 15）。
`ask` を選んだのは、`xddp.close` における git 失敗時の既存慣行が一貫して「エラー表示＋続行/中止の
確認」（Step C0-1 の `git fetch` 失敗、Step C0-2 の DOCS 非 git 時）であり、最終コミットだけが問答
無用で停止するのは非対称だからである。また Step C-Pre が dirty/`unknown` について「警告があっても
続行は可能」と案内する以上、同一実行内でのハード停止は利用者の期待と衝突する。

すなわち本 Decision は「工程7・工程10 = 配置で解決」「close = 失敗時の扱いで解決」の2本立てであり、
いずれも『VCS レイヤの失敗で XDDP 側の進行・記録が一方的に損なわれない』という同一の目的に発する。

## Consequences

- 既存の Git ユーザーに対して、工程7・工程10完了時の自動ブランチ切替・自動コミットが確認なしで
  有効化される挙動変化がある（Decision 6 の opt-out 既定による）。Git 以外の VCS を使うユーザーは
  `.git` が検出されず `none` 相当にフォールバックするため影響を受けない。
- ブランチのマージ・PR 作成・削除といった終端処理は扱わないため、`xddp.close` 完了後も
  `{VCS_BRANCH_PREFIX}{CR}` は未マージのまま残る（Decision 9）。統合は利用者が既存の運用に従って
  手動で行う。
- VCS 副作用の対象リポジトリ限定（Decision 5）は、人が `xddp.04.specout` Step 0.5 で対象リポジトリを
  絞り込まない既定フローでは `VCS_TARGET_REPOS` が `REPOS_KEYS` と一致し、限定効果が生じないことが
  ある。完全な解消には工程4成果物への影響有無フラグの導入が必要であり、本フェーズのスコープ外である。
- `xddp_vcs.py` はサブコマンド先頭形の CLI（Decision 19）を採用したことで、`tools/harness/refcheck.py`
  検査D（CLI 結線照合）の対象として `DETERMINISTIC_SCRIPTS` に登録済み。SKILL.md 側のフラグ名・
  サブコマンド名の誤りは `make test` で検出される。
- 新しい VCS 種別（SVN・Mercurial 等）への対応は、コード側は新規関数群1組の追加で完結するが、
  `xddp.config.md` テンプレート・README.md・CLAUDE.md の人可読ドキュメント3箇所は自動追従しないため
  手動更新が必要（Decision 2）。
