## Context

**用語「同じ呼び出し口の関数」:** シードの関数と同じ関数ポインタの欄に登録される、別の関数。登録する側の関数ではなく、登録される側の関数を指す。

```
a_init() { ops_a->on_connect = a_on_connect; }   ← 欄 on_connect に a_on_connect を登録
b_init() { ops_b->on_connect = b_on_connect; }   ← 同じ欄に b_on_connect を登録
core.c   (*ops->on_connect)(ops);                ← 呼び出し口。どちらもここから呼ばれる
```

frr PR #22411（M2・CR-2026-803）では bgpd・isisd・ripd・ospfd の4デーモンが変わった。ospfd の変更はシードからの波及ではなく、同じ不具合の
並行の修正だった。変更箇所 `ospf_zebra_connected` は、シード `bgp_zebra_connected`・`rip_zebra_connected` と同じ欄 `zebra_connected` に登録される。
呼び出しは関数ポインタ経由（`lib/zclient.c` の `(*zclient->zebra_connected)(zclient);`）のため、名前でたどる波紋調査ではシードから届かない。
ADR-0019 は関数ポインタ経由の呼び出しを grep 未対応パターン `function-pointer-call` として記録するだけで、呼ばれうる関数を示さない。

frr の `zebra_connected` には17デーモンの関数が登録され、PR で変わったのは4つだった。登録される関数の数は欄によって大きく違い
（frr では2〜30個の欄が88、37個以上の欄が8。northbound の `modify` は620）、すべてを追うと調べる範囲が広がりすぎる。

## Decision

### 1. 候補はスクリプトで決定的に作り、人に示す（波紋調査の中では自動で追わない）

`specout_slice.py callslot-candidates` が Step A-Seed の手順1（`seed-preview` の前）で毎回、候補表の採用したシードについて求める。候補表は変えない。

- 対象のシード: 素の名前・`名前[FILE:p]`・`名前[MEDIUM:p]` で、`名前(` の出現が母体にあるもの（`[FILE:p]`・`[MEDIUM:p]` は登録箇所を `p` に限る）。
  `名前[CLASS:X]` と `root.field` は対象にしない。
- 登録の形: コメント・文字列を除いた本文の `式->f = 名前`・`式.f = 名前`・指示付き初期化子 `.f = 名前`（`&名前` を含む）。対象の言語は C / C++ / Python
  （判定エンジンと同じ拡張子）。除外パターン・拡張子の設定を適用する。
- 同じ呼び出し口の関数: 同じ欄に登録される、シード以外の名前で、`名前(` の出現が母体にあるもの（`NULL` 等は除く）。関数の検出（規則判定の
  `_c_rule_functions`）は使わない（ファイルの前の方で波かっこの対応が崩れると `ospf_zebra_connected` を落とした）。
- 表記: C のソース（ヘッダでない）で、登録したファイルに `static … 名前(` があれば `名前[FILE:登録したファイル]`。それ以外は素の名前。
- 呼び出し口（欄の関数を呼ぶ箇所。`(*式->f)(`・`(*式.f)(`・`式->f(`・`式.f(` の字句の一致）と、シード・おすすめの登録の行を示す。用語だけでは
  伝わらないため、提示と全量の冒頭に一般的な例も毎回示す。呼び出し口はおすすめの判定に使わない。

### 2. 照合の鍵を判定エンジンで切り替える

- `slice`（tree-sitter あり）: 左辺の型＋フィールド名。型は、`式->f`・`式.f` の `式` の宣言（引数・ローカル変数・ファイルスコープの変数・他のファイルの
  `extern` 宣言）、メンバーの連鎖、指示付き初期化子なら初期化する変数・複合リテラルの型（入れ子はメンバーの型。名前の無い構造体のメンバーは
  `型.メンバー` を型名とする）。typedef は元の名前にする。
- 型を求められない登録はフィールド名だけで照合し「型未確認」の印を付ける（外さない）。両方の型が本体のある定義で、異なると決まった登録だけを
  「型が異なる」として外し、全量に載せる。
- `rule`（tree-sitter なし）: フィールド名だけで照合し、全件「型未確認」。

frr では `zebra_connected` はすべて `zclient`、northbound の `modify` は 618件が `nb_callbacks`、1件（`nhg_hooks.modify`）が `nexthop_group_hooks` で外れた。

**型の求め方は判定エンジンの索引（`Repo.build_index` の `file_var_types`・`global_var_types`）と共有しない。** プランは C のファイルスコープの変数の型を
共有の索引に足す案を挙げ、`classify` の結果が変わるなら別にするとしていた。`callslot-candidates` 用に、関係する登録のファイルだけを構文解析して
型を求める処理を別に持った。共有の索引を変えないため `classify` の判定は変わらず、`build_index`（frr で約6秒）も要らない。

### 3. おすすめ（シードに似た同じ呼び出し口の関数）

同じ呼び出し口の関数の本体が、シードの本体で使う「処理の起点になる名前」（呼び出す関数・関数の外で定義した変数・マクロ・列挙子。ローカル変数・
引数・フィールド名・予約語・型名・自分の名前は除く）を、決まり文句を除いて1つ以上使えばおすすめにする。同じ鍵に採用したシードが複数あれば
その和と比べる。決まり文句は鍵ごとに、本体を取り出せた関数（シードを含む）が4件以上のとき、その半数を超える本体に出る名前とする。

本体の取り出しは、`slice` は tree-sitter の関数の節とローカル変数・引数、`rule` は字句（前処理指令の行を空白にした本文で定義の頭部を探し、
条件コンパイルの2つ目以降の枝を空白にした写しで波かっこの対応を取る。名前は全部の枝から取る）。閉じない・定義が無い関数は「本体を確認できず」で、
おすすめにしない。

1つの鍵のおすすめが `SPECOUT_CALLSLOT_MAX_PER_FIELD`（既定 `30`。`0` で無制限）を超えたら、その鍵はおすすめにしない（frr の northbound の表では
おすすめ相当が340件残るため）。

frr では両エンジンとも同じ呼び出し口の関数15件のうち、おすすめは4件（`isis`・`ospf6`・`ospf`・`pim`。PR が変えた `isis`・`ospf` を含む）だった。

### 4. 人が repo ごとに選び、行う場合は初回とは別の調査 `callslot` にする

- 候補表には混ぜず、提示で示す。人は「行わない」（既定）・「おすすめで行う」・「`X`, `Y` で行う」から選ぶ。母体コードを知らず選べない人も、
  「行わない」か「おすすめで行う」を選べる。選択は `callslot-choose` が `work/callslot-seeds.json` に書き、「行う」と人が答えたときだけ `pending` を付ける。
- `SPECOUT_SEED_GATE: false` では選択肢を出さない（人の選択なしに波紋調査を広げない）。途中で止まった `callslot` は続ける。
- 行う場合は、初回の調査が完了・採用済みで `work/no-ripple.json` が無い repo だけ、予約名 `callslot`（由来 `callslot`）の調査を
  `SPECOUT_CALLSLOT_MAX_WAVE_DEPTH`（既定 `2`＝第0〜1波）の波数で作り、完了したら採用する。初回の調査の結果に混ぜないため、
  `/xddp-investigate unadopt` で同じ呼び出し口の関数だけを外せる。人が取り消した・取り除いた `callslot` は作り直さない。
- 採用した `callslot` は SPO の仕上げで他の採用した調査と同じに合算する（ADR-0025）。人が選んだ関数は変更の候補であり、
  シードの直接参照・追加下調べの対象（上限 `SPECOUT_MAX_AFFECTED_FILES` を初回のシードと分け合う）・ENTRY_POINTS・規模の判定に入るのが本来の姿とした。
- 計測: `prelim_summary` に `callslot_candidate_count`・`callslot_recommended_count`・`callslot_choice`・`callslot_seed_count` を足す。

## 却下した案

- **波紋調査の中で同じ呼び出し口の関数を自動で追う:** frr の `zebra_connected` には17デーモンの関数が登録され、PR で変わったのは4つ。
- **同じ呼び出し口の関数を候補表に ☐ の行として足す:** 人が母体コードを知らず選べない場合に「行わない」「おすすめで行う」を選べない。
  初回の調査の結果に混ざり、同じ呼び出し口の関数だけを取り消せない。
- **上限以内の同じ呼び出し口の関数をすべておすすめにする:** frr では15件で確定 1,010 ファイル（10波）と、初回の調査（444）より広く、
  PR が変えなかった関数まで調べる。おすすめ4件でも第2波以降の広がりはほとんど変わらず、広がりを抑えるのは件数ではなく波数だった（既定 `2`）。
- **型で常に照合する:** tree-sitter の無い環境で使えない。
- **規則判定の関数の検出で関数かどうかを決める:** `ospf_zebra_connected` を落とした。
- **下調べのエージェント（LLM）に同じ呼び出し口の関数を挙げさせる・おすすめを選ばせる:** 調査記録 §6 で、スクリプトで決定的に作ると決めた。

## Consequences

- 範囲外: 関数の呼び出しによる登録（`hook_register(h, fn)`・`signal(SIGINT, fn)` 等）、配列の添字の指示子（`[X] = fn`）、位置による初期化子
  （`{ "name", fn }`）、C++ の `&X::m`・ラムダ・`std::bind`・コンストラクタの初期化子並び、Python の束縛メソッド（`obj.cb = self.m`）・辞書、
  C / C++ / Python 以外の言語、他の repo に登録される関数、`/xddp-investigate` での提示、SPO への記載。
- `rule` ではフィールド名だけで照合するため、別の型の同名のフィールドの関数もおすすめに入る。
- おすすめはシードの変更内容ではなく本体の名前の重なりで決めるため、変更が要る関数を落とすことも、要らない関数を含むこともある
  （frr の例では共有した名前〔BFD の登録〕は PR の変更内容と別の処理だった。確かめたのは1例）。字句で取り出す `rule` では、ローカル変数の検出の誤りで
  名前の重なりが変わりうる。
- 完了した調査を `extend` で延ばすと出力が延ばす前のまま残る（共通プロシージャの既知の制約）ため、`callslot` を深く調べる場合は
  `callslot` のシードで別の名前の調査を作るよう案内する。
- 所要時間: Step A-Seed の手順1 ごとに母体を1回走査する（frr 1,411 ファイルで `rule` 約3.9秒・`slice` 約4.3秒）。採用したシード・設定・
  母体のファイルの指紋が同じ再実行は走査しない（frr で約0.3秒）。
