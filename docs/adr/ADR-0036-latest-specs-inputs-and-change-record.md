# ADR-0036: 工程11 の入力をスクリプトの一覧で決め、モジュールの同一性を `module-dir` で決め、latest-specs の変更を基準との比較で記録する理由

Status: Accepted
Date: 2026-11-08

前提: [ADR-0013](ADR-0013-close-promote-script.md)・[ADR-0034](ADR-0034-ai-index-docs-index.md)・[ADR-0035](ADR-0035-lessons-backlog-ids-and-indexes.md)。
経緯: PLAN-20261108-latest-specs-contracts（約束の監査 [docs/xddp-contract-audit-2026-11.md](../xddp-contract-audit-2026-11.md) の P4）。

## Context

約束の監査は、仕様・用語・カタログの約束（A4）に食い違いを挙げた。もとは次の6つにまとまる。

- **工程11 が工程4a のモジュール資料の置き場所を知らない。** 工程4a は統合パス（`SPO-{CR}.md` の `## 2.A.` …）・分割パス
  （`modules/{名前}-spo.md`）・索引（`modules/{名前}/*-spo.md`）に資料を書くのに、工程11 の SKILL・mod-agent は `modules/` のディレクトリだけを
  資料とみなし、precheck は別の名前で資料を引いていた。モジュール仕様がほぼ作られず、既存のモジュールが毎回廃止候補になった。
  モジュールの名前と latest-specs のディレクトリ名の対応も、工程5・6・survey・工程11 で決め方が違った。
- **材料の節の名前が書く側と違う**（`クラス図` と `データ型関連図` 等）。書く側のいない材料（data-model の `source` 注記・deployment の節）もあった。
- **latest-specs の変更を LLM が一覧に書き、close がその一覧で `{DOCS}` から書き戻す。** GATE で削除した仕様・一覧に無い人の編集・
  分割実行の前の回の更新が、close の C0-3 で `{DOCS}` の版に戻った。中止した CR の latest-specs は後の CR の close で昇格した。
- **survey (c) が承認の前に latest-specs へ書き**、衝突を latest-specs だけで判定していた。
- **工程11 の廃止候補が、今の CR が調べていないモジュール・ユースケースを毎回含んでいた。**
- 記述が実物と違う箇所が多数あった。

## Decision

1. **工程11 の入力は、スクリプトの1つの一覧（`spec_version_delta.py sources`）で決める。** 工程4a の配置の読み方は、書く側の
   `specout_bfs.module_docs` に置く（`assemble-spo` と同じ関数を使う）。統合パス・索引のモジュールは、分割パスと同じ形の資料
   （`MODULE_TEMPLATE` の §2〜§4）に直して `{CR_PATH}/04_specout/{repo}/work/spec-sources/` に書く。工程11 の LLM・precheck・レビューは、
   どの配置でも同じ形の資料を1つ読む。一覧は、latest-specs のディレクトリ名・シーケンス図のファイル名・SPO の無い CHD の変更・廃止候補・
   衝突も返す。工程5・6・`/xddp-review … spec` も同じ一覧を使う。uc-agent の `related-modules` は一覧のディレクトリ名を書く。
   - 統合パスから分割パスへ移すときに深い見出しが元の深さのまま残っていたので、書く側（`_section_to_module_doc`）で同じ段数だけ上げる。
     読む側で深さを読み替えるより、書く側で正しい形に書くほうが、分割パスの資料と同じ規則で読める。
   - `sources` は Step OV ではなく Step 0 で実行する（Step UC の uc-agent も一覧を使うため）。
2. **モジュールの同一性は、モジュールの範囲（spec.md のフロントマター `module-dir`。`REPO_PATH` 相対）で決める。** 1ファイルのモジュールは
   そのファイルのパス、リポジトリ直下のファイルのモジュールは `.`、範囲が決まらなければ空。`docs_layout.resolve_spec_dir` は、
   latest-specs、`{DOCS}` の順に同じ `module-dir` の既存のディレクトリを探し、あればその名前を使う。名前の決め方が違っても
   （CR は台帳の名前、survey は引数）、同じ範囲なら同じ仕様に書く。survey は promote の経路で Step 2 を飛ばすので、`module-dir` の
   出どころを SURVEY 成果物の「ディレクトリ」欄にし、どちらの経路でも同じ値を読む。
3. **共有の値は `docs_layout.py` に1つ定義する**（ディレクトリ名の規則・`module-dir` のキー・シーケンス図のファイル名・工程11 の2つの節の
   見出しと読み書き・進行中の CR の判定）。SPO の節の名前はテンプレートが正で、スクリプトの定数をテストでテンプレートと突き合わせる
   （テンプレートは LLM が読むので Python の定数にできない）。
4. **latest-specs の変更は、工程11 の最初の実行の時点の状態（基準）と比べて `spec_changes.py record` が記録する。** 基準は
   `{CR_PATH}/.latest-specs-baseline.json`（相対パスと SHA-256）。progress.md の「## 工程11 更新仕様書ファイル一覧」「## 工程11 削除した
   仕様書ファイル一覧」は `record` だけが作り直す。基準と比べれば、誰が何をしたか（GATE の削除・人の編集・分割実行の前の回の更新）に
   関係なく変更が分かる。
   - `seed`: 工程11 の前に、`{DOCS}` にだけある既存の仕様を latest-specs へ写す（基準にあって今は無いもの〔今の CR の削除〕・進行中の他の CR の
     削除一覧にあるものは写さない）。latest-specs に無いだけで既存の仕様を新規に作り直し、版・変更履歴を失うのを防ぐ。
   - close の C0-3 は `promote.py sync-baseline` にした。更新一覧・削除一覧にあるものを書き戻さない。C0-4 は LLM の手順なので、
     読み方を1つにするためにスクリプトの JSON の一覧を使う。C2 の削除候補には、削除一覧のうち `{DOCS}` に写しのあるものを
     ファイル単位で足す（ディレクトリごと消えたものはまとめる）。
5. **同じ作業場所の他の CR の変更が基準との比較に混ざることを、close では許容する**（人の判断）。工程11 は CR ごとに逐次実行する前提で、
   混ざっても書き戻さない向きの誤りであり、削除は人が Step D で確かめる。
6. **abort の後片付け（`spec_changes.py revert`）は、安全な向きのものだけを戻す。** 基準は SHA-256 しか持たないので、基準の時点の内容には
   戻せない。変更・削除したファイルは、基準の SHA-256 が `{DOCS}` の写しと一致するとき（基準の時点で他の CR の未昇格の変更が入っていなかった）
   だけ `{DOCS}` から戻し、変更したファイルはさらに `last-updated-cr` が今の CR のときだけ戻す。足したファイルは `last-updated-cr` が今の CR の
   ときだけ消す。それ以外は戻さずに人に示す。abort は取り消せない操作で、元に戻すのは消す向きの操作なので、5. の許容の論拠は当てはまらない。
7. **廃止候補は、母体から消えたモジュール（`module-dir` が母体に無い、またはその下に工程4a と同じ規則の対象のファイルが無い）と、
   今の CR が取り下げ・廃止を示したユースケースに絞る**（人の判断）。今の CR が調べていないことを理由に候補にしない。確かめるのは
   スクリプトによるディレクトリ・ファイルの有無だけで、LLM がソースを読む母体調査はしない。CR の外でコードが消えたモジュールも候補にする
   （範囲を今の CR のモジュールに限ると、棚卸しの CR まで残るため）。進行中の他の CR が最後に更新したものは除く。`source: survey` の仕様を
   除外する規則はやめる（候補にする理由が「母体から消えた」という事実になったため）。GATE で「保持」を選んだときの `status:` の付記もやめる
   （読む側がいない）。
8. **survey (c) は作業場所（`{XDDP_DIR}/survey/{repo}/specs-work/latest-specs/{repo}/`）で生成・レビューし、承認の後にだけ latest-specs と
   `{DOCS}` に書く。** パスに `latest-specs` の区切りを含めるのは、`artifact_lint.py` の必須キーの判定を、コードを変えずにそのまま効かせるため。
   作業場所は毎回写し直し、最後に消す。衝突は写し先の `{DOCS}` でも見る。
9. **deployment.md は工程11 が作らない**（人の判断）。SPO に材料の節が無く、材料（構成ファイル等）は今の工程4a の範囲に合わない。人が書いた
   ものは保持し、昇格する。

## 却下した案

- mod-agent に統合パスの読み方を教える（LLM が2つの形を読み分け、precheck にも別の読み方が要る）。
- 工程11 が SPO §8 の表からモジュールを取る（表のセルの書式を読み直すことになる。台帳と配置から直接取るほうが書く側と同じ定義を使える）。
- ディレクトリ名をモジュール名だけで決める（CR と survey で名前の決め方が違うので、同じコードの仕様が二重にできうる）。
- 工程11 の LLM に「一覧を累積する」「削除も書く」と指示を足す（書き漏らしを検出できない）。
- C2 を一覧のファイルだけ写す形にする（一覧に無い人の編集が昇格しない）。
- 基準として latest-specs の丸ごとの写しを CR に置く（量が大きく、レビューブリーフに混ざる。元に戻す内容は `{DOCS}` にある）。
- `_module_dir_for_file` を最長一致に直して catalog の照合に使う（他の呼び出し元の結果も変わる。catalog の照合だけ別の関数にする）。
- survey (c) で latest-specs に書いてから、却下されたら消す（消す手順を漏らすと残り、上書きした後は戻せない）。
- モジュールの廃止候補に「CHD の変更対象ファイル一覧で全ファイルが削除」を使う（CHD の表は変えたファイルしか持たず母集合にならない）。
- abort で `{DOCS}` に写しのあるファイルをすべて戻し、無いファイルをすべて消す（他の CR の未昇格の変更・追加を消しうる）。
- survey の作業場所を `latest-specs` を含まないパスにし、lint のパスの解釈を直す（lint に survey の知識が入り、解釈が2通りになる）。
- 中間ファイルを `{CR_PATH}/pending-items/` に置く（中間ファイルの置き場所の規則から外れ、レビューブリーフに混ざる）。
- SPO サマリーに「ハードウェア構成・デプロイ構成」の節を足す（人の判断で採らない）。

## Consequences

- 工程4a の配置が変わっても、`module_docs` と `sources` のテスト（`assemble-spo` が書いた資料をそのまま通す）で読む側の追従が守られる。
- シーケンス図のファイル名は NFC に正規化して比べる（macOS のファイル名は NFD で返りうる）。見出しが記号だけで名前が空になるときの
  `seq-{順番}` は、見出しを並べ替えると名前が変わる限界がある（偽の廃止候補が出うる）。
- 母体にディレクトリ・ファイルを残したまま機能をやめたモジュールは、廃止候補に出ない（サイレント廃止リスク。棚卸しの CR で扱う）。
- 旧い形の CR・仕様（`module-dir` の無い仕様・基準の無い CR）を見分ける処理は持たない（後方互換性ポリシー）。`module-dir` が空・無い仕様は、
  名前の規則で引き当て、廃止候補にしない。
