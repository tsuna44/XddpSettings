## Context

工程4a（specout）の波紋調査（Discovery BFS）は、`specout_bfs.py` の検索と、LLM による hit 行の分類
（`xddp-specout-classifier-agent`。ADR-0010）を組み合わせていた。調査記録で次のことが分かった。

- **LLM 分類の中身はほぼ機械的だった。** u1-eval の過去3 CR・179行のうち176行で、「コメント・文字列中の偽陽性」と
  「ヒット行を含む関数を次の波のシンボルにする」という決定的な規則と、次の波に渡すシンボルが一致した。不一致3行のうち
  1行は LLM の誤り、2行（`goto` のラベル名・プロトタイプ宣言の引数名）は規則を足せば決定的に扱える（調査記録 §2.1）。
- **遅さの主因は1波あたりの固定費だった。** `metrics.jsonl` の `classify_wall_ms` はヒット数によらず1波あたり約1分
  （redis: 2ヒットで87.7秒・3ヒットで62.6秒、frr: 23〜31ヒットで57〜59秒）で、行数よりもサブエージェントの起動そのものの
  コストが大きかった（調査記録 §2.2）。
- **試作の評価。** tree-sitter による関数内の静的スライス（影響が関数の外へ出る経路＝出口の判定）に、グローバル変数の
  読み手を追う「完全スライス」と、シード関数が書きうる副作用をすべて変化とみなす「computed」を組み合わせ、u1-eval
  （frr・redis と修正 PR の正解データ）で機能（モジュール）単位に評価した。4シナリオ中3つで第1波まで（2波）で正解
  モジュールが出そろった（今の BFS 相当の baseline では第2〜4波、または出そろわなかった）。検索を識別子の索引に置き換え、
  1波内に予算を設けることで、5波でも7〜80秒で終わった。解析が例外で失敗したヒットは0件だった（調査記録 §6・§10）。
- **波紋調査の目的は影響する機能の特定であり、調べきる必要はない**（調査記録 §7.1）。評価の物差しはファイル単位の
  再現率ではなく、「浅い波のうちに影響する機能が出そろうか」とする。

これを受けたユーザー判断（プラン §1.2 の D1〜D15。D13・D14 は関連プラン）に基づいてプランを作成・承認し、実装した。
本 ADR はその設計判断を記録する。

## Decision

波ループの hit 行の判定を、次のように振り分ける（D11）。

```
search（識別子索引で検索 → dedup・保守的フィルタ → 1波の予算・LLM 分類の上限）
  ├─ 言語表にある拡張子（C / C++ / Python）のヒット → specout_slice.py classify（LLM を使わない）
  │     slice: tree-sitter あり。完全スライス・computed
  │     rule : tree-sitter なし。コメント・文字列等の偽陽性と、ヒット行を含む関数
  └─ それ以外の言語のヒット                         → xddp-specout-classifier-agent（LLM 分類。1波の上限つき）
→ merge_classification.py → commit-wave（bfs-state.json・discovery-log の単一書き手）
```

個々の判断と理由は次のとおり。

### 1. LLM 分類を静的スライス・規則判定に置き換え、LLM は関数の範囲を決定的に取れない言語だけに使う（D2・D11）

- 調査記録 §2.1 の一致率から、LLM 分類が実際に行っていた判定は規則で再現できる。規則判定（`rule`）は、コメント・文字列の
  中のヒットを偽陽性とし、それ以外はヒット行を含む関数を次の波で追う（今の LLM 分類の大半の振る舞いと同じ）。§2.1 の
  不一致2行（ラベル名・プロトタイプ宣言の引数名）も偽陽性として扱う。標準ライブラリだけで動く。
- 調査記録 §2.2 から、LLM 呼び出しの量を減らすより、波のループから外す方が効く。決定的に判定できる言語のヒットでは
  classifier を起動しない（C / C++ / Python だけのリポジトリでは classifier は起動しない）。
- 完全スライス・computed（`slice`）を採用したのは、今の BFS がたどらないグローバル変数経由の影響（シードが書くグローバルの
  読み手）を追え、試作の評価で浅い波のうちに正解モジュールが出そろったため（調査記録 §6.2・§10.2）。
- 規則判定は言語表（拡張子 → コメント・文字列の書式、関数の範囲の取り方）で動く。言語表に無い拡張子（関数の範囲を決定的に
  取れない言語）のヒットだけが LLM 分類に回る。言語の追加は表の行とテストの追加で行う（別プラン）。
- LLM 分類に回るヒットには1波あたりの上限（`SPECOUT_LLM_HIT_BUDGET`）を設け、超えた分は打ち切り記録（`llm-budget`）に残す
  （無音の縮退はしない）。既定 `160` は暫定値で、今の `SPECOUT_CLASSIFY_CHUNK_SIZE` 40 × `SPECOUT_CLASSIFY_PARALLEL` 4 ＝
  1バッチ分（1波の LLM 分類が約1バッチで終わる量）とした。
- **次の波のシンボル名は、修飾を外した識別子にする。** C++ の `ns::Class::method` は `method`、`f<T>` は `f`、コンストラクタは
  クラス名、Python は `def` の名前、lambda は名前を持つ最も内側の外側の関数。次の波は識別子で検索するため、修飾名では索引で
  引けず、grep でも呼び出し箇所（`obj.method()`・`method()`）に一致しない。デストラクタ・演算子オーバーロードは呼び出し箇所に
  名前が現れないため伝播させず、「## grep未対応パターン（手動確認必要）」に記録する。

### 2. tree-sitter を外部依存として許容し、無い環境では規則判定で動かす。波数・予算は変えない（D6・D12）

- 決定的処理スクリプトは標準ライブラリのみ（Excel 変換の `openpyxl` を除く）という方針に反するが（調査記録 §8 課題7）、
  関数内のデータ依存・制御依存と出口を判定するには構文解析が要り、C / C++ / Python を同じ方法で解析できる tree-sitter
  （pip で入れる）を許容した。版は `scripts/requirements-slice.txt` で固定する（`tree-sitter==0.26.0`・
  `tree-sitter-c==0.24.2`・`tree-sitter-cpp==0.23.4`・`tree-sitter-python==0.25.0`）。tree-sitter を入れた Python は
  `SPECOUT_SLICE_PYTHON_BIN` で指定できる（`MD2EXCEL_PYTHON_BIN` と同じ扱い）。
- tree-sitter の import は構文解析を行う関数の中まで遅延させる。`--help`・`probe`・`rule` は tree-sitter が無くても動き、
  `make test` の既定環境（標準ライブラリのみ）ではスライス判定のテストだけがスキップされる。
- tree-sitter が無い環境（`SPECOUT_SLICE: auto` で import できない場合）と `SPECOUT_SLICE: off` では `rule` で判定する。
  前者は discovery-log の「## 探索設定」に警告を残す。LLM 分類には戻さない。
- **波数上限とヒット予算は、tree-sitter の有無によらず同じ値にする。** `rule` でも LLM は関わらないため、1波の処理量の
  上限を変える理由が無い。
- **判定エンジンは CR（repo の状態ファイル）ごとに固定する。** `init` が判定エンジン・影響なしとみなす呼び出し
  （`SPECOUT_SLICE_IGNORE_CALLS`）・`.h` の扱い・予算を state に保存し、再開を含むその CR の判定の単一情報源にする。
  state が `slice` なのに tree-sitter を import できないとき、`specout_slice.py` は終了コード 5 で止まり、`rule` に
  黙って切り替えない。同じ CR の中で判定の条件が黙って変わり、波ごとに追い方の違う結果が混ざるのを防ぐため。
  `import`（人可読ビューからの手動復旧）も、判定の条件を決めるキー（波数上限・起点・予算・判定エンジンの設定）を復元する。
- **例外として、人が選んだときだけ `rule` に切り替えて続けられる（`switch-engine`）。** 別のマシン・別の人による引き継ぎや、
  仮想環境・`SPECOUT_SLICE_PYTHON_BIN` の変更で、探索の途中から tree-sitter を使えなくなった場合に、探索済みの波を捨てずに
  続けるため。規則判定は今の LLM 分類と同じ振る舞いで、切り替えた後の波の追い方が粗くなるだけで誤りにはならない。
  SKILL は状態を書き換える直前（Step A の入口と Step A-cross-propagate の投入の直前）に照合し、3つの選択肢（tree-sitter を
  使える Python を指定して再実行する／規則判定に切り替えて続ける／状態ファイルを退避し規則判定で最初から探索する）を示す。
  切り替えは discovery-log と Step E の報告で人に分かるようにする。`rule` から `slice` への切り替えは行わない（state が
  `rule` なら、tree-sitter のある環境でも `rule` のまま続ける）。
- `slice` の解析が例外で失敗したヒットは `rule` で代わりに判定し、`note` に `slice-error {例外名}; rule` を残す
  （実装時に決定。ヒットを取りこぼさないため）。

### 3. 波数上限で一時停止せず自動完了し、上限は探索の起点の波から数える（D1・D3・D5・D8）

- 波数上限（`SPECOUT_MAX_WAVE_DEPTH`）を「探索の起点の波から調べる波の数」とし、既定を `10` から `6`（第0〜5波）にした
  （試作の `range(max_waves)` と同じ数え方）。ケースごとに人が設定で変える。調査記録 §9.2 の決定（3波）は、プランの D3 で
  6波に改めた。
- 上限に達したら一時停止（`paused-at-limit`・継続パス A/B/C）せず、残りの frontier を打ち切り記録（`wave-limit`）に残して
  `complete` にする。目的は影響する機能の特定であり（D1）、人は結果を見て、必要なら上限を上げて再実行する。再実行すると
  `extend` が打ち切ったエントリを優先度を変えずに frontier へ戻し、続きから探索する。一時停止の状態値は、`set-state` でも
  作れないよう `specout_bfs.py` からすべて削除した。
- state に探索の起点の波（`wave_origin`）を持ち、人がシンボルを加えたとき（`re-discover`・`merge-frontier --reset-wave-origin`）は
  経路によらず起点を置き直す。起点を持たないと、上限で完了した repo に `--re-discover`（Step A-cross-propagate を含む）で
  加えたシンボルが、1件も検索されずに打ち切られるため。起点を置き直すと frontier に残る伝播由来のシンボルの残りの波数も
  延びるが（frontier はシンボルごとの起点を持たない）、1波の予算で抑えられる。
- 予算と判定エンジンの設定は `init` の値で固定し、`extend` では変えない（再開した CR の中で判定の条件を変えないため）。
  変えて反映するには状態ファイルを退避・削除して最初から探索する。上限を下げた場合も state の値で続ける（調べ終えた波を
  取り消さないため）。

### 4. 1波のヒット予算は検索の後の件数で判定し、打ち切ったものを記録する（D4・D8・D12）

- 1波で処理するヒットの予算（`SPECOUT_WAVE_HIT_BUDGET`。既定 10,000。`0` は無制限）は、その波の frontier をすべて検索し、
  dedup と保守的フィルタを適用した後の件数で判定する。検索の前に件数を数える方式では、コマンドの生ヒットの一部だけを外す
  ことになり、件数一致検証の照合式（ADR-0009）が崩れる。検索の後なら、どのバックエンドでも同じ方法で数えられ、`index` の
  検索は辞書の参照なので検索を省く利点も小さい。
- 予算を超えたら、関数シンボル → 値シンボル（グローバル・`root.field`）の順、各群の中ではヒットの少ない順に、累計が予算に
  収まるエントリを採る。試作で「ヒットの少ない順」だけにしたところ、グローバルの読み手が予算を先に使い、正解に関わる関数
  `alsoPropagate`（23ヒット）があふれたため、関数シンボルを優先する2段にした（調査記録 §10.1）。関数か値かは state の
  `symbol_kinds`（スライス判定・規則判定の結果から `commit-wave` が決める）で判定するため、要約を作らない `rule` でも
  同じ順序が働く。
- 打ち切ったエントリは discovery-log の「## 打ち切り記録」（波・理由・シンボル・ヒット数）に残す。表は state の
  `truncated` から毎回作り直す（state が単一情報源）。理由のコードは `hit-budget` / `llm-budget` / `wave-limit` /
  `backend-unsupported`。
- 予算で除いた行は「## フィルタ除外一覧」に1行ずつは書かない（予算を超える量のヒットで discovery-log が膨らむため）。
  件数一致検証では「フィルタ除外」列に含め、照合式（生 = 記録 + dedup + フィルタ除外 + noise-collapse）と列の構成は変えない。
- 予算で打ち切ったエントリは検索済みで visited に入り、後の波で frontier に戻らない。人は打ち切り記録のシンボルを
  `/xddp-04-specout {CR} --re-discover {シンボル}` で追う（一般的な名前だが重要な関数、例えば redis の `call` が打ち切られうる。
  調査記録 §10.2）。
- 人が入れたシードが予算で丸ごと打ち切られた場合は、「## 予算で打ち切った投入シンボル（Wave N）」・波ループの提示・Step E で
  知らせ、シード確認の候補表（`seed-preview`）でも `予算超過` を警告する。CR の変更対象そのものが一度も追われないまま進む
  ことを人に知らせるため。
- 前倒し縮退と高ノイズによる波及停止（ADR-0009）は、LLM 分類に回るヒットだけに適用する。スライス判定・規則判定のヒットでは
  予算が代わりを担う。

### 5. discovery-log の種別・派生元・判定の値を英語のコードにし、説明を凡例にまとめる（D15）

- ヒット表の「伝播種別」（`false-positive`・`propagation-direct`・`slice(escape=return,global)`・`slice(file-scope=macro-def)`・
  `slice(none=…)`・`rule(enclosing)`・`rule(none=…)` 等）、「派生元」（`seed(X)`・`seed-global(X)`・行ID・`unknown-origin`）、
  実行コマンド一覧の「種別」（`HIGH-compound`・`MEDIUM`）、件数一致検証の判定（`✅ excluded(…)`・`⚠️ mismatch(…)`・
  `➖ discarded(case-a)`）、同名 MEDIUM 重複ログの「ケース」「処置」、打ち切り記録の「理由」を英語のコードにした。
  日本語の説明は、discovery-log 冒頭の「## 凡例」1か所にまとめる。
- これらの値は人が読むだけでなく、スクリプトが読み取る（`funcmap-counts` の派生元、`specout_verify_counts.py` の判定・処置、
  関連プランの打ち切り記録の読み取り）。値の定数と判定の文字列の書式関数は `specout_log_values.py` に置き、書き手
  （`specout_bfs.py`）と独立の検証（`specout_verify_counts.py`）が同じ文字列を使う。共有するのは表示の文字列だけで、件数の
  照合は今どおり各スクリプトが別々に行う（書き出されたログのテキストを独立に読み直して照合する性質は保つ）。
- 凡例には「MEDIUM」の語を書かない（実装時に決定。`xddp_review_brief.py` が MEDIUM を含む行を確信度マーカーとして数えるため）。
- 表の列の構成は変えない。波紋グラフのプラン（PLAN-20260829-specout-ripple-trace-graph）と、`funcmap-counts`・
  `extract-review-scope`・`specout_verify_counts.py` が行データを読むため。

### 6. 安全側でない仮定を置き、取りこぼしを許容する

スライス判定は次の仮定を置く（調査記録 §4・§8 課題3〜5）。いずれも影響の見落とし、または探索の偏りを生みうる。

| 仮定 | 起こりうること | 補う手段 |
|---|---|---|
| リポジトリに定義の無い関数（外部関数）は、アドレス渡し以外では引数を書き換えない | 外部関数を経由する副作用を見落とす | — |
| 呼び出し先の副作用の要約は深さ3まで再帰的に求める | 深い呼び出しの連鎖の副作用を見落とす | — |
| 関数ポインタ・コールバック経由の呼び出しは追わない | 間接的な呼び出し先を見落とす | 関数ポインタ経由の呼び出し（引数・ローカル変数・グローバル変数・定義の無い構造体フィールド経由）を「## grep未対応パターン（手動確認必要）」に `function-pointer-call` として記録する（試作には無く、実装時に追加） |
| プリプロセッサを通さない（マクロを展開しない） | マクロで構文解析が崩れた箇所を判定できない | 構文を作るループマクロを解析の前に書き換える（frr の構文エラー行は 32.8% → 2.7%。調査記録 §8 課題3）。崩れた箇所は `error_units` として要約の対象外とし、宣言の無いグローバルは誤解析とみなして unknown にする |
| 次の波のシンボル名から修飾を外す（判断1） | C++ / Python で、同名の別関数のヒットが増える | 次の波の判定（偽陽性）と1波の予算で抑える |

**許容の根拠:**

- 波紋調査の目的は影響する機能の特定であり、調べきる必要はない（D1・調査記録 §7.1）。これらの仮定を置いた試作で、
  4シナリオ中3つで第1波まで（2波）で正解モジュールが出そろった（調査記録 §10.2）。
- 静的に追えない参照が残ることは、どのバックエンドでも同じであり（ADR-0008 の不変条件）、「## grep未対応パターン」の
  人手確認の記録で補うという今の仕組みに乗せた。
- 逆向きのリスク（ログ出力・メモリ確保・参照カウント等の共通基盤であらゆる関数がつながり、探索が広がる）は、
  `SPECOUT_SLICE_IGNORE_CALLS`（影響なしとみなす呼び出しの正規表現。プロジェクト固有）と1波の予算で抑える。

### 7. 要約の拡大による関数シンボルの再訪と、dedup の鍵への要約の正規形の追加

- 試作 `bfs_sim.py` は、次の波の関数シンボルが visited 済みでも、要約が広がった（`returns` / `side` が新たに真になる、
  `out` が増える）場合は frontier に戻し、その呼び出し元を判定し直す。本番も同じ規則を採用した。合格条件を「試作の評価と
  同等の結果」としたため（プラン §5）。
- 再訪の検索で呼び出し元の行が dedup で除かれないよう、関数シンボルの HIGH 検索の dedup の鍵（`_loc_key`）のスコープ種別を
  `HIGH#{要約の正規形}`（`returns`・`side`・ソートした `out` をつないだ文字列）にした。要約が広がれば鍵が変わって判定し直され、
  変わらなければ今の dedup の効果は保たれる。要約の無いシンボル（値シンボル・`rule`・LLM 分類）の鍵は変えない。
- 分類済みロケーションには、検索した時点の鍵（`search` が各ヒットに持たせる `loc_scope_class`）を登録する。要約が広がった波と、
  その関数の呼び出し元を検索した波が同じ場合に、マージ後の要約で鍵を作り直して登録すると、次の波の再訪で呼び出し元の行が
  すべて dedup で除かれて空振りするため。
- 終わることの根拠: 要約の各項目は真偽値か有限集合（引数の位置・クロージャ変数名）で、マージは和集合なので単調に広がり、
  1つの関数が再訪される回数には上限がある。さらに波数上限と1波の予算で抑えられる。
- 再訪は `slice` だけで起きる（`rule` と LLM 分類は要約を返さない。試作の baseline と同じ）。件数一致検証は変えない
  （再訪の検索のヒットも、記録・dedup・フィルタ・予算のいずれかに数える）。

### 8. 関数の外のヒットの値を伝播させる（`slice`）

`slice` は、関数の外のヒット（`file-scope`）のうち、マクロ定義の本体（→ マクロ名）、グローバル変数の初期化子（→ 宣言した
変数名）、Python のモジュール本体・クラス本体での代入（→ 代入先の名前）を次の波で追う。マクロでラップしたインタフェース（C）と、
モジュール変数・クラス属性への代入（Python）は、関数の外を経由して影響が広がる典型的な経路であり、試作の評価（合格条件の比較
対象）もこれを追っているため。宣言だけ・マクロ名そのもののヒットと関数の定義そのもの（`self-def`）は伝播させない。
`rule` と今の LLM 分類はこれらを追わない（試作の baseline と同じ）。

**Python の別名 import の取りこぼしの修正（実装時に決定）:** 試作は `from m import f as g` を `g` の束縛として扱わず、`f` の
検索は import 行にしかヒットしないため、伝播がそこで止まっていた（試作から引き継いだ偽陰性）。本番の `slice` では、関数の中の
別名は影響を受けたローカル変数とし（以降の使用を追う）、モジュール本体・クラス本体の別名は `module/class-assign` と同じく
別名を値として次の波で追う。

### 9. シードの要約を、人がシードを入れるすべての経路で取り込む

computed は、シード関数の要約と、シードが書くグローバルの読み手を最初の波から追うことを前提にする。シードを入れる処理
（`init`・`merge-frontier --reset-wave-origin`・`re-discover`）は、`slice` の state ならそのシンボルを `seed_summary_pending` に
加え、`search` は印が残っていれば検索せずに終了コード 6 で止まる。SKILL はこれを受けて `seed-summary` を実行し、
`merge-frontier --summaries-file` で取り込んでから `search` をやり直す（関数定義の無いシンボルも印は外れる）。
経路ごとに SKILL が呼び分ける方式にすると、取り込みの途中で止まって再実行した場合などに取り込みが黙って抜けうるため、
`search` の入口で検査する方式にした。対象を印の付いたシードに絞るのは、frontier 全体に呼ぶと、伝播で得た関数シンボルの要約を
computed の要約で上書きしてしまうため。シードのグローバルは、シードの診断（未ヒット・ヒット過多の投入シンボル、
`funcmap-counts`）に混ぜない（スライス判定が導いた値が混ざると誤った警告になるため）。

### 10. 計測値 `classify_wall_ms` の意味の変化と `slice_classify_ms`

- `classify_wall_ms`（`search` から `commit-wave` までの壁時計）の意味は、「スライス判定・規則判定と LLM 分類の合計」に変わる。
  過去の `metrics.jsonl`（調査記録 §2.2 の 57〜88秒）と、そのまま比べてはならない。
- `slice_classify_ms`（スライス用チャンクの classification ファイル `wave-{N}-chunk-S-class.json` の `elapsed_ms`。関数定義の
  索引の作成を含む）を加えた。LLM 分類の所要時間を見る場合（調査記録 §2.2 との比較・`SPECOUT_LLM_HIT_BUDGET` の見直し）は、
  `llm_hits` > 0 の波について `classify_wall_ms - slice_classify_ms` を使う。波ループではスライス判定・規則判定が LLM 分類より
  先に順に実行されるため。
- per-wave metrics には、ほかに `index_build_ms`・`hit_budget_removed`・`llm_budget_removed`・`slice_hits`・`rule_hits`・
  `llm_hits`・`revisit_count` を加えた。

### 11. C / C++ / Python で LLM 分類をやめることで失われる意味判定と、許容の根拠

| 失われる判定 | 変更後 | 許容の根拠 |
|---|---|---|
| `out-of-scope-discard`（`scope_summary` によるスコープ外の除外。ADR-0012） | スコープ外のヒットも伝播する | 探索の広がりは1波の予算と波数上限で抑え、打ち切り記録で人に見せる。LLM 分類に回る言語では今どおり使う |
| `propagation-argument`（呼ばれる側の引数を MEDIUM で追う） | `slice` は呼び出し先の要約（computed）で近似する。`rule` は追わない | `rule` は含む関数の呼び出し元だけを追い、今の LLM 分類の大半の振る舞いと同じ（調査記録 §2.1） |
| `propagation-return` と `is_external_api` を起点とするケースA（MEDIUM → HIGH 昇格） | MEDIUM が出ないため、ケースA は起きない | スライス判定・規則判定は最初から HIGH（全域）で追う |

いずれも探索が狭くなる方向ではなく、広がる（または最初から全域で追う）方向の変化であり、目的（影響する機能の特定）を
損なわない。広がりのコストは予算と波数上限で上限を持たせ、打ち切りは記録に残る。

### 12. 識別子索引バックエンド（`index`）を既定にする

- `SPECOUT_BACKEND: auto` の解決先を `index` にした。試作のプロファイルで、1波の約97%（497秒中483秒）が `git grep` の待ち時間
  だったため（調査記録 §10.1）。`index` は起動時にリポジトリ全体の識別子と `root.field`（`root.field` / `root->field`）の
  転置インデックスを作り、各波は辞書を引く。作成は試作で frr（約96万行）1.8秒・redis 0.5秒。`search` は波ごとに別プロセスで
  起動するため、索引は毎回作り直してキャッシュしない（キャッシュにはコード変更の検出による無効化が要る）。
- 索引で引けるのは識別子と `root.field` だけで、それ以外の形のシンボル（`Foo::bar`・`$var`・ファイルパス等）は `index` の中で
  rg（無ければ grep）に委譲し、今と同じ `_word_boundary` のパターンで検索する。既定の経路で「無音 0 ヒット」を再発させないため。
  `root.field` を扱えるのは `index` だけで、`grep` / `rg` を明示した場合は検索せず打ち切り記録（`backend-unsupported`）に残す。
  `grep` / `rg` を明示すれば従来の挙動に戻せる。
- ファイルの列挙は、git 管理下のリポジトリでは `git ls-files -co --exclude-standard`（`.gitignore` を尊重する）、そうでなければ
  隠しディレクトリを除いた走査とし、NUL を含むファイル（バイナリ）は索引しない。識別子の境界は grep の `\b` と同じにする。
  この列挙関数（`list_repo_files`）は `specout_slice.py` の関数定義の索引も共有する（実装時に決定）。
- **帰属判定（`_matching_symbol`）の不具合の修正（実装時に決定）:** 両端が単語文字でないシンボル（`$var`・`Foo::bar`）の行が、
  候補の先頭のシンボルに誤って帰属していた。検索パターンは `_word_boundary` で境界を省いていたが、帰属判定は `\b…\b` のまま
  だったため。帰属判定の境界を検索パターンと同じに揃えた。あわせて、1コマンドの全行の帰属を識別子の集合との照合で求める
  ようにした（候補×行の正規表現照合では、u1-eval の redis で第2〜3波の `search` に39〜56秒かかっていた。修正後の
  1波あたりの `search` は0.6〜2.0秒で、ほぼすべてが索引の作成）。
- 付随して、`commit-wave` は「### 件数一致検証」の見出しの後に空行を書くようにした（実装時に決定）。`specout_verify_counts.py`
  が同じ節を書き直したときに見出しが重複せず、バイト単位で同じ出力になるようにするため。

### 13. スライス用チャンクと LLM 用チャンクに分ける

`search` は、言語表の拡張子のヒットをスライス用チャンク（`wave-{N}-hits-chunk-S.json`。ヒット0件でも常に1件書く）に、
残りを LLM 用チャンク（LLM に回るヒットが1件以上のときだけ書く）に入れる。ADR-0010 の「チャンクは必ず1件以上」の契約は、
スライス用＋LLM 用の全体で保つ。LLM に回るヒットが0件の波で空のチャンクを作らず classifier を起動しないためと、呼び出し側に
分岐を作らないため。`merge_classification.py` は `--hits-chunks` と `--chunks` を位置で対応させるので、SKILL と復旧手順が
両方の先頭にスライス用チャンクを置くことで、同スクリプトを変えずに済ませた。

### 14. 除外パターンの意味をバックエンドによらず統一する（D10）

`SPECOUT_EXCLUDE_PATTERNS` のパスで書いたエントリ（例 `lib/legacy/`）は、grep の `--exclude-dir`（名前だけで比べる）と
モジュール一括記録では無音で効かず、rg ではルートからのパスで効いていた。除外の判定を純関数 `_is_excluded` 1つにまとめ、
「`/` で終わり途中に `/` を含まない＝どの階層のその名前のディレクトリも除く」「途中に `/` を含む＝ルートからのパスで
ディレクトリ境界の前方一致」「`/` で終わらない＝ファイル名またはルートからのパスへの glob」の意味で、`index` の索引作成と
grep / rg の後段フィルタに使う。一致するファイルが0件のエントリは「## 探索設定」に警告する（書き間違いに気づけるように）。

### 15. CR の規模の判定（Step C5）にシードの直接参照ファイル数を使う

完全スライスでは確定ファイルが数百件になり、確定ファイルの合計は CR の規模を表さなくなる。工程4で決定的に数えられる値の
うち変更対象ファイル数に最も近い値として、シードが偽陽性・`out-of-scope-discard` 以外の判定でヒットしたファイルの数
（`seed_direct_files`。シードのグローバルは除く）を quick / full の推奨に使う。インタフェースを変える場合は呼び出し元も直す
ことになるため、シードの定義があるファイルだけでなく直接参照するファイルまで数える（上限寄りの値）。確定ファイルの合計は
参考値として併記する。

## Consequences

### u1-eval での確認（2026-10-04）

本番のスクリプトを、SKILL の波ループと同じ順（`search` → `seed-summary`〔終了コード 6 の経路〕→ `classify` →

### 影響

- C / C++ / Python のヒットでは classifier が起動しなくなり、1波ごとのサブエージェント起動の固定費が無くなる。代わりに
  スライス判定の時間（上記）がかかる。
- discovery-log の値が英語のコードになり、「## 凡例」「## 打ち切り記録」「## 探索の延長」「## 予算で打ち切った投入シンボル」
  「## 要約の拡大による再訪」が加わる。「## ⚠️ 探索上限到達」「## Frontier剪定ログ」と確定ファイルの MODULE-LEVEL は出なくなり、
  C / C++ / Python では MEDIUM・高ノイズ・同名 MEDIUM 重複ログもほぼ出なくなる。
- 完全スライスで確定ファイルが数百件になるため、今の document agent では読み切れないおそれがある。関連プラン（資料の確定と
  SPO レビュー）の実装完了後に、合わせて `setup.sh` でデプロイする。
- 後方互換性は保証しない。`paused-at-limit` で止まっている既存の CR と、日本語の値で書かれた既存の discovery-log は再実行を求める。
- 一時停止の経路が無くなり、`specout_bfs.py` の `prune` / `finish` / `record-module` と MODULE-LEVEL の扱いはスキルから
  呼ばれなくなる。撤去は別プランで行った（[PLAN-20261004-specout-module-level-cleanup](../../plans/PLAN-20261004-specout-module-level-cleanup.md)）。
- `SPECOUT_SLICE*`・`SPECOUT_WAVE_HIT_BUDGET`・`SPECOUT_LLM_HIT_BUDGET` の6キーを追加し、`SPECOUT_MAX_WAVE_DEPTH` の既定を `6` に、
  `SPECOUT_BACKEND: auto` の解決先を `index` に変えた。
