# ADR-0027: 回帰テストの範囲を、CHD で変更が確定した要素から決める理由

Status: Accepted（承認済み）
Date: 2026-10-18

- プラン: [plans/PLAN-20261013-regression-scope-from-chd.md](../../plans/PLAN-20261013-regression-scope-from-chd.md)
- レビュー: [plans/review/PLAN-20261013-regression-scope-from-chd-review.md](../../plans/review/PLAN-20261013-regression-scope-from-chd-review.md)
- 前提 ADR: [ADR-0021](ADR-0021-specout-symbol-identity.md)（同一性の印）・[ADR-0023](ADR-0023-specout-two-layer-output.md)（2層の出力。§5 の E12 を取り消す）・
  [ADR-0024](ADR-0024-specout-ripple-trace.md)（LLM に全量を渡さない）・[ADR-0025](ADR-0025-specout-ripple-runs.md)（調査の記録と採用）

## Context

ADR-0023 §5（E12）では、工程9 の回帰テストの範囲を SPO §5.2（資料のあるモジュールで波紋調査が届いた関数）で決めていた。
しかし、スペックアウトで調べた範囲は母体を理解するための範囲であり、波紋調査が届いた範囲も、設計が決まる前に CRS のシードから求めた影響の候補である。
どちらも、修正が確定した処理の影響範囲とは限らない。「資料があるか」で回帰テストの範囲が変わると、資料を足すと回帰テストが増え、資料の無い影響先は回帰テストから漏れる。

回帰テストが必要なのは、変更設計（工程6 の CHD）で修正が確定した要素と、その要素の影響を受ける既存の処理である。

## Decision

1. **起点は CHD §4（R1）。** §4 の表に「種別」（関数／データ構造／変数／定数／インタフェース）と「変更の内容」（追加／振る舞い／シグネチャ／削除）の列を足し、
   1行に1つの識別子にする。型のメンバーは言語によらず `{型名}::{名前}`、`.` はグローバル変数のフィールド（`root.field`）だけに使う。
   `chd_regression.py elements` が §4 を機械的に読み、書式の誤りは fail-loud にする。「追加」の要素は既存の参照元が無いので起点にしない。
2. **候補はスクリプトが出す（R2・R3）。** `specout_bfs.py regression-candidates` が、採用した波紋調査の discovery-log から要素ごとに下流を出す。
   下流は state の `symbol_origin_map` を反転してたどる（派生元の列は検索した波の確定時の値のままで、visited への再送や `seed-global` を表せない）。
   要素が検索シンボルとして現れない（含む関数としてだけ現れる・現れない）場合と、要素自身の検索が削られた（`truncated`・高ノイズ・noise-collapse）場合は、
   直接の参照元（1段）を要素の表記に応じたスコープ（`[CLASS:]`・`[FILE:]`・素の名前）で検索して補う。資料の有無に依らない。
3. **LLM には上限つきの要約だけ（R4）。** バッチごとに確認対象の候補を最大 30 行の要約にし、designer がそれを読んで、候補ごとに CHD §7 の確認種別「回帰」の行にするか、
   理由を付けて §7.1 に除外として残す。確認対象は、距離1の候補（同一性によらない）・直接検索の候補・距離2以上で同一性が `resolved` か `未判定`
   （経路のどこかで同一性を判定していない。規則判定・LLM 分類の行・`name-only` で始めた調査・ケースA の昇格）の候補。
   距離2以上の名前の一致だけの候補と上限を超えた候補は件数だけを要約に書き、全量は人向けの `regression-candidates.md` に書く。
   距離1を同一性によらず確認対象にするのは、直接検索の候補と同じ扱いにし、波紋調査でたどれた要素のほうが確認対象が少なくなる逆転を防ぐため。
4. **照合はスクリプト（R9）。** `chd_regression.py check` が、確認対象の候補がすべて §7 の回帰の行か §7.1 にあることを照合する。
   漏れがあれば designer を1回だけ再度呼ぶ。候補に無くなったキーは人に知らせる（消すかは人が決める）。
5. **回帰 TC は CHD §7 の回帰の行から作る（R5）。** test-writer は SPO §5.2 から回帰 TC を作らない。TSP §3.4 の「対応確認項目」で回帰の行と対応させ、TSP レビューはその対応で判定する。
   「未調査の回帰リスク」の記録はやめ、工程6 の要約の件数と §7.1 に移す。SPO §5.2 の作り方は変えない（母体の理解のための表。R7）。
6. **quick は距離1だけ（R6）。** マルチリポジトリでは、他の repo の要素も、この repo のクロスリポジトリ伝播の調査（`cross-{要素の repo}-*`）の行と一致すれば候補を出し、
   候補の repo のバッチファイルに書く（R8）。
7. **古くなった候補の検出（R10・R14・R15）。** `chd_regression.py record`／`status` が Step A3 の入力（§4 の要素・採用した調査の集合・discovery-log・波紋調査なしの印・設定）の指紋を比べる。
   指紋に母体のコードは入れない（回帰の範囲は変更前の既存の振る舞いが基準）。工程7 の後のやり直しでは前回の直接検索の候補を引き継ぐ（`--code-changed`）。
   工程6 の中では Step B・B2 の後に自動でやり直し、工程6 の後は `/xddp-06-design {CR} regression` でやり直せる。`/xddp-09-test` は工程9 を始める前に確かめる。
   §4 の書式の誤りでは工程6 を止めず、designer に1回直させ、直らなければその repo の Step A3 を飛ばして人に知らせる（古い要約は `invalidate` で消す）。
8. **工程7・8（R12）。** 回帰の行は「変えてはならない既存の振る舞い」であり、回帰の候補のコードを変える理由にならない。verifier は回帰の行を「CHD に無い変更で既存の振る舞いを変えていないか」で判定し、§7.1 は判定しない。

### 却下した案

- **CHD に §2.1（変更要素の一覧）を新設する。** 同じ識別子を §4 と2つの表で持つことになり、食い違いの元になる。§4 に列を足す。
- **designer が SPO §5 を読んで回帰の確認項目を決める（従来）。** 資料の有無で範囲が変わり、設計で確定した要素と結び付かない。
- **full で距離の上限を設けない。** 下流は深いほど名前の一致だけの到達が増える。距離では切らず、確認対象の行数の上限（30 行／バッチ）と同一性で絞り、残りは件数と全量で人に示す。

## Consequences

- 回帰テストの範囲が資料の有無に依らなくなる。資料の無いモジュールでも変更シンボルから届く処理は候補になり、資料があっても届かない処理は回帰の対象にならない。
- 工程6 のトークンが増える（確認対象のあるバッチごとに designer を1回。照合の漏れ・§4 の書式の誤りで1回ずつ追加）。quick でも Step A3 を行う（距離1だけ）。
- 名前の一致だけの候補が確認対象に入り、上限に達しやすくなる。上限を超えた件数は人に知らせ、全量は `regression-candidates.md` にある。
- 回帰の行ごとに回帰 TC を作るので、工程9 の TC 数の規模の警告が出やすくなる（CR 分割の判断材料）。
- 直接検索の内部リンケージの判定は字句による近似（`static`・無名名前空間）。誤ると候補が増える（別ファイルの同名を含む。designer が §7.1 で除く）か、
  減る（そのファイルの外の参照元が候補に現れず、§7.1 でも見直せない）ため、再検討条件に挙げる。

## 再検討条件

- 回帰の候補の上限超過・名前の一致だけの候補の件数が継続して大きい場合は、確認対象の選び方（同一性・距離）を見直す。
- 直接検索の内部リンケージの近似で候補が漏れた事例が出た場合は、判定エンジン（tree-sitter）の解析に切り替える。
- §7.1 に除外した候補が後工程で実際の不具合になった場合は、除外の理由の確かめ方（CHD レビューの観点）を見直す。
