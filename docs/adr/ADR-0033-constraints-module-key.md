# ADR-0033: code-knowledge の知見の置き場所（MODULE）を対象の所在ディレクトリに揃え、スクリプトで決める理由

Status: Accepted
Date: 2026-11-03

前提: [ADR-0005](ADR-0005-knowledge-guide-once.md)（AI_INDEX の知識参照ガイド）。
参照される予定: プラン②（影響仮説。ADR-0031）・プラン③（知見の循環。ADR-0032）。

## Context

既知制約 `{KNOW}/{MODULE}/constraints.md`（`{KNOW}` = `{DOCS}/{repo}/knowledge/code-knowledge`）の `{MODULE}` の決め方が、書く側と読む側で揃っていなかった。

- 書く側: CR クローズ（SPO §5.6・TRS）は「ファイルパスの第1〜2階層ディレクトリ名」（`src/auth`・`auth`・`src-auth` のどれとも読める）、
  LL `#リスク`・`#見落とし` は規則なし、LL `#仕様定義` は決める行なし、`/xddp-survey` はケバブケース（`src-auth`）、`/xddp-update-knowledge` は人の入力をそのまま使っていた。
- 読む側: 工程4a の下調べは第1階層（`{KNOW}/src/`）だけを読み、追加下調べ・依頼調査は既知制約を読まなかった。
  AI_INDEX は `{KNOW}` 直下の `_` で始まらないディレクトリだけを載せ、工程2 は AI_INDEX のラベルを最新仕様のモジュール名から組み立てて引いていた（AI_INDEX が無いと集めない）。

その結果、入れ子（`src/auth/`）・`_general`・ケバブケースで書いた制約の多くを、下調べ・AI_INDEX・工程2 のどれも見つけられなかった。

## Decision

1. **置き場所は知見の対象の所在ディレクトリ**（ファイルならその所在ディレクトリ、ディレクトリならそのディレクトリ。リポジトリ直下は `_root`）。
   対象が複数ならディレクトリ境界での最長の共通の先頭（無ければ・`_root` と混在すれば `_general`）、パスが無ければ `fallback`（既定 `_general`）。
   - 深さを固定（第1階層・先頭2要素）すると、Maven/Gradle（`src/main/java/…`）・Android（`app/src/main/…`）でプロダクションコードの制約が1つの `constraints.md` に集まり、どの構成にも合う深さが無い。
     所在ディレクトリはディレクトリの深さ・名前の慣習（Maven・C の平置き `src/`・組み込みの `Drivers/uart/`）を前提にしない。
   - 共通の先頭にするのは、どの対象のファイルからも祖先の読み方で読めるようにするため（多数決では少数側の対象から読めない）。
2. **読む側は `_general`・`_root`（直下のファイル）・所在ディレクトリとすべての祖先を読む。** 規則がどの深さで書いても、上位に置いた制約（共通の先頭・ディレクトリを対象にした制約）を下位のファイルから読める。
   - `_general`・上位の制約はすべてのファイルに当てはまるので、下調べの観察 f は制約の「対象」がファイル（または定義・使用する識別子）に関係するものとだけ照合し、
     関係を確かめられなかった制約はファイルごと・置き場所ごとに1行（`照合せず`）だけ跡を残す。SPO §5.7 は置き場所ごとに1行にまとめる。
     照合の行がファイル数 × 制約数で増えて工程5 に渡るのを防ぎつつ、LLM の関係の判断で扱いを変えたものを人が見直せるようにするため（CLAUDE.md「人の依頼は LLM の関係判断で拒否しない」）。
3. **置き場所の決定はスクリプト `knowledge_place.py place` が行う。** 書く側のエージェント・スキルは対象の表記を本文に書かれたまま渡すだけにする。
   規則を文で書いて LLM に当てさせる案は、URL・ドライブ付きのパス・`..`・ワークスペースからのパス・ディレクトリ境界の前方一致と正規化の規則が増え、レビューのたびに穴が見つかり、実行ごとにぶれた。
   文字列とファイルの有無だけで決まる決定的な処理なので、スクリプトにしてテストで確かめる（CLAUDE.md「決定的処理はスクリプト・意味判定はLLM」）。対象の表記1つの扱い:
   - 前後の空白・バッククォートを除き、`\` を `/` に揃える（Windows の表記を同じに扱う）。
   - URL は置き場所に使わない（`url`）。
   - 最後の `/` より後の最初の `:`・`#` から後を除く（`パス:行`・`#L10` のアンカー）。最後の `/` より前の `:`（ドライブ名・`host:port/…`・`git@host:org/…`）は除かない。
   - `/` を含まない表記はパスとして扱わない（`no-path`）。拡張子でファイルと判定すると `config.timeout`・`os.path.join`・`com.example.Foo` を直下のファイルとみなし、
     何を拡張子とみなすかもぶれる。直下のファイルは `./main.c` の場合だけパスとして扱う（`main.c:45` は `_general` に置かれ、置き場所が広くなるだけで読む側からは見つかる）。
   - 候補は、絶対パスはそのもの、相対パスはリポジトリのルートにつないだもの・ワークスペースのルートにつないだもの（`repo-a/src/a.c`）の順。
     `/` で始まりワークスペースの下にない表記は、リポジトリのルートからのパスの意味（`/src/a.c`）の候補も最後に加える。
   - リポジトリの下にあり（ディレクトリ境界での前方一致。`repo-a` に対し `repo-a-sdk` は下にない）、所在ディレクトリが実在する最初の候補を採る。
     リポジトリの外（`outside-repo`）・所在ディレクトリが無い（`not-found`）ものは置き場所に使わない。
     直下のファイルは実体があるか `./` で始まる場合だけ見つかったとする（`/tmp`・`/etc` を `_root` に置かないため）。
     実体の無いファイル（CR で削除した）は所在ディレクトリが残っていればそこに置く。
   - ドライブ名の大文字・小文字は区別せず、パスの解決は `posixpath` で行う（OS によらず同じ結果にする）。シンボリックリンクは解決しない。
   - 置き場所の第1要素が予約名（`_root`・`_general`・`_structures`・`_constants`・`_flows`・`_cochange`）と同じ名前のリポジトリのディレクトリになる場合は `reserved_collision` を返し、人に示す。
4. **約束事（入出力・`status`・読み方・列挙・予約名・宛先への当てはめ）は `code-knowledge-boundary.md`「## 知見の置き場所（MODULE）」だけに書く。**
   宛先の単一情報源（宛先ルーティング表）にパスの決め方まで含め、表記1つの扱いの細部はスクリプトとテストに置く（実行時ファイルに規則を書き写さない）。
5. **列挙と当てはまる置き場所は `knowledge_place.py` の関数（`list_places`・`applicable_places`）に1つだけ実装し、`promote.py`・`domain_refs.py` が import する。**
   - AI_INDEX は列挙したすべての `constraints.md`（入れ子・`_general`・`_root`）を載せる。
   - 工程2 は AI_INDEX ではなく直接列挙から集める。AI_INDEX を更新するのはクローズだけなので、survey・手での登録の制約が次のクローズまで見えず、AI_INDEX の有無で結果が変わるため。
     集めるのは `_general`・`_root`、置き場所の最後の要素にキーワードが当たるものとその祖先、最新仕様のモジュール名と一致するもの（今までの規則で置いた `src-auth` 等）。
     先頭・途中の要素（`src`・`lib`・`app`・`main`）は汎用の名前で部分一致の雑音を生むので照合しない（要素が1つの置き場所は最後の要素として照合する）。
6. **CR クローズの LL の昇格は `repo：` 欄で振り分ける。** 実体の確認と組み合わさると、repo A について書いたエントリが repo B では `not-found` で `_general`（repo B のすべてのファイルと工程2 に効く）に入るため。
   `cross`・`unknown` のエントリは制約に昇格しない。
7. 書く側のエージェント（`xddp-close-knowledge-agent`・`xddp-survey-promote-agent`）に `Bash` を足し、Process で Bash を使うのは `knowledge_place.py` の実行（とクローズの出力ファイルの親ディレクトリの作成）だけと書く。

### 却下した案

- 読む側だけを直す（第1階層と第1〜2階層の両方を読む）: 書く側の曖昧さが残り、`_general` も読めず、AI_INDEX・工程2 も直らない。
- 置き場所を第1階層・先頭2要素にする: 上記 1. のとおり集中する。
- module-catalog のモジュールディレクトリを使う: catalog は無いことがあり、更新で置き場所が変わる。
- ソースファイルを持つ最初のディレクトリまで降りる: 判定が言語に依存する。所在ディレクトリと祖先の読み方で深い構成でも上位の制約を読める。
- 置き場所を最新仕様のモジュール名にする: CR ごとの SPO のモジュール名から作られ、ファイルのパスから決定的に決められない。
- 置き場所の深さを書く人に任せ、読む側が前方一致で拾う: 同じ制約が別の深さに重複し、upsert が効かない。
- 観察 f で当てはまる置き場所のすべての制約と照合する: 行がファイル数 × 制約数で増える。
- 既存の知見を移すスクリプトを作る: ケバブケース（`src-auth`）は元のパスに戻せない。後方互換性ポリシーにより移行しない。

## Consequences

- 書く側の3経路（クローズ・survey の昇格・手での登録）は同じ入力で同じ置き場所になる。下調べ・追加下調べ・依頼調査・AI_INDEX・工程2 は同じ読み方・列挙で見つける。
- `constraints.md` の数と AI_INDEX の制約の行は、制約を書いたディレクトリの数だけ増える。工程2 の ANA §0 の参照先には `_general`・`_root` が常に入る。

**範囲外・限界:**
- 既存の知見は移さない。今までの規則で置いた `constraints.md`（`{KNOW}/src-auth/` 等）は AI_INDEX と工程2 の最新仕様のモジュール名との照合では見つかるが、下調べは見つけない。必要なら人が移す。
- リポジトリの第1階層に予約名と同じ名前のディレクトリがあると、その配下の制約と予約名の知見を区別できない（`reserved_collision` で人に示すだけ）。
- 対象のファイルの移動・改名に置き場所は追従しない。`cross` の知見（`{XKNOW}`）に `constraints.md` は置かない。
- ディレクトリごと削除したファイルを対象にした制約は、他にパスが無ければ `fallback`（多くは `_general`）に置かれる。残っている最も近い祖先に置く案は、リポジトリの外のパスまで repo のディレクトリに置きやすくなるので採らない。
  削除したファイルの制約は、所在ディレクトリが残っていればそこに残る（どの経路でも消さない）。
- ADR-0034 で、AI_INDEX は close の Step D2（C3.6 と Step D の後）で作り直すようにしたので、クローズで書いた制約はそのクローズで AI_INDEX に載る。
- 工程2 は `_structures/`・`_constants/` も同じ理由（AI_INDEX の有無で結果が変わらないように）で直接列挙し、直下の `.md` をファイル単位で渡す（ADR-0034）。
- 工程2 は置き場所の最後の要素にキーワードを当てるので、名前がドメインの語にならない置き場所（C の平置きの `src`・`lib`）の制約は `_general`・`_root` でない限り集まりにくい（下調べは祖先の読み方で読む）。
- 既存の問題: `constraints.md` の upsert の鍵は「同一出典」（survey の `SURVEY-{TODAY}`、SPO §5.6 の `{CR_NUMBER}`）で、1回の実行の全エントリに共通なので、同じ `constraints.md` に入る複数の制約が互いに置き換わりうる。
  置き場所が細かくなるので起きにくくはなるが無くならない。別途扱う。
- クローズの LL の昇格が過去の CR の LL も対象にしていた問題は、PLAN-20261102-close-ll-cr-filter（`promote.py extract-ll`。ADR-0013 に追記）で扱った。
