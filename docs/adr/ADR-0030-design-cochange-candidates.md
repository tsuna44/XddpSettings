## Context

C++ の CR で、機能A の構造体 S にフィールド f を足す変更はできたが、S のデータを通信用の構造体 M にフィールドごとに写し、`memcpy` を経て
フィールドごとにバイナリダンプする機能B に f を足す変更が CHD に上がらず、コーディングされなかった。知見の DFD はあったが使われなかった。

- 工程6 Step A3 は CHD §4 から回帰の候補を出すが、「追加」の要素は既存の参照元が無いので起点にしない（ADR-0027 Decision 1）。目的も回帰テストの範囲。
- 波紋調査は既存の値の変化の伝わり方を追う。フィールドを足しても既存のフィールドの値は変わらないので、機能B は影響先として現れない。追加するフィールドは母体に無いので、シードにもできない。
- LLM に grep させても、何を探すかが分かっていないと探さない。件数で処理済みかを確かめられない。

必要なのは「同じ型（とその写し先の型）のフィールドを並べて扱う箇所」という、波紋調査とは別の問い。

## Decision

1. **起点は CHD §4 の型のフィールドの行。** 種別 `データ構造`（`変数` も受け付ける）・変更シンボル `{型名}::{フィールド名}`・変更の内容 `追加`／`シグネチャ`／`削除`、
   種別 `データ構造`・`{型名}`・`シグネチャ`、種別 `変数`・`{変数名}.{フィールド名}`。テンプレートの注記で型のフィールドの行の種別を `データ構造` に決めた。
2. **候補はスクリプトが決定的に列挙する**（`specout_fieldtrace.py candidates`）。起点の型から、写しの辺（1つの関数の中で写し元の型の異なるフィールドを閾値以上写す）・
   包含・継承・丸ごとの写しを `DESIGN_COCHANGE_MAX_DEPTH`（既定 4）までたどって「関係する型」を求め、次を候補にする。
   - 並べて扱う関数: 関係する型 T のフィールドの集合（基底を含む）の異なるフィールドを `min(DESIGN_COCHANGE_MIN_FIELDS, N_T)`（既定 3）以上参照する関数。
     暗黙の `this`／`self` の参照はその関数のクラスに対して数える。
   - 写しを含む関数・写し先の型・形の一致が前提の丸ごとの写し（違う型・バイト列への写し）を含む関数。
   - 起点のフィールドの `削除`／`シグネチャ` では、そのフィールドを参照する関数（閾値によらない）。
3. **言語ごとの部分はアダプタに分ける。** アダプタは型の定義・フィールドの参照・写し・丸ごとの写し・書き出しの事実だけを返し、本体は言語に依存しない。
   C++ は判定エンジンの `Repo`（ADR-0028）の受け手の解決を、自前の解決で決まらないときだけ読み取りで使う（判定エンジンの `classify` の結果は変えない）。
   C の引数は判定エンジンが型を記録しないので、C のアダプタが宣言から型を求める。tree-sitter が無いときは規則判定のアダプタが字句で数え、受け手の型を決めない（すべて name-only）。
4. **LLM には上限つきの要約だけ。** 確認の条件（距離 0・1 は同一性によらず、距離 2 以上は resolved）を満たす候補を、表1（起点のフィールドを参照するだけの関数）と
   表2（それ以外）に分け、バッチごとに各表 30 行を確認対象にする（表を分けるのは、シグネチャの変更で直接の参照が多いときに間接的な箇所が上限で落ちないようにするため）。
   上限超過と遠い名前の一致のみは件数だけを要約に書き、全量は人向けの `cochange-candidates.md` に書く（ADR-0024・ADR-0027 と同じ2層）。
5. **designer が §4 か §4.1 に振り分け、スクリプトが照合する**（`chd_cochange.py check`）。変えるなら §4 に行を足し、第2・3・5・6・7章も書く（工程7 と工程9 に届けるため）。
   変えないなら新設の §4.1 に `不要`（コードで確かめた理由）か `確認できず` を書く。照合は repo の全バッチの §4・§4.1 を見て、designer を呼ぶ前にも照合する
   （他のバッチで処理済みの候補を渡さず、人の判断を覆さない）。複数の場所で処理済みなら §4 ＞ §4.1 不要 ＞ 確認できず の順で1つに決め、食い違いは `conflicts` で人に知らせる。
   上限超過は designer の再呼び出しの対象にしないが、未処理の件数と先頭10件を ⚠️ で人に示し、全量の「処理」列を書き換える。
6. **工程7 の後は報告だけ。** 設計とコードを黙って食い違わせないため、designer を呼ばず、§4・§4.1 に無い候補を人に知らせる（`/xddp-revise` と `/xddp-07-code` のやり直しを案内）。
7. **古さは独自の指紋で判定する**（`chd_cochange.py record`／`status`。この repo の §4・§4.1 の行と設定。母体のコードは入れない）。SPO の無い repo も対象にするため、
   回帰の範囲の指紋とは別に持ち、Regression Status の別の出力（`COCHANGE_STALE`・`COCHANGE_RECORDED`・`COCHANGE_FORMAT_ERROR`）で `/xddp-revise`・`/xddp-feedback`・`/xddp-09-test` に知らせる。
8. 表の読み取り（`_find_table_start`）は下位の見出しでも止まるようにした（§4 に表が無いときに §4.1 の表を §4 として読まないため。§7／§7.1 も同じ）。

### 言語を足す手順

1. 文法パッケージを `xddp-04-specout/scripts/requirements-slice.txt` に足す（`specout_slice._ts` の言語の表にも足す）。
2. アダプタのファイル `specout_fieldtrace_{言語}.py` を作り、`specout_fieldtrace.ADAPTERS` に1行足す（`collect()` が `Facts` を返す）。
3. 標準の題材（S → M へのフィールドごとの写し → 丸ごとの写し・バイト列への写し → フィールドごとの書き出し、S のフィールドを1つだけ使う関数、同じ名前のフィールドの無関係の型 X）を
   その言語で書き、`tests/fixtures/fieldtrace/{言語}/` に置き、`tests/test_specout_fieldtrace.py` の `STANDARD` に期待値を足す。適合テストが登録表のすべてのアダプタを実行する。

### 却下した案

- **designer（LLM）に grep で一緒に直す箇所を探させる:** 何を探すかが分からないと探さず、件数で確かめられない。
- **波紋調査の中でフィールドの追加を起点に追う:** 追加するフィールドは母体に無く、波紋調査は値の伝わり方を追う別の問い（工程4a で使うかは影響仮説のプランで決める）。
- **起点の型を参照するすべての関数を候補にする:** 1つのフィールドだけを使う関数まで入り雑音が大きい（削除・シグネチャの起点のフィールドは例外）。
- **工程8 でコードの差分から漏れを探す:** 漏れに気付くのがコーディングの後になる。
- **判定エンジンに言語の分岐を足す:** 言語の比較が約86か所あり、言語を足すたびに本体を直すことになる。
- **回帰の範囲の指紋に足す:** 回帰の範囲は SPO のある repo だけを対象にする。
- **工程7 の後も designer に §4 へ足させる:** 設計とコードが黙って食い違う。

## Consequences

### 計測（実装時）

| 題材 | 起点 | 結果 |
|---|---|---|
| 標準の題材（C・C++・Python、スライス判定） | `S::e`（追加） | 確認対象は `to_msg`・`relay`・`dump`・型 M の4件だけ。`only_one`・`x_dump` は候補にならない |
| 標準の題材（規則判定） | 同上 | 上の確認対象を含む（Python の `relay` を除く）。無関係の型 X と `x_dump` も名前の一致で確認対象になる（name-only） |
| spdlog（`03bec982` の親。`bench/`・`example/`・`tests/` を除外） | `log_msg::tag`（追加） | 表2 の候補9件・すべて確認対象（上限超過 0）。修正 `03bec982` で変わった既存の関数3つ（キー2つ: `log_msg_buffer::log_msg_buffer`〔オーバーロード2〕・`log_msg_buffer::update_string_views`、距離1・8位と9位）を含む。他の7件は `log_msg` のフィールドを並べて出力する sink・formatter。所要時間 約0.9秒 |
| 同上 | `log_msg::source`（シグネチャ） | 表1 8件・表2 9件。表2 は上と同じ |

### 範囲外・限界

- バイト列を経由して別の場所で別の型として読む経路は、バイト列から型へのつながりをたどらない（`丸ごとの写し` の候補を designer が読み、先を探す）。
- フィールドを1つずつ別の関数・クラスで扱う作り（spdlog の `pattern_formatter` のフラグごとの formatter 等）・オフセットの表・X マクロ・リフレクション・シリアライズのライブラリ。
- リポジトリの外・他の repo。`cross` の CHD には行わない。
- 規則判定の Python は、型を決められない丸ごとの写し（`pickle.dumps(x)` 等）を候補にできない。
- 受け手の型を決められない参照は、同じ関数がその型を1つ以上決められた参照で使うときだけ名前で数える（スライス判定）。規則判定はすべて名前で数える。
- 同じ素の名前の型は1つにまとめる（名前空間の違いを区別しない）。

### トークン

確認対象の未処理が残ったバッチごとに designer を1回（照合の漏れで1回追加）。候補の無い CR では増えない。

### 再検討条件

- §4.1 に `不要` とした候補が後で不具合になった場合は、判断の観点（`xddp.design.rules.md`）と CHD レビューの観点を見直す。
- 上限超過・遠い名前の一致のみが継続して多い場合は、閾値・並び順・上限（距離ごとの上限等）を見直す。
- spdlog 以外の実例で閾値が合わない場合は、`DESIGN_COCHANGE_MIN_FIELDS` の既定値を見直す。
