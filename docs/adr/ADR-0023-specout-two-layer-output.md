## Context

ADR-0019〜ADR-0022 で波紋調査は LLM をほぼ使わない決定的な処理になったが、その後段に次の問題が残った。

- **重いのは波紋調査の後段。** M2（u1-eval frr・CR-2026-803）では、波紋調査（第0〜9波）はスライス判定だけで LLM を使わずに完走した。
  一方、届いた全モジュールを資料にする Step A-Document で、モジュールごとの document agent（`DOC_MODE: module`）が 26 件で合計 3,357,150 トークンを使い、
  429（セッション上限）で4件が止まった（計測記録 §3.1）。
- **資料にした範囲の大半は誤った到達。** M-a で確定ファイルの 80%（30件中24件）が名前の一致のみだった（調査資料 §5.2）。
  P2 の後も frr の確定 434 件のうち 162 件が `name-only`（同 §5.3）。
- **波紋調査をしないと工程4a が終わらない。** シード確認で「下調べ資料で止める」を選ぶと ⏸ 中断になり、工程4b へ進めなかった（ADR-0018 §13）。
- **後工程の LLM に大きな表が渡る。** M2 の SPO §5.5（全確定ファイルのテスト状況）は約 850 行、SPO 全体は 153,026 バイトだった。
  full プロファイルでは §5.2 も第1波以降の全関数を載せていた。

## Decision

2026-10-12 のユーザーとの合意（プラン §1.2 の E1〜E13）に基づき、次のとおりにする。

### 1. 下調べを母体調査の本体とし、下調べだけで工程4a を完了できるようにする（E1・E2・E11）

- 下調べ（LLM が CRS に関係する母体処理を調べ、SPO とモジュール資料を書く）を母体調査の本体とする。
  波紋調査を行わない repo も、下調べの資料で工程4a を完了し、工程4b へ進める（ADR-0018 §13 を置き換える）。
- 波紋調査は「シードからの機械的な全ソースコード調査（波数・ヒット数の上限あり）」で、下調べで調べた範囲の周りを確認する追加の調査と位置付ける（E2。調査資料 §2 と同じ）。
- 下調べが完了しなかった repo は、波紋調査・SPO の仕上げへ進めず停止する（E11）。再実行で下調べからやり直す。
  「下調べなしで続行し、資料はすべて波紋調査の後に作る」経路は廃止する。

**理由:** 後段（届いた範囲の資料化）を LLM にさせない（§3）と、下調べの無い repo は SPO の詳しい資料を持てない。
下調べは CRS から出発して読むので、名前の一致による誤った到達を含まない。

### 2. 波紋調査は既定で行い、repo ごとに人が外せるようにする（E3）

- 対象リポジトリ（Step 0.5）は今と同じ。Step A-Seed で repo ごとに「波紋調査: 行う（既定）／行わない」を確認する。
  「`{repo}`: 波紋調査なし」と指示した repo には印 `work/no-ripple.json` を書き、その repo は下調べの資料で SPO を仕上げる。
- 「下調べ資料で止める」（CR 単位の ⏸ 中断）は、「中断する」（波紋調査を始めずに中断。工程4b へ進まない）と「波紋調査なし」（工程4a を完了できる）の2つに分ける。
- `SPECOUT_SEED_GATE: false` なら確認せず、全 repo で波紋調査を行う。
- `work/no-ripple.json` は「波紋調査を行わないと人が決めた」ことの唯一の情報源とし、状態テーブル・Step A-Document・Step A-cross-propagate・Step C5・Step E・
  `artifact_lint.py` の F4 が同じ印で判定する。工程4a の完了後にその repo へ波紋調査を加える入口は作らない（P4 の範囲）。

**理由:** 波紋調査はスクリプトだけで軽く、既定で行っても負担が小さい（ADR-0018 §14 の「自動でスキップしない」は維持する）。
印をファイルに残すのは、波紋調査を行わない repo には `bfs-state.json` が無いためである。印が無いと、工程4b で CRS が更新された後の再実行で
Step A-Prelim に入り、下調べを再利用せず SPO・`modules/`・台帳を削除してしまう。

### 3. 詳しい資料を書く LLM は下調べと追加下調べだけにする（E4・E5・E9・E13）

- 届いたモジュールを LLM が材料の抜粋から資料にする処理（`doc-digest` の材料作り・モジュールごとの document agent `DOC_MODE: module`）を廃止する
  （ADR-0020 §1 を置き換える）。document agent は SPO の LLM が書く欄と funcmap を書く1回だけの起動形にする。
- **追加下調べ（E5）:** 波紋調査で、シードが直接参照するファイル（`seed_direct_files`）のうち下調べの台帳に無いものがあれば、そのファイルについて
  下調べのエージェント（`xddp-specout-prelim-agent`、`PRELIM_MODE: additional`）を repo ごとに1回、自動で起動して資料を書かせる（人は選ばない）。
  エージェントはソースを読み、CRS の振る舞いに関係しないと判断したファイルは `work/prelim-gap-reviewed.md` に記録する（再実行で対象・警告に戻さない）。
  追加下調べの後も残ったものは SPO §5.0 の ⚠️ と §9 で人に警告する。
  資料の確定で「台帳に無い確定ファイル」を読んでいた ADR-0018 §3 は、「シードの直接参照のうち台帳に無いファイル」を追加下調べで読む、に置き換える。
- **設定キー（E9）:** `SPECOUT_DOC_LINE_BUDGET`・`SPECOUT_DOC_MAX_MODULES`・`SPECOUT_DOC_PARALLEL` を廃止する。打ち切り記録の理由 `doc-limit` も廃止する。
  追加下調べの対象ファイル数の上限には、既存の `SPECOUT_MAX_AFFECTED_FILES`（既定 `20`）を repo ごとの**累計**で使う。
  超えた分は追加下調べせず、E5 の警告に回す。採る順は、同一性 `resolved` のファイル → シードのヒット行数（state の `seed_direct_hits`）の多い順 → パスの順で、state だけで決める。
- **`SPECOUT_MAX_AFFECTED_FILES` の意味（E13）:** 「CR 分割警告ライン（確定ファイル数）」から「変更の中心として扱うファイル数の目安」に改める。
  CR 分割の警告はシードの直接参照ファイル数（`seed_direct_file_count`）で判定する。既定 `20` は変えず、新しい設定キーは作らない。

**理由:**
- 人は母体コードを知らないことがあり、届いたモジュールから資料にするものを選べない。このため、調査資料 §4.1 の③④（人が選んで追加の資料化）と D6 を取り消し、
  資料にする対象を機械的に決まる「シードの直接参照のうち下調べに無いファイル」に絞った。名前の一致だけで届いたファイルが大半を占めるため（Context）、
  届いた範囲全体を資料にしても誤った到達の資料が増えるだけである。
- `SPECOUT_DOC_MAX_MODULES` は最初の質問で「安全上限として残す」との回答を得た。追加下調べの件数は下調べの精度だけでなくシードの呼び出し元の数に比例し、
  プロジェクト・CR によって変わるため、安全上限をファイル単位で設ける。新しいキーは作らず、既存の `SPECOUT_MAX_AFFECTED_FILES` の意味を改めて使う。
  上限を累計にするのは、上限を上げずに再実行するだけで次の N 件が人の確認なしに追加下調べされないようにするため。
  参考: M2 ではシードの直接参照 5 件のうち下調べに無いものは 1 件だった（根拠はこの1件のみ）。
- 確定ファイル数での CR 分割の判定は、M2 で 832 件（P2 の後 434 件）対 20 となり、ほぼ常に警告が出ていた。
- 追加下調べは1つのエージェントが repo ごとに1回、台帳・観察メモへ直接書くので、並列の書き込み衝突を避けるモジュール別の一時ファイルとそのマージは不要になる。

### 4. 波紋調査の結果は LLM を使わずスクリプトで反映する（E6・E7・E8・E10）

- `specout_bfs.py ripple-summary`（`doc-digest` を置き換え）が要約を作り、`assemble-spo` が次の3つに反映する（E6）。
  - (a) SPO §5.0: 1モジュール＝1行。列は 確定ファイル数・うち名前の一致のみ・最も浅い到達波・シードの直接参照（うち資料に無い）・資料（あり／なし）・影響の経路の代表。
    全モジュールを対象にし（波で絞らない）、超えた分は「ほか {k} モジュール・{f} ファイル（`ripple-summary.md` を参照）」の1行にまとめる。
  - (b) 資料のある各モジュールの資料に「波紋調査の結果」の節（分割パスは `## 波紋調査の結果`、統合パスは `### 2.X.9 波紋調査の結果`）。そのモジュールで届いたファイルの表。
  - (c) 人向けの全量 `ripple-summary.md`（上限なし。LLM には渡さない）。
- 上限の行数（E10）: §5.0 と「波紋調査の結果」はどちらも 30 行（調査資料 D1）。設定キーにせずスクリプトの定数にする。
- 要約の範囲（E7）: 波で絞る設定（調査資料 D7）は今は作らない（保留）。§5.0 は 30 行で頭打ちになり、M-c では波で絞ってもモジュール数はほとんど減らなかった（調査資料 §5.2）。
  必要になったら後から設定を足す。
- SPO §5.2・§5.5（E8）: 資料のあるモジュール（下調べ・追加下調べ）のファイルだけを載せる。全量は `ripple-summary.md` と discovery-log に残す。
- 「影響の経路の代表」列は残す。調査資料 §4.2 は経路の列を「今のデータでは作れない」としたが、discovery-log の派生元から代表の連鎖は作れており、
  名前の一致による到達を見分ける手がかりになる。§5.0 の「主な影響箇所（関数）」と「確認の観点」（LLM が書く列）は削除する。
- 最終の組み立ての配置判定（成長型）は台帳（資料のあるファイル）だけで行い、資料の無いモジュールの `modules/` の索引を作らない。

**理由:** LLM に渡すのは、波紋調査の規模によらず上限つきの要約だけにする（調査資料 §4.1）。モジュールの集計は `doc-digest` と同じ処理を使い、
LLM 向けの材料（関数本文の抜粋）だけを無くす。配置判定に波紋調査の確定ファイルを入れると、資料の無いモジュールに `modules/` の索引ができ、
統合パスが確定ファイルの件数で分割パスへ移ってしまう。

### 5. 回帰テストは資料のあるモジュールだけを対象にする（E12）

> **ADR-0027 で取り消し。** 回帰テストの範囲は CHD §4 の変更シンボルから決め、CHD §7 の回帰の行から作る（[ADR-0027](ADR-0027-regression-scope-from-chd.md)）。

工程9 の回帰テストは SPO §5.2（資料のあるモジュール）だけを対象にし、資料の無いモジュールの回帰テストは作らない。
SPO §5.0 で「資料」が `なし` かつ同一性が確定したファイル（確定ファイル数 − うち名前の一致のみ）が 1 以上の機能は、TSP の気づき・提案メモに「未調査の回帰リスク」として挙げる。

**理由:** 調査していない既存動作の回帰テストは書けず、届いた範囲の大半は名前の一致による到達である。ただし `resolved` の到達は回帰の可能性を否定できないので、人に知らせる。

### 6. 再実行で人の修正を保持し、LLM が書く欄は入力が変わったときだけ書き直す

- モジュール資料（分割パスの `modules/`・統合パスの §2.A… の 2.A.1〜2.A.8）・台帳・累積観察メモは再実行で保持する。
  スクリプトが書く欄（§1・§1.x・§5.0・§5.1・§5.2・§8・§9 の自動転記）と「波紋調査の結果」は毎回作り直す。
  §5.5（テスト可能性）は行を毎回作り直すが、値は累積観察メモに行のあるファイルだけ観察メモの値に置き換え、それ以外は既存の値（`未確認` 以外。人の修正を含む）を残す。
  観察メモにも既存の行にも値が無いファイル（波紋調査で届いただけで読んでいないファイル等）は `未確認` と書き、空欄にしない（lint S3 の warning が SPO レビューに転記され続けるのを防ぎ、推測で埋めないため）。
- SPO の LLM が書く欄（§2〜§4・§5.3・§5.4・§5.6・§5.7・§7）と funcmap は、入力の指紋（台帳・`ripple-summary.json`・`no-ripple.json` の有無・CRS の内容・document agent に渡す ENTRY_POINTS）が
  前回の成功時から変わったとき、または前回の document agent が成功していないときだけ書き直す。指紋は document agent の成功と lint の通過の後にだけ
  `commit-assemble-inputs` で保存する。ENTRY_POINTS は人の指定と伝播のシンボルを `work/doc-entry-points.json` に累積して決める（引数なしの再実行・伝播の後の再実行で指紋が変わらない）。
- 版の確定（0.1 → 1.0）は document agent ではなく `assemble-spo` が行う。

**理由:** E1 で下調べの資料が本体になったため、人が直したモジュール資料を再実行で失わないようにする。版の確定を行っていた `DOC_MODE: module` の agent を無くすため、スクリプトに移す。

### 7. 検証スイープ・lint の追従

- `verify-sweep` の突き合わせ先を台帳から波紋調査の帳簿（`confirmed_files`・`false_positive_files`）に変える。未記録ヒット（終了コード 7）は人の承認を待たず SPO §9 に記録する。
  台帳と突き合わせると資料にしなかったファイルがすべて未記録になるため。人はコードを見て判断できないことがあり、止めても判断の材料が増えない。
- 波紋調査なしの SPO（`work/no-ripple.json`）では、`artifact_lint.py` の F4 を `checks_skipped` にする。§5.1 は台帳のファイルごとの行（識別子「（モジュール資料を参照）」）で、
  funcmap の識別子と照合できないため。F1〜F3・S1〜S5 は今どおり検査する。

### 8. 置き換える決定と維持する決定

| 既存の決定 | 扱い |

| ADR-0018 §3（資料の確定で台帳に無い確定ファイルだけを読む） | **置き換える**。追加下調べでシードの直接参照のうち台帳に無いファイルだけを読む（本 ADR §3） |

| ADR-0020 §3（成長型の配置規則・`doc-targets --auto-assign`） | 維持する |

## Consequences

- 工程4a の LLM の作業は、下調べ・追加下調べ（repo ごとに最大1回）・SPO の LLM が書く欄（1回）だけになり、波紋調査の規模に比例しない。
  M2 相当の CR では、モジュールごとの document agent（26件・約336万トークン）が無くなる見込み（見込みであり、計測はプラン §5 で行う）。
- `modules/` に入るのは資料のあるモジュールだけになる。各資料に「波紋調査の結果」（最大30行）が加わる。波紋調査で届いただけのモジュールは SPO §5.0 の1行と `ripple-summary.md` にしか情報が無い。
  工程11 の最新仕様書も資料のあるモジュールだけになる。
- 工程9 の回帰 TC は資料のある機能だけになる。
- 工程5 の architect agent は SPO §1.x・§5.0（新しい列）・§5.2 とモジュール資料の「波紋調査の結果」を読む。「確認の観点」列と「材料外（未確認）」は無くなる。
- 下調べの品質への依存が強くなる。下調べが CRS に関係するコードを拾えたかを機械的に確かめる手段は、E5 の「シードの直接参照のうち下調べに無いもの」だけである。
- 波紋調査なしの SPO では funcmap と §5.1 の識別子の食い違いを機械では見つけられない（レビュー L1 と人の確認に頼る）。
- `specout_bfs.py` の `doc-digest` が `ripple-summary` に置き換わり、`commit-assemble-inputs` が加わる。`work/digest/` は作られない。
  `metrics.jsonl` に `specout_doc_summary`（下調べ・追加下調べ・`prelim_gap` の件数）が記録される。
- マルチリポジトリで、波紋調査を行わなかった repo は Step A-cross-propagate の伝播先にならない（`cross-propagation-log.json` の `status` = `no-ripple`）。
- 後方互換性は保証しない。台帳に工程 `資料の確定` の行がある CR は台帳の書式検査で止まり、工程4a の再実行（下調べから）で作り直す。

## 再検討条件
