## 1. 基本モデル

### 1.1 Canonical JSON を正本とする（README「なぜCanonical JSONか」、JSON定義 §1）

```
                     ┌─────────────┐
                     │  Canonical  │  ← 正本（Single Source of Truth）
                     │    JSON     │
                     └──────┬──────┘
          ┌─────────┬───────┼───────┬──────────┐
       Excel    Markdown   HTML  Legacy JSON  YAML
```

- すべての USDM 成果物（マークダウン・Excel・HTML 等）は Canonical 形式を経由して変換される（JSON定義 §1）。
- 狙いは 4 点：**Git で意味のある差分が取れる／JSON Schema で機械検証できる／変換ロジックが N×N でなく N+N で済む／Excel が無くても編集できる**（README）。

> **XDDP への含意**：Markdown ⇄ Excel の直接変換（現行 `xddp.md2excel` / `xddp.excel2md`）は
> この N+N モデルでいう「N×N の一辺」に相当する。Canonical JSON を中間に置けば
> 検証と他形式への展開を同じ経路に載せられる（考察は §9.7）。

### 1.2 8 つの構成要素とスキーマの対応（JSON定義 §4）

| # | USDM 構成要素 | Canonical JSON での表現 |
|---|---|---|
| 1 | キーワードラベル | `requirement.keywords[]` / `subRequirement.keywords[]` |
| 2 | 要求 | `requirement.requirement` / `subRequirement.requirement` |
| 3 | 理由 | `requirement.reason` / `subRequirement.reason` / `specification.reason` |
| 4 | 説明 | `requirement.explanation` / `subRequirement.explanation` / `specification.explanation` |
| 5 | 仕様 | `specification.specification` |
| 6 | 仕様ラベル | `specification.verified`（`[boolean, boolean, boolean]`） |
| 7 | グループ | `requirementGroup.name` / `specificationGroup.name`（＜＞で囲む） |
| 8 | カテゴリ（＝上位要求グループ） | `category.name`（＜＞で囲む・ID を持たない） |

### 1.3 プロパティ名は英語、表示は View の責務（JSON定義 §9、スキーマ `$comment`）

日本語ラベル（「要求」「理由」等）はビュー側でのロケールマッピングとして扱う。
データ構造そのものは英語プロパティで固定する。

## 2. 文書構造

### 2.1 階層（JSON定義 §2）

```
USDMDocument（文書）
├── Metadata（メタデータ） [0..1]
├── Category（カテゴリ） [1..*]
│   └── Requirement（要求） [0..*]
│       ├── {選択} SpecificationGroup（仕様グループ） [0..*]  ← 1階層パターン
│       └── {選択} RequirementGroup（要求グループ） [0..*]    ← 2階層パターン
│                  └── SubRequirement（下位要求） [0..*]
│                       └── SpecificationGroup（仕様グループ） [0..*]
│                            └── Specification（仕様） [0..*]
├── RequirementRelation（要求間関連） [0..*]
└── SpecificationGroupRelation（仕様グループ間関連） [0..*]
```

**重要**：1 つの要求は `specificationGroups`（1階層）と `requirementGroups`（2階層）を
**同時に持つことが可能**（JSON定義 §2 注記、スキーマ `Requirement` の `$comment`）。
「どちらか一方」ではなく「両方可」である点は誤解しやすい。

### 2.2 構造上の制約（MD定義 §8、JSON定義 §9）

| 制約 | 内容 | 機械検証 |
|---|---|---|
| 階層の深さ | 上位要求 → 下位要求 の **2 階層まで**。下位要求はさらに要求グループを持てない | ○（`SubRequirement` に `requirementGroups` が無い） |
| 仕様グループ | 存在する場合 **1 以上必須**（`minItems: 1`） | ○ |
| 仕様 | 各仕様グループにつき **1 以上必須**（`minItems: 1`） | ○ |
| 下位要求 | 各要求グループにつき **1 以上必須**（`minItems: 1`） | ○ |
| カテゴリ | 文書につき **1 以上必須**（`minItems: 1`） | ○ |
| グループ名 | カテゴリ・要求グループ・仕様グループとも `^＜.+＞$`（全角山括弧・3 文字以上） | ○ |
| 独自項目の追加 | **全定義で `additionalProperties: false`**。規定外のフィールドは許されない | ○ |

`additionalProperties: false` が全定義に付いている点は、小冊子の禁止事項
「『要求』『理由』『説明』『仕様』『仕様グループ』以外の項目を追加しない」を機械的に強制したものと読める。

## 3. Markdown 記法ルール

### 3.1 見出しレベルは要素種別で固定（MD定義 §1・§2）

```
H1  # {title}                       ... 文書タイトル
H2  ## ＜カテゴリ名＞                 ... Category（＜＞・ID 無し）
H3  ### {keywords}: 上位要求 {id}     ... Requirement
H4  #### ＜要求グループ名＞           ... RequirementGroup（2階層時のみ）
H5  ##### 下位要求 {id}              ... SubRequirement（2階層時のみ）
H6  ###### ＜仕様グループ名＞         ... SpecificationGroup
-   - □□□ **{id}**: {仕様テキスト}   ... Specification（リスト）
```

- **山括弧 ＜＞ を使う「グループ系」は偶数レベル、要求は奇数レベル**という規則性を持つ（MD定義 §2）。
- **見出しレベルが要素種別を一意に決めるため、レベルを崩してはならない**（MD定義 §2）。
- **仕様は見出しではなくリスト項目**である。これにより H1〜H6 の 6 レベルで全階層が収まる。
- 要求・下位要求の本文は `**要求**:` / `**理由**:` / `**説明**:` の 3 行で表す（MD定義 §1）。

### 3.2 パースの注意（MD定義 §9「パース時の注意」）

- `### {keywords}: 上位要求 {id}` は `: ` で分割し、右側から固定ラベル `上位要求 ` を除いて `id` を得る。
- `##### 下位要求 {id}` は固定ラベル `下位要求 ` を除いて `id` を得る。
- **「上位要求」「下位要求」は表示用の固定ラベルであり、Canonical JSON には保存しない。**

### 3.3 1階層パターン（MD定義 §4）

要求グループ（H4）・下位要求（H5）が存在しないため、**上位要求（H3）の直下に仕様グループ（H6）が続く**
（H4・H5 はスキップする）。「シンプルで下位要求への分割が不要な要求に使う」。

```markdown
## ＜カテゴリ名＞

### キーワード: 上位要求 R01

**要求**: {requirement}
**理由**: {reason}
**説明**: {explanation}

###### ＜仕様グループ名＞
- □□□ **S01-01**: {specification}
```

### 3.4 2階層パターン（MD定義 §5）

「複雑な要求を下位要求に分割するときに使う」。H1〜H6 をすべて使用する。

### 3.5 強制2層パターン（MD定義 §6、v1.1.0 の新規ルール）

**ある要求グループに属する下位要求が 1 つだけの場合に適用する。**
下位要求の `requirement` は上位要求とほぼ同義になるため、
**その下位要求の `reason`（理由）・`explanation`（説明）は空白とする。**

```markdown
#### ＜要求グループ名＞

##### 下位要求 R01-01

**要求**: {requirement}
**理由**:
**説明**:

###### ＜仕様グループ名＞
- □□□ **S01-01-01**: {specification}
```

> MD定義 §6 の注記：「強制2層は『2階層として整える』ための運用ルール。
> 理由・説明を空白にすることで、上位要求との重複を避けつつ階層構造を保つ。」

このルールのために、スキーマ上 `SubRequirement` の `required` は `["id", "requirement"]` のみであり、
`reason` は必須でない（`Requirement` は `reason` が必須）。

## 4. 要素別の必須・任意（スキーマ `definitions`）

| 要素 | 必須プロパティ | 任意プロパティ | 備考 |
|---|---|---|---|
| USDMDocument | `version`, `title`, `categories` | `$schema`, `metadata`, `requirementRelations`, `specificationGroupRelations` | `version` は `"1.1.0"` 固定（`const`） |
| Metadata | （なし） | `author`, `created`, `modified`, `description` | 日時は ISO 8601 推奨。Git 管理との併用を想定 |
| Category | `name`, `requirements` | `id`（**非推奨**） | `id` は「トレーサビリティ用の内部 ID。表示には出力しない」 |
| Requirement | `id`, `requirement`, **`reason`** | `explanation`, `keywords`, `specificationGroups`, `requirementGroups` | **理由が必須**である点が重要 |
| RequirementGroup | `name`, `subRequirements` | （なし） | |
| SubRequirement | `id`, `requirement` | `reason`, `explanation`, `keywords`, `specificationGroups` | 理由が任意なのは強制2層のため |
| SpecificationGroup | `name`, `specifications` | （なし） | |
| Specification | `id`, `specification` | `reason`, `explanation`, `verified` | `verified` の default は `[false,false,false]` |

補足：

- `requirement`（要求テキスト）の説明は「**目的語と動詞で振る舞いを記述**」（スキーマ `Requirement.requirement`）。小冊子の記述マナーと一致する。
- `explanation` の default は `""`。
- `keywords` は `uniqueItems: true`（重複禁止）。
- `SpecificationGroup` の説明に「**従来のインラインマーカー方式ではなくコンテナ構造を採用**」とある。Excel 上で `＜グループ名＞` を仕様行の間に挟む方式から、明示的な親子構造へ変えたということ。

## 5. ID 体系（JSON定義 §5、スキーマ）

| 要素 | ID 形式 | パターン | 例 |
|---|---|---|---|
| Category | （ID なし） | — | ＜機能要求＞（名前のみ） |
| Requirement | `RXX` | `^[A-Za-z][A-Za-z0-9_-]*$` | R01, R02, R11 |
| SubRequirement | `RXX-YY` | 同上 | R01-01, R01-02 |
| Specification | `SXX-YY-ZZ` | **パターン制約なし**（任意文字列・`minLength: 1`） | S01-01-01, spc11-01-01 |

- **要求 ID は英字始まり**（`^[A-Za-z]...`）。数字始まりの ID はスキーマ違反になる。
- **仕様 ID にはパターン制約がない**。ドット・スラッシュ等を含む ID も許容される。
- ID は「文書全体で一意」（スキーマ `description`）。
- 下位要求 ID は「**親要求 ID をプレフィクスとする命名を推奨**」（スキーマ `SubRequirement.id`）。
- 「要求・下位要求の ID の命名規約は**プロジェクトごとに決定してよい**」（JSON定義 §5 注記）。

## 6. 仕様ラベル（verified）（JSON定義 §6、MD定義 §3）

`verified` は `[boolean, boolean, boolean]` の 3 要素固定配列。

| JSON 値 | 表示 | 意味 |
|---|---|---|
| `[false, false, false]` | □□□ | 未レビュー |
| `[true, false, false]` | ■□□ | レビュー済み |
| `[true, true, false]` | ■■□ | 実装済み |
| `[true, true, true]` | ■■■ | テスト済み |

- 「**□ の存在が『これは仕様である』ことを示し、ステータス管理にも使用する**」（MD定義 §1 注記）。
  つまり 1 つの記号が「種別の標識」と「進捗チェックボックス」を兼ねる。
- MD定義 §9 の変換擬似コードでは、`true` の**個数**で記号を決めている
  （0→□□□、1→■□□、2→■■□、3→■■■）。したがって `[false, true, false]` のような
  歯抜けは Markdown 上では `■□□` に丸められ、往復変換で情報が落ちる。
- **3 段階の意味（レビュー／実装／テスト）は本スキーマで定義されたもの**であり、
  小冊子側は「仕様どおりに実装されているかを確認するチェックリスト」とだけ述べている（§8 参照）。

## 7. 分割軸と関連（JSON定義 §7）

USDM メタモデルの「要求分割」「仕様分割」を、**トップレベルの関連配列**として表現する。
階層のネストではなく、ID 参照によるグラフとして持つ。

| 関連の種類 | プロパティ | 構成 |
|---|---|---|
| 要求間関連 | `requirementRelations[]` | `sourceId`, `targetId`, `divisionAxis`（全て必須） |
| 仕様グループ間関連 | `specificationGroupRelations[]` | `sourceName`, `targetName`, `divisionAxis`（全て必須） |

**分割軸（DivisionAxis）は 4 値の enum**：

| 値 | 説明 |
|---|---|
| `時系列分割` | 時間の流れに沿って分割 |
| `構成分割` | 構成要素ごとに分割 |
| `状態分割` | 状態ごとに分割 |
| `共通分割` | 共通する要素を分割 |

仕様グループ間の関連は **ID ではなくグループ名（`sourceName`/`targetName`）で参照する**点に注意。
仕様グループは ID を持たないため、名前が実質的な識別子になっている。

## 8.【考察】小冊子版ルールとの差分

> 本章以降は出典の記載ではなく、本書と [usdm-notation-rules.md](usdm-notation-rules.md) の突き合わせによる分析である。

### 8.1 一致している点

| 項目 | 小冊子 | スキーマ |
|---|---|---|
| 要求は 2 階層まで | 補足編 3.1「三階層以上は作成しない」 | `SubRequirement` に `requirementGroups` を持たせない構造 |
| 要求は動詞形・目的語＋動詞 | 基礎編 2.2.3 | `Requirement.requirement` の description「目的語と動詞で振る舞いを記述」 |
| 独自項目を追加しない | 補足編 3.5 | 全定義 `additionalProperties: false` |
| 分割軸 4 種 | 基礎編 4.2.4 | `DivisionAxis` enum 4 値 |
| 仕様グループは ＜＞ | 補足編 2.3 | `pattern: ^＜.+＞$` |
| 理由は必ず書く | 補足編 3.2「終盤は記述する」 | `Requirement.required` に `reason` |

### 8.2 食い違う点（要注意）

| # | 項目 | 小冊子 | スキーマ | 影響 |
|---|---|---|---|---|
| 1 | **仕様の理由・説明** | 専用欄を作らず、**仕様の文章中に【理由】【説明】として埋め込む**（補足編 2.4・3.5） | `Specification.reason` / `.explanation` という**専用フィールドがある**（JSON定義 §8.3 に記述例） | 逆の指示。スキーマ準拠なら構造化フィールドを使う |
| 2 | **主分割記号 ＜＜ ＞＞** | 補足編パターン2 に二重山括弧の「主分割記号」（文書全体で共通の大分類・オプション）と一重の「補助分割名」の 2 段がある | **表現手段が無い**。`SpecificationGroup` はネストできず、`pattern: ^＜.+＞$` は二重山括弧も形式上は通るが構造的な区別は付かない | 主分割を使っている文書は Canonical JSON に写せない |
| 3 | **カテゴリと ID** | カテゴリ記号を要求 ID の prefix にする（`URIAGE-01`） | カテゴリは ID を持たず、要求 ID との関係も規定しない（`Category.id` は「非推奨」） | 命名規約の裁量はプロジェクト側 |
| 4 | **仕様 ID の飛び番号** | 補足編 2.6「枝番は飛び番号にしたほうが追加がしやすい」。PDF の全例が飛び番号 | 制約なし・推奨の記載もなし | スキーマは飛び番号を妨げない。運用側で決める |
| 5 | **仕様ラベルの意味** | 「USDM 自体をチェックリストとして使用でき、仕様どおりに実装されているかを確認できる」（基礎編 3.1①）。3 段階の定義は無い | **レビュー済み／実装済み／テスト済みの 3 段階を定義**（JSON定義 §6） | スキーマ側で意味を追加している |
| 6 | **1 要求が両パターンを併用** | パターン1／パターン2 のいずれかとして図示 | `specificationGroups` と `requirementGroups` の**同時保持が可能** | スキーマのほうが緩い |
| 7 | **強制2層** | 記載なし（v1.1.0 で追加されたルール） | MD定義 §6 で規定 | 小冊子だけを読んでいると知らないルール |
| 8 | **記述マナー（文の質）** | 否定表現・「等」「etc」・ペースト作文の禁止、動詞 5〜7 個、範囲の明示など | **一切規定していない** | スキーマ検証を通っても USDM として不十分になりうる |

**結論**：スキーマ検証は「骨格の妥当性」しか見ない。
`ajv validate` が通ることと USDM として良い要求仕様書であることは別問題である。
XDDP のレビュー観点は、両方を独立にチェックする必要がある。

### 9.1 概念対応

| Canonical Schema | 現行 CRS テンプレート | 評価 |
|---|---|---|
| `USDMDocument.title` | `# 変更要求仕様書` + 文書番号等の属性行 | 対応 |
| `Category.name`（＜＞・ID 無し） | `#### カテゴリ：{カテゴリ名}` ＋ UR の `**カテゴリ：**` 属性 | 対応。ただし ＜＞ 無し・見出しレベルが異なる |
| `Requirement`（上位要求） | `##### UR-XXX` | 対応 |
| `RequirementGroup.name` | `###### 要求グループ：{名前}` | 対応。＜＞ 無し |
| `SubRequirement`（下位要求） | `###### SR-XXX-YYY` | 対応。**要求グループと同一見出しレベル** |
| `SpecificationGroup.name` | `####### 仕様グループ：{名前}` | 対応。＜＞ 無し・**H7 は Markdown に存在しない** |
| `Specification` | `####### SP-XXX-YYY.ZZZ`（見出し＋属性リスト） | スキーマはリスト項目。**構造が異なる** |
| `Specification.verified` | `**ステータス：**`（確定 / 🔍 要検討 / ⚠️ 懸念あり / ❓ 未決） | **意味が異なる**（§9.5） |
| `Specification.reason` | （**該当なし**） | 欠落 |
| `requirementRelations[].divisionAxis` | 記述ルールに「要求の分割方法：時系列・構成・状態・共通」とあるのみ。**記録先が無い** | 欠落 |
| `Metadata` | 文書番号・対象CR・作成日・作成者・版数 | 対応（`description` 相当は無し） |
| （スキーマに該当なし） | `**Before：** / **After：**` | XDDP 拡張 |
| （スキーマに該当なし） | `懸念・検討事項` / `付記A` / `付記B` / `付記C` | XDDP 拡張 |

### 9.2 【最重要】見出しレベルの構造欠陥

現行 CRS テンプレートの見出しレベルは次のようになっている。

| 要素 | 現行レベル | スキーマ規定 |
|---|---|---|
| カテゴリ | `####`（H4） | H2 |
| UR（上位要求） | `#####`（H5） | H3 |
| 要求グループ | `######`（H6） | H4 |
| SR（下位要求） | `######`（H6） | H5 |
| 仕様グループ | `#######`（H7） | H6 |
| SP（仕様） | `#######`（H7） | リスト項目 |

問題は 2 点ある。

**(a) H7 は Markdown に存在しない。**
CommonMark の ATX 見出しは `#` 1〜6 個までであり、`####### 仕様グループ：...` および
`####### SP-001-001.001 ...` は**見出しとしてレンダリングされず、本文テキストとして表示される**。
`crs_md2excel.py` は自前の正規表現（`^####### (SP-\S+)\s+(.*)`）でパースしているため動作はするが、
**汎用 Markdown ツール（目次生成・アウトライン表示・Artifact 化・GitHub 表示）では階層が壊れる。**

**(b) 異なる要素種別が同一レベルに載っている。**
`要求グループ` と `SR` がともに H6、`仕様グループ` と `SP` がともに H7。
スキーマの「**見出しレベルが要素種別を一意に決める**」（MD定義 §2）という前提を満たさない。
現行パーサはプレフィクス（`SR-` / `SP-`）で区別しているが、
これは「レベル」ではなく「ID の綴り」に依存した判別であり、脆い。

**改善候補（推奨）**：仕様を見出しからリスト項目に変え、USDM ブロック全体を 1 レベル上げる。

```
現行                            改善案
## 2. USDM 要求仕様             ## 2. USDM 要求仕様
### 2.1 機能要求                ### ＜カテゴリ名＞          （= Category, H3）
#### カテゴリ：{名前}           #### UR-001 {タイトル}      （= Requirement, H4）
##### UR-001                    ##### ＜要求グループ名＞     （= RequirementGroup, H5）
###### 要求グループ：{名前}     ###### SR-001-001 {タイトル}（= SubRequirement, H6）
###### SR-001-001               **＜仕様グループ名＞**       （= SpecificationGroup, 太字行）
####### 仕様グループ：{名前}    - **SP-001-001.001**: ...    （= Specification, リスト）
####### SP-001-001.001
```

これにより H1〜H6 に収まり、レベルと要素種別が 1 対 1 になる。
機能要求／非機能要求の区別は `### 2.1 機能要求` という見出しではなく
**カテゴリ名（`＜機能要求＞` / `＜非機能要求＞`）で表す**のがスキーマの流儀であり、§9.4 の欠落も同時に解決する。

> **影響範囲**：`crs_md2excel.py`（`^##### (UR-\S+)` 等の正規表現とそのテスト）、
> `xddp.excel2md/SKILL.md`、`chd_sp_coverage.py`、TM の ID 照合、`artifact_lint.py`、
> 各スキル・エージェント定義中の CRS 構造記述。**大きな変更**であり、単独プランを立てるべき規模。
> 後方互換性は本リポジトリのポリシー上不要（CLAUDE.md「後方互換性ポリシー」）。

### 9.3 グループ名の ＜＞ 表記

スキーマは `Category.name` / `RequirementGroup.name` / `SpecificationGroup.name` すべてに
`pattern: ^＜.+＞$` を課している。現行 CRS は `要求グループ：{名前}` の形式で ＜＞ を使っていない。

→ **改善候補**：`＜{名前}＞` 形式に統一する。§9.2 の見直しと同時に実施すれば追加コストは小さい。

### 9.4 非機能要求の節が無い

現行テンプレートは `### 2.1 機能要求` のみで、非機能要求の節を持たない。
一方 `crs_md2excel.py` の docstring には `UR-NF-xxx`（後方互換）の記載があり、
**過去には非機能要求 ID の体系が存在した形跡がある**（現テンプレートには無い）。

スキーマ／小冊子の双方が非機能要求の記述を求めている
（`Category` は「要求をドメインや機能領域で分類する」、基礎編 2.2.9「非機能要求も記述する」）。

→ **改善候補**：カテゴリで表現する（`＜非機能要求＞` カテゴリ）。
CLAUDE.md「適用ドメインの中立性」に従い、性能・信頼性・リアルタイム性・リソース制約など
複数ドメインで意味を持つ分類にすること。

### 9.5 ステータスと verified は別軸

| | 現行 CRS `ステータス` | スキーマ `verified` |
|---|---|---|
| 意味 | **合意状態**（確定 / 要検討 / 懸念あり / 未決） | **進捗状態**（レビュー済 / 実装済 / テスト済） |
| 値域 | 4 値の排他 | 3 要素の boolean 配列（累積） |
| XDDP での既存対応物 | — | TM の `設計` / `実装` / `テスト` 列 |

両者は直交しており、どちらかに寄せる話ではない。

→ **改善候補**：TM の `設計`/`実装`/`テスト` 列を `verified` の 3 要素に対応付けて
機械変換できるようにする（`xddp_progress.py` と同様の決定的処理として実装可能）。
`ステータス` は XDDP 固有の拡張として維持し、Canonical JSON 出力時は
仕様文中の埋め込み（小冊子の【理由】方式に倣う）か、非準拠として明示する。

### 9.6 SP の「理由」が記録されない

スキーマは `Specification.reason` / `.explanation` を持つ。
現行 CRS の SP には `備考` と `懸念・検討事項` があるが、**理由に相当する欄が無い**。
工程 6 以降で「なぜこの仕様なのか」を辿れない。

→ **改善候補**：SP に `**理由：**` を任意欄として追加する。
小冊子は文中埋め込み（【理由】）を指示するが、スキーマは専用フィールドを持つため、
**構造化フィールドとして持つほうが両立しやすい**（Markdown 表現は文中埋め込みでも可）。

### 9.7 分割軸の記録先が無い

現行テンプレートの記述ルールに「要求の分割方法：時系列・構成・状態・共通」とあるが、
**どの分割軸を適用したかを記録する欄が無い**。適用結果が文書に残らないため、
レビュー時に「この分割は妥当か」を検証できない。

→ **改善候補**：要求グループの属性として分割軸を記録する
（要求グループは分割の結果そのものであるため、自然な記録先になる）。

```markdown
##### ＜{要求グループ名}＞

- **分割軸：** 時系列分割 / 構成分割 / 状態分割 / 共通分割
```

### 9.8 Canonical JSON 出力の検討

現行は CRS Markdown ⇄ Excel の直接変換（`xddp.md2excel` / `xddp.excel2md`）。
Canonical JSON を経由すれば、`ajv validate` による**構造の機械検証**が無料で手に入る。

ただし `additionalProperties: false` のため、
**Before/After・ステータス・懸念・検討事項・付記 A〜C は Canonical JSON に載せられない。**
選択肢は次の 3 つ。

| 案 | 内容 | トレードオフ |
|---|---|---|
| A | XDDP 拡張情報を仕様テキストに埋め込む（小冊子の【理由】方式に倣い【Before】【After】等） | スキーマ完全準拠。構造化された情報が文字列に潰れ、`chd_sp_coverage.py` 等の機械処理が困難になる |
| B | Canonical JSON を**出力専用**（外部連携・検証用）とし、正本は現行 Markdown のまま | 実装が小さい。往復（round-trip）できない |
| C | Canonical JSON を採用せず、スキーマの**構造ルールのみ**（階層・必須項目・グループ名・強制2層）を取り込む | コスト最小・即効性あり。外部ツール連携の利点は得られない |

→ **推奨は C を先に実施し、B を後続で検討する**。
C は §9.2〜9.7 の改善そのものであり、外部依存なく品質が上がる。

### 9.9 追加できる決定的チェック（機械検証候補）

CLAUDE.md「決定的処理はスクリプト・意味判定は LLM」に照らすと、
以下はスキーマ由来の**決定的チェック**として `artifact_lint.py` 相当に実装できる。
（意味判定側のチェックは [usdm-notation-rules.md](usdm-notation-rules.md) §11.4 を参照）

| # | チェック | 出典 |
|---|---|---|
| 1 | 見出しレベルが要素種別と 1 対 1 か（H7 の不在を含む） | MD定義 §2 |
| 2 | グループ名が `^＜.+＞$` にマッチするか | スキーマ `pattern` |
| 3 | 要求 ID が `^[A-Za-z][A-Za-z0-9_-]*$` にマッチするか | スキーマ `pattern` |
| 4 | UR に理由が空でないこと（`Requirement.required` に `reason`） | スキーマ |
| 5 | 各要求グループに SR が 1 つ以上あること | `minItems: 1` |
| 6 | 各仕様グループに SP が 1 つ以上あること | `minItems: 1` |
| 7 | 各 SR に仕様グループが 1 つ以上あること | `minItems: 1` |
| 8 | SR のネストが無いこと（要求 3 階層の禁止） | 構造 |
| 9 | 強制2層：要求グループ内の SR が 1 つの場合、その SR の理由・説明が空か | MD定義 §6 |
| 10 | ID が文書全体で一意か | スキーマ `description` |
| 11 | 文書にカテゴリが 1 つ以上あるか | `minItems: 1` |

### 9.10 1階層パターンの許容（運用改善）

スキーマは UR → 仕様グループ → SP の 1 階層パターンを正式に認めている（MD定義 §4）。
現行 CRS は UR → SR → SP を常に要求するため、
**小さな CR では上位要求の言い換えでしかない SR が量産される**リスクがある。

→ **改善候補**：次の使い分けを記述ルールに明記する。

| 状況 | パターン |
|---|---|
| 要求がシンプルで下位分割が不要 | 1 階層（UR → 仕様グループ → SP。SR を作らない） |
| 要求が複合的で分割が必要 | 2 階層（UR → 要求グループ → SR → 仕様グループ → SP） |
| 分割したいが下位要求が 1 つしか立たない | 強制2層（SR の理由・説明を空白にする） |

同一文書内での混在はスキーマ上も許容されている（MD定義 §4）。

## 11. 参考：スキーマ準拠チェックリスト

構造面の自己レビュー用。文の質については [usdm-notation-rules.md](usdm-notation-rules.md) §12 を併用すること。

### 文書全体
- [ ] カテゴリが 1 つ以上あるか
- [ ] すべてのグループ名が全角 ＜＞ で囲まれ、3 文字以上か
- [ ] ID が文書全体で一意か
- [ ] 見出しレベルと要素種別が 1 対 1 に対応しているか

### 要求（UR）
- [ ] ID が英字始まりか
- [ ] 理由が記入されているか（必須）
- [ ] 1階層／2階層のどちらのパターンかが明確か

### 要求グループ・下位要求（SR）
- [ ] 各要求グループに下位要求が 1 つ以上あるか
- [ ] 下位要求 ID が親要求 ID をプレフィクスとしているか
- [ ] 下位要求の下にさらに要求グループを作っていないか（3 階層禁止）
- [ ] 下位要求が 1 つだけの要求グループで、その理由・説明を空白にしたか（強制2層）

### 仕様グループ・仕様（SP）
- [ ] 各下位要求（1階層なら要求）に仕様グループが 1 つ以上あるか
- [ ] 各仕様グループに仕様が 1 つ以上あるか
- [ ] 仕様ラベル（進捗状態）が付与されているか
- [ ] 仕様の理由・説明が必要な箇所に記録されているか
