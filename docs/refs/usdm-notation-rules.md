## 1. USDM の全体像

### 1.1 USDM とは（基礎編 2.1.1 / p.4）

USDM は次の2つから成る。

1. 要求と仕様を階層化された構成に記述するための **『要求仕様書（様式・フォーマット）』**
2. 要求と仕様を表現する **『記述マナー（Describing Manner）』**

> つまり USDM は「表の書式」だけではなく「文章の書き方の作法」までを含む。
> 書式だけ真似ても効果が出ないのはこのため。

### 1.2 構成要素（補足編 1.2 / p.3）

USDM は基本的に **「要求」「理由」「仕様」** からなる。オプションとして **「説明」** がある。
実際のフォーマット上はこれに **「カテゴリ名（記号）」「要求ID」「仕様グループ」「仕様ID」
「仕様チェックボックス（仕様記号）」「備考欄」** が加わる（基礎編 2.1.1 / 4.1、補足編 1.3）。

### 1.3 使用ツール（補足編 1.1 / p.3、基礎編 4章冒頭 / p.18）

Microsoft Excel または同等の表計算ソフト（OpenOffice Calc 等）。バージョン指定はない。
形式手法のような厳密記法に対し、**一般的なツールで気軽に導入でき仕様漏れを防ぐ効果が高い**ことが
USDM の位置づけとされている（基礎編 2.1.2 / p.6）。

### 1.4 XDDP との関係（基礎編 2.1.2 / p.6）

- ソフトウェア開発の多くは新規開発ではなく既存システムの一部改修＝**派生開発**である。
- 派生開発における品質向上技法 **XDDP の中心成果物には USDM の記法が利用されている**。
- XDDP により「担当者がそのシステムを完全に把握しない状況でも、品質を守りながら
  最小の時間で開発を完了させる」ことができる。

## 2. フォーマット

### 2.1 パターン1：要求が1階層（補足編 1.3 / p.3、基礎編 4.1 / p.18）

要求に対して仕様が展開されるケース。行構成は上から順に：

| 行 | カテゴリ名（記号） | 要求 | （要求ID） | 内容 | 備考欄 |
|---|---|---|---|---|---|
| 1 | カテゴリ名 | 要求 | (要求ID) | ここに要求を記述します | |
| 2 | | | 理由 | 要求の背景や理由について記述します | |
| 3 | | | 説明 | 要求について必要に応じて説明してください。**仕様とはみなされません**。セルを広げて、図を貼ってもよいです | |
| 4 | | | ＜仕様グループ名＞ | 上記の要求に含まれるべき要求仕様を記述します。必要に応じて "＜ ＞" でグループ分けしてください | |
| 5.. | | □□□ | (仕様ID) | 仕様 | |
| n | | | ＜仕様グループ名＞ | （2つ目以降の仕様グループ） | |
| n+1.. | | □□□ | (仕様ID) | 仕様 | |

### 2.2 パターン2：要求が2階層（補足編 1.3 / p.4、基礎編 4.1 / p.18）

「1つの要求の範囲が大きいと判断した場合」に用いる。図の見出しに
**「要求がもう一段階層化されるケース。これ以上の階層化は避けたほうがよい」** と明記されている。

上位要求（要求・理由・説明）の下に、下位要求（要求・理由・説明）が入り、
**下位の要求ID は一段下げられる**。その下に仕様グループ・仕様が並ぶ。

パターン2 の図には、パターン1 にない2種のグループ記号が現れる 🔍：

| 記号 | 図中の注記 | 意味 |
|---|---|---|
| ＜＜仕様グループ名＞＞（二重山括弧）＝**主分割記号** | 「全体を通して共通の分割基準として決めます（オプション）。＜＜前提条件＞＞ ＜＜内部処理＞＞」 | 文書全体で共通に使う大分類。オプション扱い |
| ＜仕様グループ名＞（一重山括弧）＝**補助分割名** | 「主分割のなかに異なるテーマの仕様が混在する場合に補助分割記号を使って、純度の高い集合を作ります」 | 主分割の中をさらに純度の高い集合に切る小分類 |

### 2.3 記述例（基礎編 2.1.1 / p.5、4.1 / p.19、2.2.3 / p.9）

- 売上分析（URIAGE）：要求ID `URIAGE-01`、仕様ID `URIAGE-01.001` `URIAGE-01.101`
- 画像表示（Dpic）：要求ID `Dpic30`、仕様ID `Dpic30.10` `Dpic30.20` `Dpic30.30`
- WEBページ検索（SER）：要求ID `SER10`、仕様ID `SER10.10` `SER10.12` `SER10.14` `SER10.16`
- 顧客情報更新（Cim）：要求ID `Cim10`、仕様ID `Cim10.1` `Cim10.5` `Cim10.9`

いずれも **カテゴリ記号 + 要求番号 + 枝番** の形をとり、枝番は飛び番号になっている。

## 3. 要求の書き方

### 3.1 要求の定義（基礎編 2.2.3 / p.7、4.2 / p.20）

- 要求とは、**依頼者が求めている "ソフトウェアで実現して欲しい動作（処理）"** のこと。
- 記述するのは「ソフトウェア要求」である（補足編 2.1 / p.5）。
- 依頼者からの要求書やヒアリング結果には **"ユーザーの振る舞い" のみが記述され、
  "ソフトウェアの振る舞い" が隠れていることがある**ため、この時点で引き出して表現を調整する
  （基礎編 2.2.6 図 / p.12）。

### 3.2 要求が果たすべき3つの役割（基礎編 2.2.2 / p.7）

USDM が要求を書かせる理由は、**"仕様を漏れなく引き出させる"** ためである。
そのために要求に次の3つの役割を担わせる。要求を書くときはこの3つを満たすこと。

1. 要求されている **"ソフトウェアの振る舞い" を見せて、動きを感じさせる**役割
2. 要求されている **"範囲" を示す**役割
3. 要求に含まれる **全ての "動詞" と "目的語" を見せる**役割

### 3.3 振る舞いとして書く（基礎編 2.2.3 / p.7-8）

- 振る舞いの範囲は **「イベントに始まり、『入力処理』→『変換処理』→『出力処理』までの
  一連の処理を行って止まるまで」**。
- 1つ1つの動作は**具体的な動詞**で表現し、**目的語と動詞をセット**にする ＝ 「〜〜を〜〜する。」
- 一連の流れは目的語と動詞が交互に連鎖した形になる
  ＝ 「〜〜を〜〜して、〜〜を〜〜して、… 〜〜を〜〜する。」
- **必ず "動詞形" で書く**。名詞形にしない。

| | 例 | 評価 |
|---|---|---|
| 例1 | 平均値を**表示する** | ◯ 動詞形。動きを感じさせる |
| 例2 | 平均値の**表示** | ✗ 名詞形。動きを感じさせない |

要求を振る舞い・動詞形で書くことにより、**ユースケース図や PFD（Process Flow Diagram）
のような性質を要求仕様書に持たせる**ことができる（基礎編 2.2.3 / p.9）。

補足編 2.1（p.5）は、要求を「○○して、○○して、○○して、」の形で書いた後、
**行間に無理がなく自然な流れになっているかを確認する**ことを求めている。
（例：「ユーザーが画面のドロップダウンリストで店舗を指定したら、／指定された店舗の店舗コードを
取得し、／店舗コードをキーとして売上テーブルを検索し、／検索結果を編集し、／
当月分の売上一覧表を表示する。」の各行間で確認する）

### 3.4 範囲を示す（基礎編 2.2.4 / p.10）

要求にまつわる範囲には次の2つがある。

| 範囲 | 内容 | 例（「計測データを受信し、10件ごとに平均値を計算して、画面に表示する」） |
|---|---|---|
| 動作（処理）の範囲 | "何々の動作" から始まり "何々の動作" で終わるまで | "計測データを受信する" から "（平均値を）画面に表示する" まで |
| データの範囲 | 入力／出力データの上限値・下限値、正常値と異常値の基準など | （別例）天気予報＝1週間分、最初の2日は時間単位、その後5日は1日単位 |

### 3.5 動詞の数と分割（基礎編 4.2.2 / p.20-21、4.2.3 / p.21）

- 要求を文章化する際、**動詞をできる限り細かく出す**。
- その上で **動詞を時間軸にまとめ、5〜7個程度にまとめて下位要求とする**。
- **動詞が8個以上になると仕様が多すぎて見づらくなる。その場合は要求を分ける。**

分け方は2方向：

| 方向 | 方法 |
|---|---|
| 垂直方向 | 要求を階層化する（上位要求／下位要求） |
| 水平方向 | 別の要求とする |

階層化する場合は「要求をまとめるための要求（上位要求）を作り、その配下に分割対象の要求を含める」。
**下位要求にも理由をつける**（基礎編 4.2.3 / p.22）。

### 3.6 異常系も明確にする（基礎編 4.2.2 / p.21）

例：「絞込の結果、ヒット件数が0件になった場合、条件変更を促すメッセージを表示する」
のような異常系も要求として記載する。

### 3.7 要求の共通化（基礎編 4.2.8 / p.23）

細かいユーザーの誤入力などを毎回書くのではなく、**共通化できるものは
「共通として別の要求とする（水平方向）」**。

### 3.8 要求の分割基準 4パターン（基礎編 4.2.4 / p.22）

要求を分割する際は**基本的には時系列で書いていく**。USDM としては4パターンの分割基準を設けている。

| 分割 | 内容 |
|---|---|
| 時系列分割 | 時間軸に要求を分割する方法 |
| 構成分割 | 「機能別」や「構成別」で要求を分割する方法 |
| 状態分割 | 「状態」という概念で要求を分割する方法 |
| 共通分割 | 共通する機能を切り出して独立する方法 |

分割後、必要ならばカテゴリでグループ化する（基礎編 2.2.6 図 / p.12）。

### 3.9 粒度（基礎編 4.2.6 / p.22）

- 要求とは **仕様を束ねる範囲**のこと。
- 仕様に関する気づきを得るため、要求は十分小さい粒度にする。
- その粒度は **「関係者が認識を特定（Specify）できる」程度**とする。

### 3.10 仕様から要求を逆に導出・検証する（基礎編 4.2.7 / p.22-23）

- 仕様を記述後、**その仕様が正しく要求の配下にいるかという観点で検証**を行う。
- 結果、よりふさわしい要求の配下に仕様を移動する。
- ある仕様が既存のどの要求ともうまく対応しない場合、**よりふさわしい要求を新たに作る**。
- 仕様から要求を導出することは、**依頼者の要求がこうであるという新たな仮説を立てること**と言える。

### 3.11 機能要求だけでなく非機能要求も書く（基礎編 2.2.9 / p.13）

要求仕様書は「作るためのドキュメント」であり、**機能要求に加えて非機能要求（品質要求）も記述**して、
作るために必要となる情報を盛り込む。

また、**関係者に応じて記述の詳細度を変えてよい**。
（経験の浅い者が担当する部分は詳しく、ドメイン経験が豊富な者が担当する部分は
ポイントだけの必要最小限の記述で済ませることも可能）

## 4. 理由の書き方

### 4.1 位置づけ（基礎編 2.2.5 / p.11、4.3 / p.23）

依頼者が発する「要求」には、それが必要な「理由」（背景）がある。
**「理由」は「要求」に比べ変化することが少ない**。理由は要求の一部といえるが、USDM では欄を分ける。

理由を押さえることで得られるもの：

- 「要求」の意味が理解しやすくなる
- 依頼者と作業者の「要求」に対する認識のズレを調整できる
- 「要求」に根拠がないことに気付ける
- 「仕様」の引き出しや設計方法に配慮できることがある
- 依頼者も気が付いていない要求を引き出せることがある

### 4.2 書き方（基礎編 4.3 / p.23、4.3.1 / p.23）

- 依頼者が求める要求が、**どういう背景のもとで生じたか**を記述する。
- 突き詰めると「儲かりたいから」になるが、それでは理由にならない。
  できる限り **「要求に特有の理由」「依頼者が重きをおいているポイント」**を押さえる。
- 「現在までどうやったのか？ これからどうしたいのか？」「実際に使うユーザーがどういう状況で
  その機能を使うのか」を把握する。
- 「どうしてこの機能が必要ですか？」と直接聞いても明確な理由が返らないことが多い。**聞き方を工夫する**。

### 4.3 タイミング（補足編 2.2 / p.5、3.2 / p.10）

- 理由が明確になっていなければ**後で記述してもかまわない**。
- ただし **終盤は記述すること**。
- 記述後、**要求と整合性が取れているか確認**する。
- **理由が思いつかない場合は、その要求の存在自体を検討する**。

## 5. 説明の書き方

（基礎編 4.1 表 / p.19、補足編 2.5 / p.8、3.3 / p.10）

- 「要求」および「理由」に対しての**補足**を記述する。オプション項目。
- **実装に関わらないような内容に限る。**
- 説明欄の内容は **仕様とはみなされない**。
- セルを広げて図を貼ってもよい。
- 記述例：「実装時期は、10月ごろ。」

**禁止：**
- ここに「要求」や「仕様」を書き込まない。
- 自信がないからといって、**製造する際に必要な仕様やロジックを説明欄に書かない**。
  その場合は「仕様」として記載する。

## 6. 仕様グループの書き方

（基礎編 4.4.2 / p.24、補足編 2.3 / p.6、基礎編 メリット⑤ / p.16）

- **要求のうち1つの「動詞」と、付随する「目的語」に着目して仕様グループを定義する。**
  分割されている場合は下位要求の動詞から設定する。
- 例：要求文中の「検索条件を**プリセットする**」→ ＜検索条件のプリセット＞
- 補足編 2.3 の図では、要求文の5つの動詞（指定したら／取得し／検索し／編集し／表示する）が
  そのまま5つの仕様グループ（＜店舗（ドロップダウンリストの指定値）の受け取り＞／
  ＜店舗コードの取得＞／＜売上テーブルの検索＞／＜検索データの編集＞／＜売上一覧表の表示＞）
  に1対1で対応している。
- **仕様グループを見て漏れや重複を見つけた場合は、要求を見直して仕様グループを記述し直す。
  逆に仕様グループを見直してから要求を見直してもよい。**

効果（基礎編 メリット⑤ / p.16）：
仕様グループというスコープの配下に仕様を記載することで**思考のフォーカスを絞り込むことができ、
容易に仕様が書きやすくなる。重複や漏れも見つけやすくなる。**

## 7. 仕様の書き方

### 7.1 仕様とは（基礎編 2.2.7 / p.13、4.4.1 / p.24）

> 仕様とは、「明確にされた動作（動詞と目的語）の1つ1つに対して、
> 具体的な "制約" や "処理内容" や "選択肢" などを記述したもの」（基礎編 2.2.7）

仕様とは、要求に含まれる動詞を具体的に表現したもの。次の条件を満たす粒度で要求を具体化する。

| 条件 | 説明 |
|---|---|
| 要求から導出される | **すべての仕様は、要求に属する** |
| 設計をイメージできる | 仕様毎に**作業タスクと作業時間が導出できる** |
| 検証をイメージできる | 仕様を**テストする手段が導出できる** |

仕様は「設計の概要」「ソースを書く際の論理的なまとまり」と捉える（基礎編 4.4 / p.24）。

### 7.2 仕様化の観点（基礎編 2.2.7 / p.13）

それぞれの動作（動詞と目的語）について次の観点で仕様を引き出す。

- 何ができれば良いのか？
- どのような状況で動けば良いのか？
- 結果はどのような形で返せば良いのか？

### 7.3 粒度（基礎編 4.4.3 / p.24-25、補足編 2.4 / p.7）

- 仕様は **何を作るか（What）** を定義する。最終的に**ソースコードに対応させることができる**。
- **「コード（実現方法）がイメージできる」ほど具体的に書く**（補足編 2.4）。
- 依頼者と合意するため、**依頼者が理解できる粒度**にする。

判断基準：

1. 依頼者が理解できること
2. 作業者が大まかな作業の流れをイメージできること
3. 要求から仕様に落とす際のモレが生じないこと

- **1項目は1つの内容（細目）で記述する。** 細目にある「動詞」と「目的語」に着目し、
  関係者の間で同じイメージを持てるかを確認する。
- 依頼者と作業者の認識が合っている場合は粗く書いてよい。
  作業者が新参ベンダーで認識が合っていない場合は細かく書く。

### 7.4 仕様に対する理由・説明（補足編 2.4 / p.7、3.5 / p.11）

「仕様」に対する「理由」や「説明」がある場合、**専用の欄を作らず、
「仕様」の文章中に埋め込む**。

```
店舗コードをキーに、次の条件で、売上テーブルを検索する。
　・状態コードが"売上"および"売掛"のもの
　・売上日が当月のもの
　・売上日の昇順
【理由】売上テーブルの検索は現状システムと同じにしたいため
【説明】売上テーブルの月ごとの件数は、約1000件。
```

### 7.5 図表の使用（補足編 2.4 / p.8、3.4 / p.10、基礎編 4.5.3 / p.26）

- 仕様欄にディシジョンテーブル（補足編本文の「テンジョンテーブル」は誤記と思われる）や
  PAD などの図を記述してよい。
- **コード値や状態などを記載する場合は、マトリックスや PAD などの図を記載する**（補足編 3.4）。
- フローチャートやディシジョンテーブルなど、**テスト工程で条件の分類を行う時の書き方を
  流用するとよい**（基礎編 4.5.3）。

### 7.6 仕様チェックボックス（基礎編 3.1① / p.14、フォーマット図）

仕様行の左には □□□ のチェックボックス（仕様記号）がある。
USDM は「要求」「仕様」を一覧表として扱うため、**USDM 自体をチェックリストとして使用でき、
仕様どおりにプログラムが実装されているかを確認できる**。

## 8. ID の付与

### 8.1 目的（基礎編 4.2.5 / p.22、4.4.4 / p.25）

要求・仕様それぞれに ID を振る。

- 依頼者とやりとりする際、**「話の対象が明確になる」「類似の項目との誤解もなくなる」**
- **トレーサビリティを確保しやすくなる**

### 8.2 採番ルール（補足編 2.6 / p.9）

- 要求および仕様を記述し終わった**後**に、要求ID・仕様IDを記述する。
- ID は**略称や数字を使ってもかまわない**。
- **仕様ID ＝ 要求ID + 枝番**
- **仕様IDの枝番は飛び番号にしたほうが、追加がしやすくなる。**

例：

```
要求ID： URIAGE-01
仕様ID： URIAGE-01-0001
```

## 9. 禁止事項・注意すべき表現

### 9.1 禁止事項一覧（補足編 3章 / p.10-11）

| 対象 | 禁止事項 |
|---|---|
| 要求 | **階層は二階層まで。三階層以上は作成しない**（階層が深くなると理解しにくい）。＜＞でグループ化するなどの工夫をする |
| 要求 | 説明文などの**要求以外のものを要求欄に書かない** |
| 理由 | 当初は書かなくてもよいが**終盤は記述する**。記述後、要求との整合性を確認する。理由が思いつかない場合は要求の存在を検討する |
| 説明 | **「要求」や「仕様」を書き込まない** |
| 説明 | 自信がないからといって、**製造する際に必要な仕様やロジックを書かない**（仕様として記載する） |
| 仕様 | **コーディングできないほど抽象化したものを書かない**（この場合は要求として再考する） |
| 仕様 | 仕様欄に**「理由」や「要求」を書かない** |
| 仕様 | コード値や状態を記載する場合は**マトリックスや PAD などの図を記載する** |
| 仕様 | **コピペして書かない**（せめて「〃」「々」「同上」などを使う） |
| 仕様 | **否定表現は避ける** |
| その他 | **USDM の構成および書き方を変更しない** |
| その他 | **「要求」「理由」「説明」「仕様」「仕様グループ」以外の項目を追加しない** |
| その他 | 仕様に対する理由・説明は、仕様の文章中に【理由】【説明】として追加する |

### 9.2 USDM が名付けた「注意すべき表現」（基礎編 4.5.3〜4.5.5 / p.26-27、5.2 / p.28）

基礎編 5.2 は、**まずこの3つを修正して無くすことから始めるとよい**としている。

#### (a) 「等」「etc」（基礎編 4.5.5）

- セルが縦に長くなる・見栄えが悪いという理由で「等」「etc」で仕様のパターンを止めない。
- **現タイミングで確定できることは、すべて書く。**
- 表示幅が狭いなら複数セルを使う、別資料にまとめて参照を記載するなど工夫して書き切る。
- 現タイミングで未確定であれば、**仕様の合意時期を決めて記載する**（＝「T.B.D.」で放置しない）。

#### (b) 否定表現（基礎編 4.5.4）

- 例：「受信環境が Wifi（無線 LAN）の場合は、バックアップを有効にしない。」
- 実装時は IF 文になる。IF 文ということは**すべての場合分けを考える必要がある**。
  （有線 LAN の場合は？ パケット通信の場合は？ 通信帯域が遅い場合は？）
- 文章に「もし…の場合は」があれば、**「else は何？」と考える癖をつける**。
- この「隠れた IF 文」は **文章の末尾が「〜しない」という場合に生じやすい**。
  そのため USDM ではこれを「否定表現」とよび、注意すべき表現としている。

#### (c) ペースト作文（基礎編 4.5.3）

- 一部だけ仕様が違う場合に、文章をコピペで作り一部修正という形で書くと**差異がわかりにくくなる**。
- 読み手に伝わりづらい注意すべき表現として、USDM では「ペースト作文」と呼び避ける。
- 仕様欄に表や図を追加して、見やすい形にする。

### 9.3 要求の範囲外の仕様（基礎編 メリット④ / p.16）

要求の配下に仕様を記述するため、**要求の範囲からはずれた仕様はレビュー時に違和感があり
簡単に見つけられる**。
図の例では、要求「画面で性別を選択させ、選択時に性別コードを決定し、DB格納にする。」の配下に
「ついでに音楽を流す。」という仕様が混入している。この場合は**削除するか、
別途その仕様を満たす要求を立てる**必要がある。

## 10. プロセス上のルール

### 10.1 要求の引き出しと仕様化を分ける（基礎編 4.5.1 / p.26）

**仕様グループの作成までを「要求の引き出し」作業とし、仕様化と分ける**ことが推奨される。

分ける理由は**分業のため**。

| 作業 | 性質 |
|---|---|
| 要求の引き出し | 本来的には依頼者の作業。依頼者やその背景に眠っている要求を探る作業は作業者だけで完結できない。**本質的に属人的で、人を増やしても効果が上がらず、生産性が読めない** |
| 仕様化 | 要求が適切に表現されてさえいれば、**組織のやり方に合わせた解決策を過去の経験ないし類推から導出できる**。仕様数と作業時間を記録することで生産性を把握でき、作業工数を見積できるようになる |

### 10.2 仕様化の担当者（基礎編 4.5.2 / p.26）

**仕様化の作業者は、次工程の設計担当とする。**
異なる担当をつける場合、「要求仕様書を確かに理解できた」という引継を保証する仕掛けが必要になる。

### 10.3 設計前に仕様を出し切る（基礎編 2.2.8 / p.13、5.1 / p.28）

- 設計作業の手戻りを解消するには、**設計作業を始める前に**要求をもとに考えられる仕様を
  USDM のフォーマットでドキュメントにして設計作業に引き継ぐ。
- **設計作業と仕様化作業を明確に区別する。**
  設計工程で仕様化するよりも要求仕様書作成の中で仕様化したほうが手戻りを防げ、
  トータル工数が短くなる。

### 10.4 USDM のメリット（基礎編 3.1 / p.14-17、要約）

| # | メリット |
|---|---|
| ① | 要求・仕様が一覧形式で記載されるため「漏れ」「重複」に気づきやすい（MECE）。仕様が USDM 一つにまとまるので整合性を保持できる |
| ② | 「要求」「仕様」「理由」「説明」を分けて記載するため内容が明確になり、トレーサビリティがとれる |
| ③ | 「理由」を記載するため要求・仕様の根拠がわかりやすい（So What / Why So） |
| ④ | 要求の配下に仕様を記述するため、要求の範囲に収まる仕様を作成でき、範囲外の仕様を発見しやすい |
| ⑤ | 要求の1つ1つの動詞を仕様グループとするため、思考のフォーカスを絞り込め、仕様が書きやすい |
| ⑥ | 仕様から曖昧性を排除し具体的に記述するため、迷うことなく実装できる |
| ⑦ | 要求を振る舞いとして記述するため、「要求の動き（順序性）」と「範囲」を持たせられる |

### 10.5 導入の糸口（基礎編 5.2 / p.28-29）

いきなり全面入れ替えはハードルが高い。まずは自分だけで書いてみる。

1. 完了したプロジェクトの設計資料から自分の担当部分の要求・仕様を一部抜粋し、USDM で清書してみる
   - 要求を振る舞いで表現する
   - 要求の中の動詞をすべて表現し、それを分割して表現する
   - 分割された要求の下に仕様を配置する
2. 要求と仕様を見比べて、仕様にモレがないか・曖昧な表現がないかを確認する
3. 「等」「etc」／否定表現／ペースト作文 の3つを修正して無くすことから始める

### 11.2 「三階層以上禁止」との整合（重要）

補足編 3.1 の「階層は二階層まで」は **要求の階層**についての規定であり、仕様は含まない。
したがって現行の **UR（上位要求）→ SR（下位要求）→ SP（仕様）** は
USDM パターン2 そのものであり、**規定に違反していない**。

ただしこの解釈からは次の制約が導かれる：

- **SR の下にさらに SR を作ってはならない**（要求が三階層になるため）
- 範囲が大きすぎる場合は、垂直方向の追加階層ではなく **水平方向の別 UR に分ける**（基礎編 4.2.2）

→ **改善候補**：現行テンプレートの記述ルールにこの制約が明記されていない。
「SR のネストは禁止。範囲超過時は UR を分割する」を追記すると、AI が階層を掘り下げるのを抑止できる。

### 11.3 現行と食い違う可能性がある記述

#### (a) 否定表現の扱い

現行テンプレートの記述ルールは
「受け身表現（〜される、〜されない、〜が存在しない）は禁止。能動表現（〜する、**〜しない**）を使う。」
と書いており、`〜しない` を**推奨側**に置いている。

一方 USDM は `〜しない` を「否定表現」と呼び、**注意すべき表現として避ける**対象としている
（補足編 3.4、基礎編 4.5.4）。理由は「隠れた IF 文」が生じ、else 側の場合分けが漏れるため。

両者は目的が異なる（現行＝主体の明確化／USDM＝条件網羅）。矛盾を解消する案：

> 能動表現を使う。ただし述語が「〜しない」となる場合は、
> **else 側（それ以外の条件）の仕様を必ず併記する**か、
> ディシジョンテーブルで全条件を網羅すること。

#### (b) 仕様に対する理由

USDM は仕様の理由・説明を **仕様文中に【理由】【説明】として埋め込む**（補足編 2.4、3.5）。
現行テンプレートの SP には `備考` と `懸念・検討事項` があるが、**【理由】に相当する欄・記法がない**。
SP レベルの設計判断根拠が残らないため、工程6以降で「なぜこの仕様か」を辿れない懸念がある。

→ **改善候補**：SP の `備考` の用法として【理由】記法を明示する、または `理由` を任意欄として追加する。

#### (c) 非機能要求

基礎編 2.2.9 は「機能要求に加えて非機能要求（品質要求）も記述する」と明記する。
現行テンプレートには **`### 2.1 機能要求` しかなく、非機能要求の節が存在しない**。

→ **改善候補**：`### 2.2 非機能要求` を追加する。
ドメイン中立性の観点（CLAUDE.md「適用ドメインの中立性」）から、
性能・信頼性・リアルタイム性・リソース制約など複数ドメインで意味を持つ分類にすること。

#### (d) 仕様ID の飛び番号

補足編 2.6 は「仕様IDの枝番は飛び番号にしたほうが、追加がしやすくなる」とし、
PDF の全例（`Cim10.1/10.5/10.9`、`SER10.10/.12/.14/.16`、`Dpic30.10/.20/.30`）が飛び番号である。
現行は `SP-001-001.001` からの連番であり、**工程4b/6b/10c のフィードバックで仕様を挿入する際に
番号が詰まる**。

→ **改善候補**：枝番を 010, 020, 030… 刻みにする。
ただし `crs_md2excel.py` / `chd_sp_coverage.py` / TM の ID 照合に影響するため、
変更する場合は正規表現・テストの同時修正が必要（後方互換性は本リポジトリのポリシー上不要）。

### 11.5 UR / SR / SP の分類判断フロー（提案）

出典の定義から、分類の判断は次の順で行える。

```
入力文を1つ取る
 ├─ 「作るために必要な具体度」がなく、"何をしたいか" の願望か？
 │    → UR（ユーザ要求）。理由を必須で付ける
 ├─ ソフトウェアの振る舞い（イベント→入力→変換→出力）を動詞連鎖で表せるか？
 │    → SR（システム要求）
 │      ├─ 動詞が 8 個以上 → 分割する
 │      │    ├─ 時間軸で切れる → 時系列分割
 │      │    ├─ 機能・構成で切れる → 構成分割
 │      │    ├─ 状態で切れる → 状態分割
 │      │    └─ 他要求と共通 → 共通分割（水平方向の別要求へ）
 │      └─ 動詞 5〜7 個 → その各動詞＋目的語が仕様グループになる
 └─ 特定の動詞1つに対する制約・処理内容・選択肢か？
      → SP（仕様）。所属先は「その動詞を含む SR の、その動詞の仕様グループ」
        ├─ どの SR にも収まらない → よりふさわしい SR/UR を新設する（基礎編 4.2.7）
        └─ コードがイメージできない抽象度 → 仕様ではなく要求として再考する（補足編 3.4）
```

判定に迷う典型例（出典からの導出）：

| 入力 | 分類 | 根拠 |
|---|---|---|
| 「営業部の○○部長からの要望です」 | UR の**説明** | 実装に関わらない補足（補足編 2.5） |
| 「名前からでは性別を判断できないため」 | UR/SR の**理由** | 要求の背景（基礎編 4.3） |
| 「売上テーブルの月ごとの件数は約1000件」 | SP 文中の**【説明】** | 仕様に対する補足（補足編 2.4） |
| 「実装時期は10月ごろ」 | UR の**説明** | 実装に関わらない補足（補足編 2.5、図の実例） |
| 「男ならば"1"とする／女ならば"2"とする／不明ならば"0"とする」 | 1つの **SP**（選択肢を図・箇条書きで内包） | 「1項目は1つの内容」＋コード値は図表化（基礎編 4.4.3、補足編 3.4） |
| 「絞込結果が0件の場合、条件変更を促すメッセージを表示する」 | **SR**（異常系も要求として書く） | 基礎編 4.2.2 |

### 11.6 出典に無いため独自判断が必要な領域

以下は本リポジトリで既に運用しているが、**出典2冊に根拠がない**。
「USDM に準拠している」と説明する際は区別すること。

- **Before / After 対比**（派生開発向けの XDDP 拡張）
- **ステータス**（確定 / 🔍 要検討 / ⚠️ 懸念あり / ❓ 未決）
- **懸念・検討事項** 欄
- **付記A スコープ外事項 / 付記B 前提条件・実装参考情報**
  （補足編 3.5 の「『要求』『理由』『説明』『仕様』『仕様グループ』以外の項目を追加しないでください」に
  形式上は抵触する。ただし本文中の欄ではなく付記であり、AI 運用上のフェイルセーフという
  別目的を持つため、意図的な逸脱として記録しておくのが妥当と考える）
- **UR/SR/SP という記号体系そのもの**（USDM は「要求／仕様」の2区分のみ。
  UR/SR の2階層化は USDM パターン2 に対応するが、`UR-` `SR-` `SP-` という prefix は独自）
