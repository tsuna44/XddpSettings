## 1. 背景と目的

工程4a（specout）の波紋調査（Discovery BFS）は、`specout_bfs.py` による grep と、LLM による hit 行の分類
（`xddp-specout-classifier-agent`）を組み合わせている。LLM が判定する行が多く、時間がかかっていた。

本調査の問い:

1. LLM の判定を最小限に、または無くせるか。
2. 静的スライス（Static Program Slicing）を Python で実装できるか。
3. それを使うと、波紋調査の質（探索範囲と、影響箇所の見つけやすさ）はどう変わるか。

## 2. 出発点の分析: LLM 分類は何をしているか

u1-eval（frr・redis を題材にした評価用ワークスペース）にある過去3 CR の LLM 分類結果
（`04_specout/{repo}/wave-*-chunk-*-class.json`）を調べた。

### 2.1 判定の中身はほぼ機械的

標準ライブラリだけの簡易スクリプト（試作の `stdlib_c_classify.py`）で、次の2つだけを判定させた。

- コメント・文字列中の偽陽性
- そのヒット行を含む関数（呼び出し元として次の波へ渡す名前）

LLM の判定と「次の波に渡すシンボル」を比べた結果:

| CR | 判定行数 | 一致 | 不一致の内容 |
|---|---|---|---|
| frr CR-2026-801 | 82 | 81 | 1件は **LLM の誤り**（`isis_route.c:857` を別の関数の中と判定していた） |
| frr CR-2026-802 | 92 | 90 | `goto install;`（ラベル名）とプロトタイプ宣言の引数名。どちらも規則を足せば決定的に扱える |
| redis CR-2026-819 | 5 | 5 | — |

CR-2026-802 は 92行中 70行が偽陽性で、シードが `replay`・`route` などの一般語だったことが原因。
LLM の意味判定が本当に必要だった行はごく一部だった。

### 2.2 遅さの主因は1波あたりの固定費

`04_specout/{repo}/metrics.jsonl` の `classify_wall_ms` は、ヒット数によらず1波あたり約1分だった
（redis: 2ヒットで87.7秒、3ヒットで62.6秒。frr: 23〜31ヒットで57〜59秒）。
行数よりも、サブエージェントの起動そのもののコストが大きい。
**LLM 呼び出しを減らすより、波のループから無くす方が効く。**

## 3. 静的スライスとは

- **前方スライス:** 変更箇所から「影響を受ける文」をたどる。波紋調査そのもの。
- **後方スライス:** ある文に「影響を与える文」をたどる。原因の追跡に使う。

アルゴリズムは「依存グラフ（データ依存＋制御依存）を作り、到達可能な文を集める」もので、Python で実装できる。
難しいのは対象言語ごとの前処理である。構文解析、ポインタの別名解析、関数をまたぐ呼び出し文脈の扱いが該当する。

参考文献（本調査では原文を確認していない）: Weiser "Program Slicing"（ICSE 1981 / IEEE TSE 1984）、
Horwitz, Reps, Binkley "Interprocedural Slicing Using Dependence Graphs"（PLDI 1988 / TOPLAS 1990）。

今の BFS は、関数名・変数名の単位で粗く行う、名前ベースの前方スライスとみなせる。
データ依存を名前の文字列一致で近似し、別名解析はしていない。

## 4. 試作の設計

tree-sitter で C / C++ / Python を構文解析し、grep のヒット行ごとに**関数内**で保守的なスライスを行う。
影響が関数の外へ出る経路（出口）を判定し、それによって次の波で何を追うかを決める。

| 出口 | 意味 | 次の波で追うもの |
|---|---|---|
| `return` / `exception` | 影響を受けた return・yield・throw・raise | 呼び出し元（関数名） |
| `out` | ポインタ/参照引数・self/this 経由の書き込み | 呼び出し元 |
| `heap` / `state` / `unknown` / `closure` | 出所不明のポインタ経由・static ローカル・解析不能な呼び出し・外側関数のローカル | 呼び出し元（安全側） |
| `global` | グローバル変数（構造体はフィールド単位。例 `server.dirty`）への書き込み | その変数を読む箇所 |
| なし | 影響が関数内で閉じる | 追わない（伝播を止める） |

- 関数内の解析は、流れ依存性を簡易に近似している。データ依存・制御依存・早期 return・ループ・
  if/else の排他・return で終わるブロックを考慮する。
- 関数をまたぐ部分は、今の BFS と同じく名前で grep する。呼び出し先については、リポジトリ全体の定義索引から
  副作用の要約（戻り値・出力引数・書き込むグローバル）を再帰的に求める（深さ3まで）。
- C の構文を作るループマクロ（`for (ALL_LIST_ELEMENTS_RO(...))`、`frr_each(...) {`）は、
  構文解析の前に `for (;__xddp_iter(...);)` へ書き換える（行番号は保つ）。

## 5. 3つの方式とシードの扱い

### 5.1 次の波で何を追うか（方式）

どれも、ヒットした行ごとに「関数の中で影響がどこへ届くか」を判定するところまでは同じ。
違うのは、影響が関数の外へ出たときに次の波で何を追うか。

| 影響の出口 | baseline（今の LLM の振る舞い） | 剪定フィルタ | 完全スライス |
|---|---|---|---|
| 影響が関数内で閉じる | 呼び出し元を追う | **追わない（止める）** | **追わない（止める）** |
| 戻り値・出力引数・ポインタ経由の書き込み | 呼び出し元を追う | 呼び出し元を追う | 呼び出し元を追う |
| グローバル変数への書き込み | 呼び出し元を追う | 呼び出し元を追う | **その変数を読む箇所を追う** |

- **baseline:** ヒットがあれば無条件に呼び出し元へ広げる。呼び出しの連鎖を上へたどるだけ。
- **剪定フィルタ:** baseline と同じ範囲の中で、影響が関数内で閉じる箇所の伝播を止める。baseline より狭くなるだけ。
- **完全スライス:** 伝播を止める点は剪定フィルタと同じ。加えて、グローバル変数への書き込みを見つけると、
  その変数を読んでいる箇所をリポジトリ全体から探す。呼び出し関係では直接つながっていない関数にも届く。

例:

```c
void A() { g_count = SEED; }      // シードの影響がグローバル g_count へ書き込まれる
void B() { if (g_count > 3) ... } // A とは呼び出し関係がない
```

baseline と剪定フィルタは A の呼び出し元をたどるだけで、B には届かない。完全スライスは `g_count` を読む B を見つける。

### 5.2 シード関数について何が変わったとみなすか

方式とは別の軸の設定。

| 設定 | 意味 |
|---|---|
| interface | シードの変更は戻り値・出力引数にだけ現れるとみなす（最も狭い。安全側でない） |
| computed | シードが書きうる副作用（グローバルへの書き込みを含む）がすべて変わるとみなす。シードが書くグローバルの読み手も最初の波から追う |
| unknown | 何が変わるか不明として、必ず呼び出し元へ伝播させる |

## 6. 評価結果

正解は u1-eval の `truth/*.txt`（修正 PR で変更されたソースファイル）。これは代用指標であり、
「影響する機能」そのものではない（§7.1 参照）。
baseline は LLM の実測と一致することを確認済み（redis CR-819 で第0波2ヒット・第1波3ヒット）。
数値の出典は試作の `results/eval-final.txt` と `results/eval-full-slice-waves.txt`。
本節は、検索に `git grep` を使い、ヒット上限で波全体を打ち切っていた時点の結果である。
索引による検索と1波内の予算を入れた後の、機能単位の評価は §10 を参照。

### 6.1 剪定フィルタ（unknown）: 今の BFS の範囲内での削減

| シナリオ | baseline（確定ファイル/関数） | 剪定フィルタ（unknown） | 正解再現 |
|---|---|---|---|
| frr・CR-801 のシード | 82 / 127 | 45 / 89 | 3/8 → 3/8 |
| frr・Issue のシード | 89 / 179 | 31 / 84 | 5/8 → 5/8 |
| redis・CR-819 のシード | 2 / 2 | 2 / 2 | 1/7 → 1/7 |
| redis・Issue のシード | 79 / 873 | 78 / 855 | 7/7 → 7/7 |

interface にするとさらに狭くなるが、正解を落とした（frr・Issue 5/8→4/8、redis・Issue 7/7→6/7）。

### 6.2 完全スライス（computed）: 波ごとの累積

上限は10波・1波10,000ヒット。

| シナリオ | 方式 | 波ごとの累積確定ファイル（正解再現） |
|---|---|---|
| frr・CR-801 | baseline | 第0波 4（3/8）… 第9波 82（3/8） |
| frr・CR-801 | 完全・computed | 第0〜6波 4〜31（3/8）、第7波 372（5/8）、第8波 630（7/8）、第9波で打ち切り |
| frr・Issue | baseline | 第0波 5（4/8）、第2波 63（5/8）… 第9波 89（5/8） |
| frr・Issue | 完全・computed | **第0波 31（4/8・主要ファイル4/4）**、第1波で打ち切り（frontier 275） |
| redis・CR-819 | baseline | 第1波 2（1/7）で収束 |
| redis・CR-819 | 完全・computed | 第0波 29（5/7）、**第1波 69（7/7）**、第9波 149（7/7） |
| redis・Issue | baseline | 第0波 6（5/7）、第4波 39（7/7）… 第9波 79（7/7） |
| redis・Issue | 完全（無視リストあり） | 149（7/7）（波ごとの記録なし） |

- redis・CR-819 は、今の BFS がたどらないグローバル経由の流れ（シードが書く `server.also_propagate` 等の読み手）
  をたどって、修正対象のファイル群に届いた。
- frr・Issue は、第0波だけで主要ファイル（bgp・isis・rip の zebra 連携）4/4 がそろった。
- frr・CR-801 はシードが IS-IS だけのため、他の機能に届くのは探索が爆発する第7〜8波だった。

### 6.3 速度

- LLM を使わずに全ヒットを判定できた（解析が例外で失敗したヒットは0件）。
- 1ヒットの判定は2〜85ms。呼び出し先の要約を新たに計算するほど遅い。10,000ヒットの波は最悪で約10分
  （redis の実測は566秒）。
- frr・CR-801 の完全スライスは全体で4,141秒かかったが、各波の合計は292秒。差の約3,850秒は、打ち切った
  第9波の検索に使われていた（§8 の課題6）。

## 7. 決まった方針と要求（2026-10-03 のユーザー判断）

### 7.1 波紋調査の目的

**影響する機能が分かれば十分で、調べきる必要はない。** 実装方法や評価が必要なパターンは、影響する機能から導ける。

このため評価の物差しは、ファイル単位の再現率ではなく**「浅い波のうちに影響する機能が出そろうか」**とする。
波数やヒット数の上限による打ち切りは許容される。

### 7.2 要求

| # | 要求 | 補足 |
|---|---|---|
| R1 | **完全・computed を採用する** | グローバル経由の影響を追い、シードの副作用もすべて変化とみなす |
| R2 | **波数の上限を設定ファイルに書き、ケースごとに人が制御できる** | 2波では足りない可能性が高い（ユーザー所感）。既定値は未決 |
| R3 | **人のチェック用に、波紋調査の全結果を残す** | 全ヒット・全判定・伝播経路 |
| R4 | **LLM がまとめた内容も出す** | 人が全結果を読む前の入口 |
| R5 | **打ち切ったことが人に分かる** | どの波で、何の上限で打ち切ったか、未処理のシンボルは何か |
| R6 | **影響範囲から修正方法を検討する LLM（工程5以降）向けの概要を出す** | 全結果は大きすぎて入力にできないため、影響する機能の単位でまとめる |

R3/R4/R6 から、出力は2層になる。**人が確認する全結果**と、**LLM が扱える概要**である。

### 7.3 既存の仕組みとの関係（確認済みの事実）

- **波数の上限:** すでに `SPECOUT_MAX_WAVE_DEPTH`（既定 `10`）がある。超えると探索を終了せず一時停止し
  （`paused-at-limit`）、人が継続パスを選ぶ（A: frontier を剪定して再開／B: 残りのモジュールを一括記録して完了／
  C: 残りをスコープ外として根拠を記録して完了）。
  出典: `ClaudeCode/.claude/skills/xddp-01-init/templates/xddp.config.md` の「SPECOUT_MAX_WAVE_DEPTH」節。
  R2 はこのキーの延長で満たせる可能性がある。
- **全結果の記録:** 今の `discovery-log.md` は、全ヒットを行ID・検索シンボル・ファイル・含む関数・伝播種別・
  確信度・派生元のテーブルとして記録している。フィルタで除外した行も「## フィルタ除外一覧」に全件記録される。
  R3 はこれにスライスの判定（出口の種類）を足す形が考えられる。
- **伝播経路の可視化:** `plans/PLAN-20260829-specout-ripple-trace-graph.md`（承認待ち）が、波紋の構造化データ
  （`ripple-edges.jsonl`）からグラフ（`ripple-graph.md`）と階層表（`ripple-tree.md`）を自動生成する設計を持つ。
  R3 の「伝播経路」と重なる。
- **LLM の概要:** 今の SPO（`xddp-specout-document-agent` が生成するモジュール別の資料）が R4/R6 の受け皿になりうる。

## 10. 追加評価: 機能（モジュール）単位（2026-10-03）

### 10.1 試作の改良

- **検索を識別子の索引に置き換えた。** 起動時にリポジトリ全体の識別子（と `root.field` の組）の転置インデックスを作り、
  各波は辞書を引くだけにした。作成は frr（約96万行）で1.8秒、redis で0.5秒。プロファイルでは、それまで1波の約97%が
  `git grep` の待ち時間だった（497秒中483秒）。
- **1波内の優先順位つき予算。** 先にシンボルごとのヒット数を数え、関数シンボル（呼び出し関係の伝播）→ 値シンボル
  （グローバルの読み手）の順に、各々ヒットの少ない順で予算内だけ処理する。予算に入らなかったシンボルは
  ヒット数つきで「打ち切り記録」に出す。
  - 当初は「ヒットの少ない順」だけにしたが、グローバルの読み手が予算を先に使い、正解に関わる関数
    `alsoPropagate`（23ヒット）があふれたため、関数シンボルを優先する2段にした。
- **打ち切り記録（R5 の試作）。** 波ごとに「ヒット予算で打ち切ったシンボル（ヒット数）」と、最後に「波数上限で
  未処理のシンボル（ヒット数）」を出す。

### 10.2 結果

機能の近似は frr＝最上位ディレクトリ（デーモン）、redis＝ファイル（`src/` が平らな構成のため）。
モジュールカタログは評価用ワークスペースに無かった。上限は5波。出典は試作の `results/eval-feature-level.txt`。

「正解モジュールが出そろった波」と、その時点の確定モジュール数・ファイル数・累積秒:

| シナリオ | baseline | 完全・computed 予算1,000 | 予算3,000 | 予算10,000 |
|---|---|---|---|---|
| frr・CR-801（IS-IS のみのシード） | isisd のみ（1/4） | 1/4 | 1/4 | 1/4 |
| frr・Issue | 第2波 4/4（26モジュール・63ファイル） | 第3波（22・154・5.8秒） | **第1波（20・190・5.9秒）** | 第1波（26・426・11.9秒） |
| redis・CR-819 | 1/7 のまま収束 | 第1波（50ファイル・3.8秒） | **第1波（59・7.8秒）** | 第1波（69・15.5秒） |
| redis・Issue | 第4波（39ファイル） | 第2波（53・4.2秒） | **第1波（48・7.2秒）** | 第1波（56・10.7秒） |

- frr・Issue と redis の3シナリオでは、完全・computed（予算3,000以上）で、**第1波まで（2波）で正解モジュールが
  出そろった**。主要モジュールはすべて第0〜1波でそろった。
- frr・CR-801 は、工程2で対象範囲が IS-IS に絞られた CR（u1-eval の README による）なので、他デーモンが出ないのは
  シードの範囲どおりで、波数の問題ではない。
- 予算1,000では、出そろうのが1〜2波遅れた。予算10,000は3,000と同じ波で出そろい、ファイル数と時間が1.5〜2倍になった。
- 5波の完全・computed にかかった時間は 7〜80秒（以前は1波で数百秒）。解析が例外で失敗したヒットは0件。
- 打ち切られたシンボルの例: `node`(6615)、`main`(317)、`call`(602)、`addReplyError`(458)。一般的な名前が多いが、
  redis の `call`（コマンド実行の中核関数）のように重要な関数も含まれうる。打ち切り記録に残るので、人が判断できる。
- 確定モジュール数（frr で20〜26）は baseline（26）と同程度で、モジュール単位のノイズは増えていない。
