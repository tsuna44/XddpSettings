## 1. 🔴 MEDIUM スコープ検索が常に 0 ヒットになる

### 症状

✅ `make test` が **4 件 FAIL** する（186 件中、実測 0.769 秒）。

```
FAIL: test_search_dedup_key_includes_scope_class          AssertionError: 0 != 1
FAIL: test_search_known_symbols_normalizes_medium_scope   AssertionError: [] != ['validate']
FAIL: test_search_medium_scope_limits_to_file             AssertionError: 0 != 1
FAIL: test_search_medium_scope_resolves_relative_path      AssertionError: 0 != 1
```

4 件すべてが specout の MEDIUM スコープ検索に関するもの。
他の 6 テストスイート（design / close / common / excel2md / md2excel / harness）は全て OK。

### 原因

✅ `ClaudeCode/.claude/skills/xddp-04-specout/scripts/specout_bfs.py:785`（grep 経路）:

```python
cmd = ["grep", "-rn", "-E"] + (exclude_opts_grep if not scope else []) + [pattern, target]
```

✅ 同 `:804`（rg 経路）:

```python
cmd = ["rg", "-n", "--no-heading"] + (exclude_opts_rg if not scope else []) + ["-f", patternfile, target]
```

MEDIUM スコープでは `_resolve_scope_target()`（`:774`）が `target` に**単一ファイルパス**を返す。
grep も rg も、**引数が単一ファイルの場合はファイル名接頭辞を出力しない**。

実測（GNU grep 3.11 / ripgrep 15.2.0、いずれも同一挙動）:

```
$ grep -rn -E 'validate' gt/src/a.py
2:    return validate(x)                    ← ファイル名なし

$ grep -rn -E 'validate' gt/src
gt/src/a.py:2:    return validate(x)        ← ディレクトリ指定なら出る
```

✅ 一方 `:764` のパーサは `file:line:content` 形式を要求する:

```python
_HIT_LINE_RE = re.compile(r"^(?P<file>.+?):(?P<line>\d+):(?P<content>.*)$")
```

`2:    return validate(x)` はこの正規表現にマッチしない（`file` の後に `:数字:` が必要）。
`:793` / `:813` の `if m:` によって**マッチしない行は無言で捨てられる**。

結果、MEDIUM スコープ検索は例外もエラーも警告も出さずに 0 件を返す。

### 影響

- ✅ `:82` の分類マッピングにより `propagation-argument` は MEDIUM に割り当てられる。
  これは**変数の代入伝播を追う経路そのもの**であり、波紋調査の中核にあたる。
- MEDIUM が 0 件を返すため、伝播先の波が静かに空になる。
- `discovery-log.md` 上は「調査済み・ヒット 0」として記録されるため、
  ログを読んでも取りこぼしと区別がつかない。
- 「再現率（見逃さない）を優先する」という specout の設計方針に対して、
  最も検知しにくい形で反する。
- ✅ 両バックエンドで同一挙動であるため、`README.md:186` の
  「既定 `auto` は rg があれば rg・無ければ grep で従来と同一挙動」という記述は、
  少なくともこの経路では成立していない（どちらも同じく壊れている）。

### 修正案と検証結果

以下 2 行の変更で 4 件とも解消することを、リポジトリのコピーで実測確認済み（✅ `run_all: OK`）。

| ファイル:行 | 変更前 | 変更後 |
|---|---|---|
| `specout_bfs.py:785` | `["grep", "-rn", "-E"]` | `["grep", "-rn", "-H", "-E"]` |
| `specout_bfs.py:804` | `["rg", "-n", "--no-heading"]` | `["rg", "-n", "--no-heading", "--with-filename"]` |

なお、`_HIT_LINE_RE` にマッチしない行を無言で捨てる構造自体が今回の無症状化の原因であるため、
`-H` 追加とあわせて「パース不能行が 1 件以上あれば警告する」ガードの追加も検討に値する
（本レポートでは未検証の提案）。

### 補足

⬜ この不具合がいつ混入したかは特定していない（`--depth 1` で clone したため履歴を持っていない）。

## 2. 🟡 cross 成果物が review / revise から到達不能

### 症状

✅ 実際に生成される cross 成果物のファイル名は 4 種:

```
{CR_PATH}/04_specout/cross/SPO-{CR}-cross.md
{CR_PATH}/05_architecture/cross/DSN-{CR}-cross.md
{CR_PATH}/06_design/cross/CHD-{CR}-cross.md
{CR_PATH}/09_test-spec/cross/TSP-{CR}-cross.md
```

✅ しかし `xddp-revise/SKILL.md:42` の解決表は:

```
| `specout` | {CR_PATH}/04_specout/{REPO_NAME}/SPO-{CR}.md |
```

`arch`（`:43`）・`test`（`:45`）・`design`（§1a）も同じ `{REPO_NAME}/{TYPE}-{CR}.md` 形式であり、
`-cross` サフィックスを組み立てられない。`REPO_NAME` に `cross` を渡しても
`04_specout/cross/SPO-{CR}.md` という**存在しないパス**を解決する。

✅ `xddp-review/SKILL.md:29-32` も同様。cross は REFERENCE_FILES としてのみ登場し、
TARGET_FILE には指定できない。

### 案内との矛盾

✅ `xddp-04-specout/SKILL.md:591` は人レビューゲートの成果物一覧に cross SPO を含めて提示する:

```
{if HAS_CROSS:}
- cross: `{CR_PATH}/04_specout/cross/SPO-{CR}-cross.md`
```

✅ その直後 `:600` で修正手段を案内する:

```
REVISE_COMMAND: `/xddp-revise {CR} specout`（対象リポジトリを指定）
```

**案内された通りに実行しても cross 成果物は修正できない。**
マルチリポジトリ構成の 4 工程すべてで同じ穴が開いている。

### 参考

✅ `xddp-review/SKILL.md:87-91` には、`cross` が `REPOS_KEYS` に含まれない予約名であることと、
`Discover CHD Files` を `REPO_NAME: "cross"` で呼ぶ方式を採用しなかった理由が明記されている。
つまり cross が特殊であること自体は認識されており、解決表側の対応だけが漏れている。

✅ `xddp-05-arch/SKILL.md:213` は品質ゲートルールを以下のキーで渡す:

✅ このファイルを参照するのは `xddp-05-arch/SKILL.md` のみで、エージェント側からの参照はない。

### 他工程との対比

同じ「フェーズ別品質ゲートの外部化」でも、工程 6・7 はエージェント側が受領を宣言している。

| 工程 | 呼び出し側 | エージェント側の宣言 |

## 5. 🔵 `⏸` 状態の CR が in-progress 判定から漏れる ／ 用語不一致

### 5-1. in-progress 判定漏れ

✅ `xddp-common/SKILL.md:155`（CR Resolution / Step 2 Auto-detect）:

> **Multiple found** → read each directory's `progress.md`; a CR is "in progress" if any step has 🔄, 👀, or 🔁

判定対象は 🔄 / 👀 / 🔁 の 3 種のみ。

✅ しかし `⏸` を設定する箇所が実在する:

| 設定箇所 | 状況 |
|---|---|
| `xddp-10-test-run/SKILL.md:178` | `STATE: ⏸ 中断, DETAIL_STEP: Step B: テスト追加待ち` |
| `xddp-close/SKILL.md` | `xddp-11-specs 再実行待ち` / `最終コミット失敗` の 2 箇所 |

複数 CR が存在するワークスペースで、テスト追加待ちや close 失敗で中断している CR は
in-progress とみなされない。「0 or multiple in progress」分岐に落ちて
毎回 CR 番号の明示を求められる。

### 5-2. STATE 語彙の不一致

✅ `xddp-common/SKILL.md:538` の STATE 定義:

```
- `STATE`: 新しい状態（✅ 完了 / 🔄 進行中 / 👀 レビュー待ち / 🔁 修正中 / ⏸ 保留 / 🛑 中止）
```

「⏸ **保留**」と定義されているが、✅ 実際に書き込まれる値は全箇所「⏸ **中断**」である。

| 表記 | 出現箇所 |
|---|---|
| `⏸ 保留` | `xddp-common/SKILL.md:538`（定義行のみ・実使用 0 件） |
| `⏸ 中断` | `xddp-10-test-run`, `xddp-close`×2, `xddp-abort`×2, `test_xddp_progress.py` |

定義側が実装から取り残されている。`xddp-abort/SKILL.md:37` は `⏸ 中断` を条件判定に
使っているため、定義行の表記に合わせて実装すると逆に壊れる。**修正すべきは定義行の側**。
