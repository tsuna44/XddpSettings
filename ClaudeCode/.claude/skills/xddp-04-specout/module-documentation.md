# xddp-04-specout モジュール文書化手順

> このファイルは xddp-04-specout 専用の文書化手順。`xddp-specout-prelim-agent`（下調べ）と
> `xddp-specout-document-agent`（資料の確定）が冒頭で Read し、各見出しを apply する。他スキルから参照しないこと。
>
> - 本文中の「呼び出し元」は、この手順を apply するエージェントを指す。「呼び出し元が指定する」値
>   （対象ファイル・対象モジュール・判定の時点・件数・工程名等）は、各エージェントの手順が定める。
> - `CR_NUMBER`・`REPO_PATH`・`OUTPUT_DIR`・`TODAY`・`SUMMARY_TEMPLATE`・`MODULE_TEMPLATE`・`LEDGER_TEMPLATE`・
>   `SPECOUT_MAX_FILES_PER_MODULE`・`SPECOUT_DIAGRAM_LEVEL`・`SPECOUT_SEQUENCE_LEVELS` は呼び出し元の入力の値を使う。
> - ファイルパス・モジュールディレクトリは `REPO_PATH` 相対で書く。
> - 資料はすべて日本語で書く。

## 変更対象種別フラグ

呼び出し元が指定した入力（CRS の SP 項目と、あれば確定した初期シンボル）から次のフラグを設定する:

```
HAS_VAR_CHANGE:    変数・フィールド・プロパティが含まれるか
                   （CRS の SP 項目に「変更」「追加」「削除」を伴うフィールド・変数の言及があるか）
HAS_STRUCT_CHANGE: 構造体・クラス・インタフェース・型エイリアスが含まれるか
                   （SP 項目に class / struct / interface / type の変更が含まれるか）
HAS_FUNC_CHANGE:   関数・メソッドが含まれるか
                   （SP 項目に func / method / def / function の変更が含まれるか）
```

フォールバック: 3フラグがすべて false（種別不明）の場合は `HAS_FUNC_CHANGE` = true とみなす
（apply "## 必須図" のモジュール内シーケンス図を生成する）。

## 観察と累積観察メモ

### 書き込みの順序

呼び出し元が指定したファイルを1つ Read して文書化するたびに、次の順に書く:

1. モジュール資料（apply "## モジュール資料の記載要件"。統合パスでは `SPO-{CR_NUMBER}.md` の §2.A…）
2. 累積観察メモ `{OUTPUT_DIR}/work/observation-memo.md` の行（観察 a〜d・f）
3. 文書化済みファイル台帳 `{OUTPUT_DIR}/work/documented-files.md` の行

観察 e はモジュール資料の §2.4・§2.5（統合パスは §2.A.4・§2.A.5）へ書く（累積観察メモには書かない）。

### 文書化済みファイル台帳

- ファイルが無ければ `LEDGER_TEMPLATE` から作る（`{CR}` `{repo}` を置換する）。
- 1ファイル1行で追記する:
  `| {ファイルパス} | {モジュール名} | {モジュールディレクトリ} | {工程} | {関係する振る舞い（CRS）} |`
  - モジュール名・モジュールディレクトリ: apply "## モジュールの決め方" で決めた組
  - 工程: 呼び出し元が指定する（`下調べ` / `資料の確定`）
- 実際に Read して文書化したファイルだけを書く。既に行があるファイルは追記しない。書いた行は書き換えない。
- セル内の `|` は `\|` にエスケープする。

### 累積観察メモ

ファイルが無ければ、次の5セクションのヘッダで作成する（あれば作成しない。ヘッダを二重に書かない）。
このファイルは削除しない。全セクションの「ファイルパス」列は台帳と同じ表記（`REPO_PATH` 相対）で書く。

```
## 外部副作用
| 識別子（関数/メソッド） | ファイルパス | 副作用種別 | 対象 | 備考 |
|---|---|---|---|---|

## テスト可能性
| ファイルパス | テスト可能性 | 備考 |
|---|---|---|

## 非機能特性
| ファイル/識別子 | ファイルパス | 特性種別 | 観察内容 | アーキテクトへの示唆 | 影響度 |
|---|---|---|---|---|:---:|

## 入力源
| ファイルパス | 入力種別 | 識別子（ハンドラ/購読関数等） | 外部エンティティ（想定） | 備考 |
|---|---|---|---|---|

## 制約照合
| MODULE | ファイルパス | 既存制約 [CK-NNN] | 新観察内容 | 矛盾・不整合の有無 |
|---|---|---|---|---|
```

行は該当セクションのテーブル末尾へ追記する。副作用なしのファイルは「外部副作用」に
`| （副作用なし） | {ファイルパス} | — | — | — |` を追記する。

MODULE-LEVEL の行（呼び出し元が MODULE-LEVEL のモジュールについて一括で書く行）は、ファイルパス列を
`{モジュールパス}/*` とする（`{モジュールパス}` が `_root` の場合は `./*`。`_root` はリポジトリ直下のファイル
〔`_root/` ディレクトリが実在すればその配下も〕を表す）。

### 観察 a〜f

a. 外部副作用の観察:
   以下のパターンを手がかりに、外部状態を変更する箇所を特定する:
     - ORM / SQL 呼び出し（`.save()`, `.create()`, `.update()`, `INSERT`, `UPDATE` 等）
     - HTTP クライアント呼び出し（`requests.post`, `fetch`, `http.Client` 等）
     - メッセージキュー / イベント発行（`.publish()`, `.emit()`, `send()` 等）
     - ファイル書き込み（`open(..., 'w')`, `os.Write`, `fs.writeFile` 等）
     - キャッシュ更新（`cache.set()`, `redis.Set()`, `.put()` 等）
     - トランザクション境界（`@Transactional`, `BEGIN`/`COMMIT`/`ROLLBACK`, `db.begin()`, `session.begin_transaction()` 等）
   観察できた場合: ファイルパス・関数名・副作用種別・対象（DB表名/APIパス/キュー名等）を「外部副作用」に記録する。
   DB 書き込みがトランザクション内に属する場合は備考列に「トランザクション境界あり（{制御識別子}）」と記録する。
   観察できない（副作用なし）場合: そのファイルを「副作用なし」の行として記録する。

b. テスト可能性の観察:
   以下の基準で判定し、ファイルパスとともに「テスト可能性」に記録する:
     DI可能: コンストラクタ引数・メソッド引数・インタフェース経由で依存を注入できる構造
     密結合: `new SomeClass()` 等の直接インスタンス化や静的参照が多く、依存の差し替えが困難
     シングルトン: グローバルインスタンス・モジュールレベルのグローバル状態を持つ
     未確認: 上記いずれとも判断できなかった場合
   複数パターンが混在する場合は「DI可能/シングルトン混在」のように列挙し、
   具体的な混在箇所（例: `UserService.instance` がシングルトン参照）も備考に記録する。

c. 非機能特性の観察:
   以下のいずれかが観察された場合のみ「非機能特性」に記録する（該当なしは記録不要）:
     パフォーマンス感度:
       コメント依存パターン（コードにコメントがない場合は検出不可、検出できなければ記録不要）:
       - SLO / SLA / timeout / deadline コメントや変数名の言及
       コード構造パターン（コメントなしでも判定可能、該当すれば必ず記録）:
       - HTTP ハンドラ登録: `router.GET` / `@app.route` / `http.HandleFunc` / `@GetMapping` 等のパターン → 高頻度呼び出しパス候補として一律記録する
         （管理画面・バッチ専用エンドポイントも同パターンを持つ。実際の頻度はアーキテクトが判断するため、絞り込まず一律記録する）
       - ループ内 DB アクセス: for/while ループ内に ORM/SQL 呼び出しが存在する構造 → N+1 候補として記録
     並行性: Mutex / Lock / RWMutex / synchronized / goroutine / async / Channel / Promise 等の使用
     後方互換性: エクスポートされた公開インタフェース・Deprecated マーカー・バージョン番号
     スレッドセーフ: グローバル変数への書き込み・シングルトン初期化箇所
     その他: 上記に当てはまらないが方式選択に影響する制約

d. 入力源の観察:
   以下のパターンを手がかりに、「この関数・モジュールを最初に呼び出す外部エンティティ」を観察する:
     HTTP ハンドラ登録（エンドポイント定義）:
       `router.GET/POST/PUT/DELETE`, `@app.route`, `http.HandleFunc`, `@GetMapping` 等のパターン
       → 入力種別=HTTPリクエスト、外部エンティティ={HTTPメソッド} {パス}
     メッセージキュー購読:
       `.subscribe()`, `.consume()`, `@KafkaListener`, `channel.receive()` 等のパターン
       → 入力種別=メッセージキュー購読、外部エンティティ={キュー名/トピック名}
     イベントハンドラ登録:
       `EventBus.subscribe`, `on('event', fn)`, `@EventListener` 等のパターン
       → 入力種別=イベント、外部エンティティ={イベント名}
     バッチ・スケジューラ起動:
       `@Scheduled`, `cron.AddFunc`, `schedule.every()`, `@CronJob` 等のパターン
       → 入力種別=バッチ/スケジューラ、外部エンティティ={スケジュール設定}
     公開インタフェース（エクスポートされた関数）:
       モジュールのエクスポート定義（`export function`, `public func`, `pub fn` 等）で、
       具体的な呼び出し元が調査範囲外の場合
       → 入力種別=外部呼び出し、外部エンティティ=外部モジュール（詳細未調査）
   観察できた場合: ファイルパス・入力種別・ハンドラ識別子・外部エンティティ（想定）を「入力源」に記録する。
   観察できなかった場合（内部処理ファイル等）: 記録不要。

e. 定数・グローバル変数の観察（呼び出し元が指定した対象ファイルのみ）:
   Read 済みのファイルから定数・グローバル変数を特定し、モジュール資料の §2.4・§2.5（統合パスは §2.A.4・§2.A.5）に直接記録する。

   【定数・列挙値の検出対象】スコープが「モジュール」または「グローバル/エクスポート」を優先。
     C/C++:           `#define` マクロ定数・`enum`/`enum class`・ファイルスコープ `const`
     Java/C#/Kotlin:  `static final`/`const` フィールド・`enum` 型定義
     Python:          モジュールレベル ALL_CAPS 変数・`Enum` クラス継承メンバ
     Go:              `const` ブロック（`iota` 含む）・パッケージレベル `const`
     TypeScript/JS:   モジュールレベル `const`/`readonly`/`as const`
     その他:          言語慣習に従う定数構文
   業務ルール・閾値・設定値に相当するものは積極的に記録する。純粋な内部実装定数は省略可。

   スコープの判定:
     ファイルローカル: ファイル外から参照不可（`static`（C言語）/ プライベート定数等）
     モジュール公開:   モジュール内で共有（パッケージ内公開等）
     グローバル:       複数モジュール・複数ファイルから参照可
     エクスポート:     パッケージ・ライブラリ外部から参照可（`public`/大文字始まり（Go）等）

   【グローバル変数の検出対象】
     C/C++:           関数外の変数宣言（ファイルスコープ）・`extern` 宣言・`static` 変数（関数外）
     Java/C#:         `static`（`final` でない）フィールド・シングルトン保持フィールド
     Python:          モジュールレベル可変変数（ALL_CAPS でない）・`global` 使用箇所
     Go:              `var` パッケージレベル宣言
     TypeScript/JS:   モジュールレベル `let`/`var` 宣言

   スレッド/割り込み安全性の判定:
     安全:   `Mutex`/`RWMutex`/`sync`/`volatile`/`atomic`/`synchronized` 使用を確認
     要注意: 複数スレッド・割り込みからアクセス可能だが排他制御を確認できない
     未確認: シングルスレッド環境か不明・判断できない場合

   記録方法: §2.4・§2.5 テーブルのプレースホルダー行をデータ行に置換する（Edit ツールで行単位置換）。
     既にデータ行があれば行を追加する。定数が存在しない場合は「定数なし」、グローバル変数が存在しない場合は
     「グローバル変数なし」と記入する（既に「定数なし」「グローバル変数なし」があり、今回記録するものがあれば、その行を置き換える）。
   対象ファイル以外には行わない。

f. 制約照合の観察（呼び出し元が `KNOWN_CONSTRAINTS` を用意し、空でない場合のみ）:
   `KNOWN_CONSTRAINTS` のキー MODULE は、ファイルの第1階層ディレクトリ（ルート直下のファイルは `_root`）である
   （apply "## モジュールの決め方" のモジュールとは別）。
   現在のファイルの MODULE に対応する `KNOWN_CONSTRAINTS[MODULE]` が存在する場合、観察した実装内容が当該制約と
   矛盾しないかを確認し、「制約照合」へ1行追記する:
     矛盾が見つかった場合: `| {MODULE} | {ファイルパス} | [CK-NNN] {制約の要約} | {新たに観察した実装内容} | 矛盾あり |`
     矛盾がない場合も確認済みエビデンスとして: `| {MODULE} | {ファイルパス} | [CK-NNN] {制約の要約} | {観察内容} | 矛盾なし |`
   `KNOWN_CONSTRAINTS[MODULE]` が存在しない場合: 記録不要。

## 必須図

呼び出し元が指定したモジュール（必須図の対象モジュール）の資料には、`SPECOUT_DIAGRAM_LEVEL` の設定に関わらず
（`minimal` でも省略せず）、apply "## 変更対象種別フラグ" で設定したフラグに応じて次を生成する:

| フラグ | 節（分割パス: モジュール資料 ／ 統合パス: §2.A…） | 内容 |
|---|---|---|
| `HAS_VAR_CHANGE` | §4.3 データ構造 ／ §2.A.8.3 | 変更変数・フィールドが属する型の定義と、関連型との関係 |
| `HAS_STRUCT_CHANGE` | §4.2 データ型関連図 ／ §2.A.8.2 | 変更対象型の継承・依存・実装関係（Mermaid classDiagram。手続き型言語では構造体の参照・埋め込み関係）。変更対象型と直接関係する型（親・実装インタフェース・フィールドの型・依存先）を含める |
| `HAS_FUNC_CHANGE` | §4.5 モジュール内シーケンス図 ／ §2.A.8.5 | 変更対象関数の呼び出しフロー（呼び出し元 → 変更対象 → 内部呼び出し先） |

対象モジュール以外の図は `SPECOUT_DIAGRAM_LEVEL` に従う（apply "## モジュール資料の記載要件"）。
節が「対象外」またはテンプレートのままの場合は、必須図で置き換える。既に図がある節は書き直さない。

## Section 3 必須化判定

`SPO-{CR_NUMBER}.md` §3（モジュール間シーケンス図）は、呼び出し元が指定したファイル集合（判定対象ファイル）と
変更対象シンボルについて、次のいずれかを満たす場合に必須とする:

- 判定対象ファイルの直接の親ディレクトリパスが 2 種類以上ある
- 変更対象シンボルの参照箇所が、複数の異なるモジュールパス（`REPO_PATH` 相対の第1階層）に分散する

いずれも満たさない場合のみ「対象外」と記載する。必須の場合は `SPECOUT_SEQUENCE_LEVELS` に従い、
変更対象シンボルが関与するモジュール間の呼び出しフローを書く。

## モジュール資料の記載要件

### モジュール資料（分割パス）

`{OUTPUT_DIR}/modules/{モジュール名}-spo.md` を `MODULE_TEMPLATE` から作り、各セクションの blockquote に従って書く。

- 文書番号: `SPO-{CR_NUMBER}-{モジュール名}`。対象モジュール欄・§1 のディレクトリ欄: モジュールディレクトリ
- 作成者・版数・§5 変更履歴: apply "## 資料の状態（作成者・版・変更履歴）"
- テンプレートのプレースホルダーを残さない（該当なしの節は「対象外」等、テンプレートの指示どおりに書く）

既存のモジュール資料に追記する場合:

- 同じファイルの記載が既にあれば二重に書かない。
- 表の節（§2.2〜§2.5・§4.3 等）には行を加える。文章の節（§1 の役割・責務、§2.1 処理フロー、§2.6 制約・前提条件、§3）は
  追記したファイルを含む内容に更新する。図の節は追記したファイルの要素を加える。

### Section 4（モジュール内ダイアグラム）の生成範囲

必須図の対象モジュールは apply "## 必須図" の図を必ず生成する。それ以外は `SPECOUT_DIAGRAM_LEVEL` に従う:

- `minimal`: 必須図以外は「対象外」
- `standard`: 状態遷移図(4.1), データ型関連図(4.2), データ構造(4.3)
- `full`: 上記すべて + PAD(4.4) + データアクセスマトリクス(4.6) + データモデル(4.7)
  ※ モジュール資料でデータアクセスマトリクス・データモデルを生成した場合、サマリー `SPO-{CR_NUMBER}.md` の §4.3/§4.4 へのマージ対象となる

### 統合パスの §2.A… の構成

統合パスでは、モジュールごとの資料を `SPO-{CR_NUMBER}.md` の §2（全体アーキテクチャ図）の直後に
`## 2.A. {モジュール名}`、`## 2.B. {モジュール名}` … として書く（1モジュールでも `## 2.A.` を使う）。
構成は `MODULE_TEMPLATE` の §2〜§4 と同じにし、次の見出しで書く（§1 モジュール概要は §2.A の冒頭の数行
〔ディレクトリ・役割・責務・既存仕様書〕、§5 変更履歴は持たない）:

| モジュール資料 | §2.A… |
|---|---|
| §2.1〜§2.6（処理フロー〜制約・前提条件） | `### 2.A.1`〜`### 2.A.6`（同じ見出し名） |
| §3 既存仕様の文書化（§3.1…） | `### 2.A.7 既存仕様の文書化`（`#### 2.A.7.1`…） |
| §4 モジュール内ダイアグラム（§4.1〜§4.7） | `### 2.A.8 モジュール内ダイアグラム`（`#### 2.A.8.1`〜`#### 2.A.8.7`、同じ見出し名） |

§2.B 以降も同様に `2.B.1`… とする。必須図と `SPECOUT_DIAGRAM_LEVEL` の規則はモジュール資料と同じに適用する。

## 配置判定（成長型）

配置判定は呼び出し元が指定した時点で行う。

- **統合パス**: `{OUTPUT_DIR}/modules/` を作らず、モジュールごとの資料を `SPO-{CR_NUMBER}.md` の §2.A… に書く
  （apply "## モジュール資料の記載要件" の「統合パスの §2.A… の構成」）。§5・§6 は分割パスと同じに書く。
- **分割パス**: モジュールごとに `{OUTPUT_DIR}/modules/{モジュール名}-spo.md` を書く。

現在の配置は `{OUTPUT_DIR}/modules/` の有無で判定する（無い＝統合パス／ある＝分割パス。`SPO-{CR_NUMBER}.md` も
`modules/` も無い＝未作成）。

- `DOCUMENTED_TOTAL` ＝ 台帳のファイルと今回文書化するファイルの和集合の件数（工程を問わない）
- モジュールごとのファイル数 ＝ 台帳のファイルと今回文書化するファイルの和集合を、モジュールごとに数えた件数。
  呼び出し元が指定する（スクリプトの算出値があればそれを使い、自分で数え直さない）
- `HAS_MODULE_LEVEL` ＝ 呼び出し元が MODULE-LEVEL のモジュールがあると指定したか（下調べは常に false）

1. 未作成の場合:
   `DOCUMENTED_TOTAL` ≤ `SPECOUT_MAX_FILES_PER_MODULE` かつ NOT `HAS_MODULE_LEVEL` → 統合パスで書く。
   それ以外 → 分割パスで書く（`mkdir -p {OUTPUT_DIR}/modules`）。続けて手順3 を各モジュールに適用する。
2. 統合パスで、`DOCUMENTED_TOTAL` > `SPECOUT_MAX_FILES_PER_MODULE` または `HAS_MODULE_LEVEL` → 分割パスへ移す:
   a. `mkdir -p {OUTPUT_DIR}/modules`
   b. `SPO-{CR_NUMBER}.md` の §2.A… をモジュールごとに `MODULE_TEMPLATE` の §2〜§4 へ移して `modules/{モジュール名}-spo.md` を作る
      （`### 2.A.n` → `### 2.n`、`### 2.A.7` → `## 3.`、`### 2.A.8` → `## 4.` の対応で節をそのまま移す。§1 モジュール概要は §2.A… の冒頭と
      §8 の行から書く。作成者・版数・§5 変更履歴は apply "## 資料の状態（作成者・版・変更履歴）" に従って書く。
      テンプレートのプレースホルダーを残さない）
   c. `SPO-{CR_NUMBER}.md` から §2.A… を削除する
   d. §8 を分割パスの書式（`modules/{モジュール名}-spo.md` へのリンク）に置き換える（apply "## §8 の書き方"）
   e. `modules/` と §2.A… が併存していないことを確認する
   続けて手順3 を各モジュールに適用する。
3. 分割パスで、あるモジュールのファイル数が `SPECOUT_MAX_FILES_PER_MODULE` を超える場合:
   - モジュールディレクトリの直下にサブディレクトリがある → そのモジュールだけサブディレクトリ単位に分割する:
     - ファイルを、モジュールディレクトリ直下のサブディレクトリごとに分ける。サブディレクトリごとに
       `{OUTPUT_DIR}/modules/{モジュール名}/{subdir}-spo.md` を `MODULE_TEMPLATE` から作る
       （`mkdir -p {OUTPUT_DIR}/modules/{モジュール名}`。文書番号 `SPO-{CR_NUMBER}-{モジュール名}-{subdir}`。そのサブディレクトリのファイルだけを書く）。
     - モジュールディレクトリ直下のファイル（どのサブディレクトリにも属さないもの）は
       `{OUTPUT_DIR}/modules/{モジュール名}/root-spo.md` に書く（該当ファイルが無ければ作らない）。
     - 既存の `modules/{モジュール名}-spo.md` に書かれていた内容は、ファイルごとに対応するサブモジュール資料へ移す。
     - `modules/{モジュール名}-spo.md` を次の索引に置き換える（文書番号 `SPO-{CR_NUMBER}-{モジュール名}`）:
       - Section 1: モジュール概要（`MODULE_TEMPLATE` §1 と同じ）
       - Section 2: サブモジュール一覧
         | サブモジュール | ファイル | 波及ファイル数 | 概要 |
         |---|---|---|---|
         | {subdir} | `modules/{モジュール名}/{subdir}-spo.md` | N | {1行の概要} |
       - Section 3: サブモジュール間シーケンス図（`SPECOUT_SEQUENCE_LEVELS` に従う。サブモジュール間の呼び出しが無ければ「対象外」）
       - Section 4: サブモジュール間クラス関係図（複数のサブモジュールにまたがる継承・依存・インタフェース共有を Mermaid classDiagram で。
         手続き型言語では構造体の参照関係。`SPECOUT_DIAGRAM_LEVEL` が `minimal` の場合は「対象外」）
       - Section 5: サブモジュール間データフロー・データアクセスマトリクス／データモデル
         （データフロー: 複数サブモジュールにまたがるものを書く。識別できなければ省略。
         データアクセスマトリクス／データモデル: `SPECOUT_DIAGRAM_LEVEL` が `full` の場合のみ。それ以外は「対象外」）
       - 作成者・版数・変更履歴: apply "## 資料の状態（作成者・版・変更履歴）"
   - サブディレクトリが無い → 分割せず、`modules/{モジュール名}-spo.md` の冒頭に次の注記を書く（既にあれば件数を更新する）:
     > ⚠️ 波及ファイル数（{count}）が SPECOUT_MAX_FILES_PER_MODULE（{閾値}）を超えています。
     > サブディレクトリによる分割候補がないため、単一ファイルに出力しています。
   既にサブディレクトリ分割済みのモジュールに書くファイルは、該当する `modules/{モジュール名}/{subdir}-spo.md`
   （無ければ作る）または `root-spo.md` へ書き、索引のサブモジュール一覧と件数を更新する。
4. 移動は統合パス→分割パス、単一のモジュール資料→サブディレクトリ分割の一方向のみ。逆方向には戻さない。

## §8 の書き方

`SPO-{CR_NUMBER}.md` §8（調査済みモジュール一覧）の表は、最終の配置と全モジュール（台帳のモジュール。
呼び出し元が指定した場合は MODULE-LEVEL のモジュールも）から毎回作り直す（既存の行に追記しない）。
「モジュール名」列にはモジュール名、「ディレクトリ」列にはモジュールディレクトリ（apply "## モジュールの決め方"）を書く。

**統合パス:** モジュールごとに1行。§2.B 以降のモジュールは対応する節番号（§ 2.B …）を書く。

| モジュール名 | ディレクトリ | 個別資料 |
|------------|------------|--------|
| {モジュール名} | {モジュールディレクトリ} | SPO-{CR_NUMBER}.md § 2.A, § 5（文書化ファイル数が閾値以下のため modules/ 未生成） |

**分割パス:** モジュールごとに1行。作成したすべてのモジュール資料へリンクする。
サブディレクトリ分割したモジュールは索引ファイルへリンクし、索引であることを付記する。

| モジュール名 | ディレクトリ | 個別資料 |
|------------|------------|--------|
| {モジュール名} | {モジュールディレクトリ} | [modules/{モジュール名}-spo.md](modules/{モジュール名}-spo.md) |
| {モジュール名} | {モジュールディレクトリ} | [modules/{モジュール名}-spo.md](modules/{モジュール名}-spo.md)（インデックス・N サブモジュールに分割） |

**MODULE-LEVEL のモジュール（呼び出し元が指定した場合のみ）:** 配置によらず、MODULE-LEVEL のモジュールごとに1行を加える。
このモジュールはモジュール資料を持たない。

| モジュール名 | ディレクトリ | 個別資料 |
|------------|------------|--------|
| {モジュールパス}（MODULE-LEVEL） | {モジュールパス}（`_root` の場合は `（リポジトリ直下）`） | なし（探索上限によりモジュール単位で記録。個別調査は設計・テスト工程で実施すること） |

## モジュールの決め方

モジュールは「モジュール名」と「モジュールディレクトリ」（`REPO_PATH` 相対）の組で表し、台帳に記録する。

1. 記録済みのモジュールディレクトリ（台帳の組と、呼び出し元が同じ実行の中で既に決めた組）のうち、ファイルのパスに
   ディレクトリ境界で前方一致する最長のものがあれば、そのファイルはそのモジュールに属する
   （`src/a` は `src/ab/x.c` に一致しない）。資料の確定では、この割り当てと件数はスクリプト（`specout_bfs.py doc-targets`）が行う。
2. どれにも一致しないファイルは、呼び出し元が新しいモジュールを決める。
   - モジュールディレクトリは、機能的にまとまったソースファイルを持つディレクトリとする。ソースファイルを持たず
     サブディレクトリだけを持つディレクトリ（名前空間の入れ物）はモジュールにしない
     （例: C の `src/`・Java の `src/main/java/com/example/auth/`・組み込みの `Drivers/uart/`）。
   - モジュールディレクトリは、そのファイルのパスにディレクトリ境界で前方一致するディレクトリにする。
   - リポジトリ直下のファイル（ディレクトリを持たないファイル）のモジュールディレクトリは `.` と書く。`.` はリポジトリ直下のファイルにだけ
     一致し、サブディレクトリのファイルには一致しない。
   - モジュール名は台帳内で一意とし、ファイル名に使える文字（英数字・`-`・`_`）だけで作る。
3. 一度記録した名前とディレクトリの組は変えない。

モジュール資料のファイル名（`modules/{モジュール名}-spo.md`）と §2.A… の見出しにはモジュール名を、
§8 の「ディレクトリ」列にはモジュールディレクトリを使う。

観察 f の MODULE（code-knowledge の参照先）はこの規則とは別で、ファイルの第1階層ディレクトリ
（ルート直下のファイルは `_root`）を使う。
