## 2. USDM 要求仕様

> **記述ルール**
> - **採番体系**：ID 先頭に CR 番号を名前空間として付与し（形式 B）、その後ろで Prefix が種別を、番号が親子関係を表す。CR プレフィクスにより CR 横断で ID が固有になる
>   - ユーザ要求：`{CR番号}-UR-XXX`（XXX は 3桁ゼロパディング、例: `CR-2026-970-UR-001`）
>   - システム要求：`{CR番号}-SR-XXX-YYY`（UR番号を継承、例: `CR-2026-970-SR-001-001`）
>   - 仕様：`{CR番号}-SP-XXX-YYY.ZZZ`（SR番号を継承。ZZZ は 10 刻みの飛び番号 `010, 020, 030…` とし、
>     後から仕様を挿入する場合は間の番号（例 `015`）を用いて既存 ID を変更しない。例: `CR-2026-970-SP-001-001.010`。
>     出典: AFFORDD USDM小冊子 補足編 2.6）
>   - `{CR番号}` は本仕様書の対象 CR（文書冒頭の「対象CR」。例 `CR-2026-970`）。同一 CR 内の全 ID で共通のプレフィクスとなる。ローカル採番（`XXX-YYY.ZZZ`）は従来どおり親番号を継承する
> - **見出しレベルと要素種別の対応**（レベルが種別を一意に決める。H1〜H6 のみ使用し、H7 以降は使わない）
>   - カテゴリ（機能要求／非機能要求）：`### ＜{カテゴリ名}＞`（H3）
>   - ユーザ要求（UR）：`#### {CR番号}-UR-XXX {タイトル}`（H4）
>   - 要求グループ：`##### ＜{要求グループ名}＞`（H5）
>   - システム要求（SR）：`###### {CR番号}-SR-XXX-YYY {タイトル}`（H6）
>   - 仕様グループ：`**＜{仕様グループ名}＞**`（太字行。H7 が存在しないため見出しではなく太字行で表す）
>   - 仕様（SP）：`- **{CR番号}-SP-XXX-YYY.ZZZ**: {タイトル}`（リスト項目。属性は 2 スペースインデントの子リストで記載）
> - **ID管理**：UR・SR は ID を見出しに含める。SP は ID をリスト項目の先頭（`- **{CR番号}-SP-XXX-YYY.ZZZ**:`）に保持する。独立した **ID:** 行は設けない。すべての ID に CR プレフィクスを付けること（CR プレフィクスを欠く ID は artifact_lint の L13 で error として検出される）
> - **カテゴリの位置付け**：`### ＜…＞`（H3）カテゴリは「機能要求／非機能要求」の要求種別軸のみを表す。内容単位の細分（例: ＜検索＞／＜表示＞）はカテゴリではなく要求グループ（H5）または UR で表現する
> - **ユーザ要求**：要求書から転記・整理する。"何をしたいか" をユーザ視点で記述する。実現したいこと（抽象的）。「〜したい」の形で記述
> - **理由**：要求の根拠。要求とセットで必ず記載。「〜なので、〜のため」の形で記述
> - **説明**：備忘録。実装されなくてもよい補足情報
> - **システム要求**: ユーザ要求を実現するためにシステムが満たすべき要求。"システムが何をすべきか" を記述する。「〜のとき、〜して、〜する」の形で記述
> - **仕様**：システム要求を実現するための具体的な仕様。要求に含まれる"動詞"およびその"目的語"（具体的）。「〜を〜する」の形で記述。Before/After で変更内容を明確にする。受け身表現（〜される、〜が存在しない）は避け、能動表現（〜が〜する）で主体を明示する。述語が「〜しない」となる否定表現は「隠れた IF 文」を生みやすいため、else 側（それ以外の条件）の仕様を必ず併記するか、ディシジョンテーブル等で全条件を網羅すること（出典: AFFORDD USDM小冊子 基礎編4.5.4）。
> - **新規開発モード（`xddp.config.md` の `DEVELOPMENT_MODE: new`）の場合:** 仕様は Before/After の
>   対比ではなく、単一の「仕様：」項目として目標動作を記述する
>   （例: `- **仕様：** {実現する仕様・動作}「〜を〜する」`）。CR 全体が新規開発であり、
>   対比すべき「変更前」の状態が存在しないため。
> - **ステータス**：各 UR/SR/SP に必ず記載。`確定` / `🔍 要検討` / `⚠️ 懸念あり` / `❓ 未決` のいずれかを選択する
> - **懸念・検討事項**：ステータスが `確定` 以外の場合は必ず記載。不明点・リスク・確認が必要な内容を記述する。`確定` の場合は省略可
> - 要求の分割方法：時系列・構成・状態・共通
> - **要求の階層とネスト**：要求は UR（上位要求）→ SR（下位要求）の 2 階層まで。SR の下にさらに SR を作らない（要求 3 階層は禁止）。範囲が大きすぎる場合は垂直方向に階層を増やさず、水平方向に別 UR として分割する（分割基準: 時系列／構成／状態／共通）。（出典: AFFORDD USDM小冊子 補足編 3.1）
> - **階層パターンの使い分け**：
>   - 要求がシンプルで下位分割が不要 → 1 階層（UR → 仕様グループ → SP。SR を作らない）
>   - 要求が複合的で分割が必要 → 2 階層（UR → 要求グループ → SR → 仕様グループ → SP）
>   - 分割したいが下位要求が 1 つしか立たない → 強制 2 層（SR を 1 つ立て、その SR の理由・説明は空欄にする）
>   （出典: AFFORDD usdm-schema v1.1.0）
> - **理由の必須性**：UR の理由は必須。SR の理由は原則記載するが、強制 2 層（要求グループ内の SR が 1 つ）の場合のみ空欄可。（出典: AFFORDD USDM小冊子 補足編 3.2／AFFORDD usdm-schema `SubRequirement.reason` 任意）
> - **分割軸の記録**：要求グループには適用した分割軸（時系列分割／構成分割／状態分割／共通分割）を記載する。（出典: AFFORDD USDM小冊子 基礎編 4.2.4）
> - **グループ名表記**：要求グループ名・仕様グループ名は全角山括弧 `＜＞` で囲む（例: `＜検索条件のプリセット＞`）。（出典: AFFORDD usdm-schema v1.1.0）
