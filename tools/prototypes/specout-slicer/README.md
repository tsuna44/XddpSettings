# specout-slicer（試作）

工程4a（specout）の波紋調査で、LLM による hit 行の分類（`xddp-specout-classifier-agent`）を
**決定的な静的スライス**に置き換えられるかを検証した試作です。

- 状態: **試作（評価用）**。スキル・エージェントからは参照されていません。`setup.sh` のデプロイ対象外です。
- 作成: 2026-10-03
- 対象言語: C / C++ / Python（tree-sitter で構文解析）

## 何をするか

grep のヒット行（「変更シンボルがこの行に現れた」）ごとに、その関数の中だけで保守的なスライスを行い、
影響が**関数の外へ出るか**を判定します。外へ出る経路（出口）の種類によって、次の波で何を追うかが決まります。

| 出口 | 意味 | 次の波で追うもの |
|---|---|---|
| `return` / `exception` | 影響を受けた return・yield・throw・raise | 呼び出し元（関数名） |
| `out` | ポインタ/参照引数・self/this 経由の書き込み | 呼び出し元 |
| `heap` / `state` / `unknown` / `closure` | 出所不明のポインタ経由・static ローカル・解析不能な呼び出し・外側関数のローカル | 呼び出し元（安全側） |
| `global` | グローバル変数（構造体はフィールド単位。例 `server.dirty`）への書き込み | その変数を読む箇所 |
| なし | 影響が関数内で閉じる | 追わない（伝播を止める） |

関数内の解析は、流れ依存性を簡易に近似しています。具体的には、データ依存・制御依存・早期 return・ループ・
if/else の排他・return で終わるブロックを考慮します。呼び出し先は、リポジトリ全体の定義索引から副作用の要約
（戻り値・出力引数・書き込むグローバル）を再帰的に求めます（深さ3まで）。

## セットアップ

```bash
cd tools/prototypes/specout-slicer
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt
./.venv/bin/python test_slicer.py        # 合成コードのテスト（OK=61 NG=0 になること）
```

`make test` の対象外です（tree-sitter が必要なため）。

## 使い方

```bash
# 1つのリポジトリで、baseline（今の LLM の振る舞いの再現）とスライス BFS を比べる
./.venv/bin/python bfs_sim.py --repo <対象リポジトリ> --seeds SYM1,SYM2 \
    [--truth 正解ファイル一覧.txt --main 主要ファイル,...] \
    [--modes baseline,slice] [--seed-summary interface|computed|unknown] \
    [--globals-as-up] [--ignore-calls '正規表現'] [--max-waves 10] [--max-hits 3000] \
    [--module-level dir1|file] [--extra-excludes deps/] [--h-as c|cpp]

# u1-eval（frr / redis と正解データ）での一括評価
U1_EVAL=/path/to/u1-eval ./eval/run_feature_eval.sh                  # 機能単位の評価（最新）
U1_EVAL=/path/to/u1-eval MODES="baseline filter-unknown" ./eval/run_eval.sh   # 方式の比較
```

| オプション | 意味 |
|---|---|
| `--seed-summary interface` | シード関数の変更は戻り値・出力引数にだけ現れると仮定する（最も狭い。安全側でない） |
| `--seed-summary computed` | シード関数が書きうる副作用（グローバルを含む）がすべて変わると仮定する |
| `--seed-summary unknown` | 何が変わるか不明として扱う（呼び出し元へは必ず伝播） |
| `--globals-as-up` | 剪定フィルタ方式。グローバルの読み手は追わず、呼び出し元への伝播に読み替える（今の BFS の範囲内で剪定するだけ） |
| `--ignore-calls` | 影響なしとみなす呼び出し（ログ出力・メモリ確保・assert 等）。プロジェクトごとの設定に相当する |
| `--max-hits` | 1波で処理するヒットの予算。関数シンボル → 値シンボル（グローバルの読み手）の順、各々ヒットの少ない順に予算内で処理し、残りは「打ち切り記録」に出す |
| `--max-waves` | 波数の上限。上限で残ったシンボルも「打ち切り記録」に出す |
| `--module-level` | 機能（モジュール）の近似。`dir1`=最上位ディレクトリ、`file`=ファイル |

検索は `git grep` ではなく、起動時に作るリポジトリ全体の識別子の索引（`TokenIndex`）を引く
（frr 約96万行で作成1.8秒）。

## 評価結果の要点

正解は u1-eval の `truth/*.txt`（修正 PR で変更されたファイル）です。baseline が LLM の実測と一致することは確認済みです
（redis CR-2026-819 で第0波2ヒット・第1波3ヒット）。

**決定的分類と LLM の一致（`stdlib_c_classify.py`）:** 過去3 CR の LLM 判定179行のうち176行で、
次の波に渡すシンボルが一致しました。不一致3行のうち1行は LLM の誤りです。

**剪定フィルタ方式（`--globals-as-up --seed-summary unknown`、`results/eval-final.txt`）:**

| シナリオ | baseline（確定ファイル/関数） | フィルタ（unknown） | 正解再現 |
|---|---|---|---|
| frr・CR-801 のシード | 82 / 127 | 45 / 89 | 3/8 → 3/8 |
| frr・Issue のシード | 89 / 179 | 31 / 84 | 5/8 → 5/8 |
| redis・CR-819 のシード | 2 / 2 | 2 / 2 | 1/7 → 1/7 |
| redis・Issue のシード | 79 / 873 | 78 / 855 | 7/7 → 7/7 |

- `interface` はさらに狭くなりますが、正解を落とします（frr Issue 5/8→4/8、redis Issue 7/7→6/7）。
- `computed`（シードが書くグローバルの読み手も追う）は、redis CR-819 で正解 1/7 → 7/7 に上がりました（87ファイル）。
**完全スライス（グローバルの読み手を追い続ける）の波ごとの累積（`results/eval-full-slice-waves.txt`、上限 10波・1波10,000ヒット）:**

| シナリオ | 方式 | 波ごとの累積確定ファイル（正解再現） |
|---|---|---|
| frr・CR-801 | baseline | 第0波 4（3/8）… 第9波 82（3/8） |
| frr・CR-801 | 完全・computed | 第0〜6波 4〜31（3/8）、第7波 372（5/8）、第8波 630（7/8）、第9波で打ち切り |
| frr・Issue | baseline | 第0波 5（4/8）、第2波 63（5/8）… 第9波 89（5/8） |
| frr・Issue | 完全・computed | 第0波 31（4/8）、第1波で打ち切り（frontier 275） |
| redis・CR-819 | baseline | 第1波 2（1/7）で収束 |
| redis・CR-819 | 完全・computed | 第0波 29（5/7）、**第1波 69（7/7）**、第9波 149（7/7） |
| redis・Issue | baseline | 第0波 6（5/7）、第4波 39（7/7）… 第9波 79（7/7） |
| redis・Issue | 完全（無視リストあり） | 149（7/7）（`results/eval-final.txt`。波ごとの記録なし） |

- この一括実行は、redis・Issue の完全スライスの途中で時間上限（2時間）に達し停止しました。
- 1ヒットの判定は 2〜85ms です。呼び出し先の要約を新たに計算するほど遅くなります。
- frr・CR-801 の完全スライスは全体で4,141秒かかりましたが、各波の合計は292秒です。差の約3,850秒は、打ち切った
  第9波の検索（`root.field` 形式のシンボルをフィールド名で grep し、後から絞り込む方式）に使われています。
  これはスライスではなく検索の実装の問題で、`root.field` を正規表現のまま grep すれば解消できる見込みです（未検証）。

**機能（モジュール）単位の評価（`results/eval-feature-level.txt`、最新）:**
機能の近似は frr=最上位ディレクトリ（デーモン）、redis=ファイル（`src/` が平らな構成のため）。上限5波。
「正解モジュールが出そろった波」と、その時点の確定モジュール数・ファイル数・累積秒。

| シナリオ | baseline | 完全・computed 予算1,000 | 予算3,000 | 予算10,000 |
|---|---|---|---|---|
| frr・CR-801（IS-IS のみのシード） | isisd のみ（1/4） | 1/4 | 1/4 | 1/4 |
| frr・Issue | 第2波 4/4（26モジュール・63ファイル） | 第3波（22・154・5.8秒） | **第1波（20・190・5.9秒）** | 第1波（26・426・11.9秒） |
| redis・CR-819 | 1/7 のまま収束 | 第1波（50ファイル・3.8秒） | **第1波（59・7.8秒）** | 第1波（69・15.5秒） |
| redis・Issue | 第4波（39ファイル） | 第2波（53・4.2秒） | **第1波（48・7.2秒）** | 第1波（56・10.7秒） |

- 主要モジュールは、frr・Issue と redis の各シナリオで第0〜1波にそろった。
- frr・CR-801 は、工程2で対象範囲が IS-IS に絞られた CR（u1-eval の README）なので、他デーモンが出ないのは
  シードの範囲どおり。
- 予算1,000では、正解モジュールが出そろうのが1〜2波遅れた。10,000では出そろう波は3,000と同じで、
  ファイル数と時間が1.5〜2倍になった。
- 打ち切られたシンボルの例: `node`(6615)、`main`(317)、`call`(602)、`addReplyError`(458)。一般的な名前が多いが、
  redis の `call` のように中核の関数も含まれうる。打ち切り記録に残るので、人が判断できる。

## 既知の限界

- **評価範囲が狭い:** C の2リポジトリ・4シナリオのみです。正解は「PR で変更されたファイル」という代用指標です。
  C++ は合成コードのテストのみ、Python はこのリポジトリでの動作確認のみです。
- **安全側でない仮定:** 外部関数はアドレス渡し（`&x`）と既知の標準関数（`memcpy` 等）以外では引数を書き換えない
  （`--policy strict` で無効化できる）。呼び出し先の要約は深さ3まで。関数ポインタ・コールバックは追わない。
  マクロ本体は代入パターンの正規表現でしか見ない。
- **評価時期による違い:** `results/eval-final.txt` と `results/eval-full-slice-waves.txt` は、検索に `git grep` を使い、
  ヒット上限で波全体を打ち切っていた時点のもの。最新の方式（索引＋予算）は `results/eval-feature-level.txt`。
- **C の構文解析:** プリプロセッサを通さないため、構文を作るマクロで構文解析が崩れます。ループマクロの書き換え
  （`preprocess_c`）で、frr の構文エラー行は 32.8% → 2.7% に減りましたが、残りはあります。
- **共通基盤の副作用:** ログ出力・メモリ確保・参照カウント・`errno` などの書き込みは意味上は正しい副作用ですが、
  波紋としてはノイズになります。完全スライスでは `--ignore-calls` の設定が実質的に必須です。
- **依存:** tree-sitter（pip）を使います。リポジトリの決定的処理スクリプトは標準ライブラリのみ（openpyxl を除く）
  という方針なので、本採用するなら ADR での判断が必要です。
