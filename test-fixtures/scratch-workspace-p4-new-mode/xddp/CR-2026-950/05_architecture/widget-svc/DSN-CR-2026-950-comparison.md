## 4. 採用方式と理由

**採用方式：** 案A（レイヤードパイプライン方式）

**採用理由：**
CRS付記の未決事項一覧（Q2・Q3・Q4・Q5・Q6・Q7・Q8・Q9・Q10）が示すとおり、本CRはパス指定方式・スキーマ定義ファイルの記述形式／置き場所・真偽値の表記揺れ・値域指定方式・エラーメッセージ形式・マスキング対象・検証済み設定値オブジェクトのフィールド定義・読込失敗時挙動・未知キー扱いなど、CR起票者確認待ちの暫定方針を多数抱えたまま工程5に持ち込まれている。これらは工程5完了までにCR起票者確認を要し（一部は工程5開始前が期限）、確定内容が暫定方針と異なった場合の手戻りが発生する可能性が高い。案Aはこれらの仕様点をConfigLoader（読込失敗時挙動）／SchemaLoader（スキーマ定義ファイルの記述形式・置き場所、Q3）／Validator（真偽値表記揺れ・値域指定方式）／ErrorFormatter（エラーメッセージ形式・マスキング対象）／ConfigObjectBuilder（検証済み設定値オブジェクトのフィールド定義、Q8）という対応コンポーネントに切り分けて実装するため、確定後の変更が該当コンポーネントに限定され、他コンポーネントへの手戻りを抑制できる。また CR-2026-950-UR-001 の理由（起動時の設定検証は複数コンポーネントで共通して必要になる見込み）を踏まえると、将来のチェック種別追加（気づきメモ#3）や部分的な再利用に対しても案Aの分離構造が有利である。初期実装工数・学習コストの増加は案Bに劣るものの、本CRの未決事項の多さと将来の拡張見込みを踏まえ、保守性・技術的リスクを優先して案Aを採用する。

**懸念事項と対策：**

| 懸念事項 | 対策 |
|----------|------|
| コンポーネント分割により初期実装・レビュー工数がやや増加し、スケジュール適合性で案Bに劣る | CHDでは各コンポーネントのインタフェース（データ受け渡し形式）を先に固定し、実装を並行着手可能にすることで工数増加を吸収する |
| 新規開発モードのためSPO・funcmapが存在せず、影響範囲・非機能特性・テスト状況（SPO Section 5.x・Section 9相当の情報）を根拠とした定量評価ができない。本方式比較はCRSの記述のみを根拠としている | CHD作成時・工程9（テスト設計）時に、コンポーネント間インタフェースと処理時間（CR-2026-950-SP-008-001.001暫定200ms）を具体的に検証し、想定との乖離があれば本DSNを更新する |
| CR-2026-950-SP-008-001.001（起動処理200ms以内、暫定値・CR起票者未確認）の閾値次第では、コンポーネント分割による関数呼び出しオーバーヘッドが問題になる可能性がある（50件規模の設定ファイルでは影響は軽微と想定されるが未検証） | CHD完了時に簡易ベンチマーク（処理ステップ数×想定コスト）を実施し、閾値確定後に工程9で正式な合否基準とする |
| Q13（呼び出し元とのインタフェース仕様：関数シグネチャ・戻り値／例外送出の別・エラーコード体系）が未確定のまま案Aのコンポーネント分割を進めると、公開インタフェース（ファサード関数）の確定が遅れた場合に内部設計の手戻りが生じうる | CHDでは公開インタフェース（ファサード関数のシグネチャ）を最初に確定し、内部コンポーネント分割はその後段階的に設計する順序とする |

## 5. 変更設計書作成への指針

- **公開インタフェースの確定を最優先とすること：** ファサード関数（例：`load_and_validate_config`）の引数（設定ファイルパス、CR-2026-950-SP-002-001.002：呼び出し元が絶対パスまたは相対パスを明示的に指定）、戻り値（検証済み設定値オブジェクト、CR-2026-950-SP-007-001.001：型変換済みの専用データ構造）、失敗時の応答方式（読込失敗時は例外送出：CR-2026-950-SP-002-001.003暫定。検証失敗時の応答方式はCR-2026-950-SR-006-001／Q6が未確定のため、CR起票者確認結果を反映してからCHDで確定すること）を最初に固定する。Q13（関数シグネチャ・戻り値／例外送出の別・エラーコード体系、モジュール配置・パッケージ構成）はCRS §5未決事項表にて対応期限「工程5完了まで」と規定されており、下記「未決事項の解消順序」のQ3・Q6・Q7・Q8と同じ分類（工程5完了まで＝CHD着手前までにCR起票者確認結果を反映）に含める。CHD着手前に、Q13の確認結果、および下記のCR-2026-950-SP-001-001.001具体案に対するCR起票者の承認可否を取得すること。
- **CR-2026-950-SP-001-001.001の具体案（CR-2026-950-UR-001／CR-2026-950-SR-001-001対応・提案）：** CR-2026-950-UR-001「懸念・検討事項」およびCR-2026-950-SR-001-001「懸念・検討事項」は、モジュール配置・パッケージ構成・呼び出し元とのインタフェース境界（関数シグネチャ等）を工程5で確定したうえでCR-2026-950-SP-001-001.001として追加することを要求している（Q13参照）。本DSNの方式比較結果（案A＝レイヤードパイプライン方式の採用）を踏まえ、以下をCR-2026-950-SP-001-001.001の具体案として提案する。
  - **モジュール配置：** widget-svc内に本CR専用の新規パッケージ（例：`config/`）を新設し、案Aの5コンポーネント（ConfigLoader／SchemaLoader／Validator／ErrorFormatter／ConfigObjectBuilder）およびFacadeをこのパッケージ配下に格納する。他の既存パッケージ（README.mdのみの空リポジトリのため現時点では存在しない）には配置しない。
  - **パッケージ構成：** パッケージ内部は案Aのコンポーネント境界（下記「採用方式（案A）のコンポーネント境界」参照）どおりに5つの内部モジュール（ファイル）に分割し、Facadeモジュールがこれらを合成する。
  - **呼び出し元とのインタフェース境界：** 呼び出し元（本CRスコープ外・別CRで実装）が参照できるのはパッケージが公開する単一のファサード関数（例：`load_and_validate_config(config_path)`）のみとし、ConfigLoader／SchemaLoader／Validator／ErrorFormatter／ConfigObjectBuilderの各内部モジュールはパッケージ非公開（呼び出し元から直接参照不可）とする。これによりCR-2026-950-SR-001-001「既存の内部モジュールに依存しない独立モジュール」を、本モジュール自身が外部に対して単一の窓口のみを持つ形で満たす。
  - **確定範囲の注記：** ファサード関数の具体的な引数型・戻り値の型・例外クラス設計（Q13本体）はCR起票者確認待ちのためCHDで確定するが、上記のパッケージ配置・「Facadeのみ公開」という境界方針はCHDでも変更せず維持すること。
  - この提案は工程5完了時点でCRSへフィードバック（xddp.feedbackまたは工程6bのCRSフィードバック）し、正式にCR-2026-950-SP-001-001.001として追加することを想定する。
- **採用方式（案A）のコンポーネント境界：**
  - ConfigLoader：ファイルI/O・YAMLパース（読み込み対象ファイル形式はYAML形式、CR-2026-950-SP-002-001.001）。ファイル不存在／権限不足／YAML構文エラーの3種を判別可能な情報を含めて例外送出する（CR-2026-950-SP-002-001.003）。
  - SchemaLoader：外部スキーマ定義ファイル（必須キー一覧・型・値域）の読込（CR-2026-950-SP-003-001.001）。具体的な記述形式・置き場所・バージョニング方針はQ3未確定のため、CHDで確定すること。
  - Validator：必須キーチェック（CR-2026-950-SP-003-001.002）・型チェック（CR-2026-950-SP-004-001.001／CR-2026-950-SP-004-001.002：真偽値はYAMLパーサがbool型と解釈した値のみ許容）・値域チェック（CR-2026-950-SP-005-001.001：最小値・最大値の片側指定許容／CR-2026-950-SP-005-001.002：inclusive判定）の3種を、最初のエラーで中断せず全項目実行してから結果を集約する（CR-2026-950-SP-006-001.001）。未知キーの扱い（CR-2026-950-SP-003-001.003：暫定許容方針、Q10未確定）もここに実装する。
  - ErrorFormatter：Validatorの集約結果から、キー名と不正理由のペアリストを生成し（CR-2026-950-SP-006-001.002：文字列連結か構造化リストかはQ6未確定でCHD確定事項）、機密情報を示すキー名パターン（Q7未確定）に一致する値をマスキングする（CR-2026-950-SP-006-001.003）。
  - ConfigObjectBuilder：検証成功時に、スキーマ指定の型へ変換済みの専用データ構造（検証済み設定値オブジェクト）を生成する（CR-2026-950-SP-007-001.001）。フィールド定義の詳細はQ8未確定でCHD確定事項。
- **未決事項の解消順序：** Q2・Q4・Q5・Q9・Q10（工程5開始前が期限）はCHD着手前にCR起票者確認結果を反映し、Q3・Q6・Q7・Q8・Q13（工程5完了まで＝CHD着手前までが期限）はCHD着手前までにCR起票者確認結果（Q13についてはあわせて上記CR-2026-950-SP-001-001.001具体案への承認可否）を反映すること。いずれの場合も、案A採用の前提（変更影響のコンポーネント局所化）を活かし、該当コンポーネントの内部実装のみを更新する形でCHDに反映すること。
- **性能要件：** CR-2026-950-SP-008-001.001（暫定200ms、CR起票者未確認）はCHD完了時点で簡易見積り（コンポーネント呼び出し段数×想定処理コスト）を記載し、CR起票者確認後に工程9（テスト設計）で正式な合否基準とすること。
- **新規開発モードに関する記録：** 本CRはDEVELOPMENT_MODE=newであり、SPO・funcmapは生成されていない。widget-svcは既存コードが存在しない前提（README.mdのみの空リポジトリ）で方式比較を実施した。既存コードとの後方互換性・波及範囲の定量評価はCRSの記述のみに基づく。
