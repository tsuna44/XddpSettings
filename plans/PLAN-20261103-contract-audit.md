## 1. 背景・目的

### 1.1 起きていること

不具合を1つ直すと、その隣の不具合が見つかる状態が続いている。2026-11-02〜03 に見つかった不具合は、どれも
**同じもの（ファイル・見出し・ラベル・形式）を書く側と読む側の約束の食い違い**だった。

| 不具合 | 書く側 | 読む側 | 対応 |
|---|---|---|---|
| 制約の置き場所 `{MODULE}` の決め方が経路ごとに違い、書いた制約を読めない | close・survey・update-knowledge | 下調べ・AI_INDEX・工程2 | PLAN-20261102-constraints-module-key（fbf3956） |
| 過去の CR の LL も取り込む | close Step C（LL を書く） | `promote.py` は CR で絞る／knowledge agent は絞らない | PLAN-20261102-close-ll-cr-filter（fbf3956） |
| AI_INDEX のラベル `{repo} 構造体関連図` と `{repo} 共有構造体` が食い違う | `promote.py` | `domain_refs.py` | PLAN-20261103-domain-refs-shared-knowledge（承認待ち） |
| 参照先にディレクトリのパスを渡す | `domain_refs.py` | `xddp-analyst-agent`（ファイルを Read する前提） | 同上 |

スクリプトの単体テストは、各スクリプトが自分の思う約束どおりに動くかしか確かめない。
`tools/harness/refcheck.py` は `apply "## 見出し"` の存在（検査A）・スクリプトのサブコマンドとフラグ（検査D）等を機械検査するが、
**データの中身の約束（ラベル・表の列・JSON のキー・パスの形・値の語彙・書く時期と読む時期）が書く側と読む側で合っているか**は、どこでも検査していない。

### 1.2 目的

1. 直前の変更（fbf3956）に新しい不具合が無いかを確かめる。
2. ファイルをまたぐ約束を棚卸しし、食い違いを**修正せずに**まとめて洗い出す（直しながら探すと連鎖するため）。
3. 見つけた食い違いを、まとまりごとのプランで直し、書く側の出力を読む側に通すテストと、共有の値の単一定義で再発を防ぐ。

### 3.2 段階2: 約束の棚卸し監査

#### 3.2.1 「約束」の範囲

2つ以上のファイル（スキル・エージェント・テンプレート・スクリプト）が、同じものを書く側・読む側として扱っているもの:
- ファイルのパス・名前の形（`{KNOW}/{MODULE}/constraints.md`・`LL-{CR}.md` 等）
- 見出し・節の名前と番号（`## 3. NG詳細`・SPO §5.7 等）
- 表の列・行のラベル（AI_INDEX の「知りたいこと」列の `{repo} 共有定数` 等）
- メタ行・エントリの書式（LL の `**CR：** … ／ **repo：** …` 等）
- JSON・stdout のキーと値の語彙（`status`・`reason`・種別名 `制約`／`共有構造体` 等）
- エージェントへの入力（`Inputs` の名前・中身。パスかファイルか・存在しない場合の意味）
- テンプレートのプレースホルダー（テンプレートに書く側と、埋める側）
- 書く時期と読む時期（読む側が読む時点で、書く側は書き終えているか）

refcheck が既に機械検査しているものは対象外とする: 検査A（`apply` 見出しの存在）、検査B（`subagent_type` のエージェントへの解決と Inputs のキー名）、検査D（サブコマンド・フラグ）、検査E・F・G。
ただし、検査B は Inputs のキー名しか見ないので、Inputs の中身（パスかファイルか・存在しない場合の意味）は対象とする。検査C（テンプレートのプレースホルダー）は警告だけで合否を決めないので、プレースホルダーの約束も対象とする。

#### 3.2.2 範囲と分担

段階2a は、約束の領域ごとに1人ずつ監査する。ファイル数は、検索語を含むスキル・エージェント・スクリプトの数（fbf3956 時点。監査の対象リビジョン〔3.2.4〕が異なれば、そのリビジョンで数え直す。`grep -rlE '{検索語}' ClaudeCode/.claude/skills ClaudeCode/.claude/agents | grep -v '/tests/' | wc -l`。検索語の間でファイルは重なる）で、分け方の目安にした。

監査者が担当外の約束で食い違いに気付いたら、「担当外」と印を付けて報告する（統合で担当の領域に寄せ、重複を除く。3.2.4）。

各監査者の手順:
1. 領域の約束を列挙する。約束ごとに、書く側・読む側のファイルと節、それらを見つけた検索語（検索した範囲を含む）を表にする（3.2.5 の「確認した約束の一覧」になる）。最初に読むファイルは上の表の検索語で得た一覧とし、そこから参照をたどって書く側・読む側を足す。
2. 約束ごとに、すべての書く側とすべての読む側を Read し、食い違いを探す（形式・語彙・パスかファイルか・存在しない場合の扱い・時期）。
3. 時期の約束は、1つのファイルでは判断できないので、「書く側のスキル・ステップ見出し → 読む側のスキル・ステップ見出し」の順序を表にし、その順で実行される根拠（例: `xddp-11-specs` の後に `xddp-close` を実行する、close の Step の順）を添える。
4. 食い違いを見つけたら、書く側と読む側の該当箇所（ファイルパス・節名。行番号は報告書の作成日時点の値として添える）と、食い違いの内容・起きること・確度を書く。
5. 修正はしない。修正案は書いてよいが、決めない。リポジトリのファイルを書き換えない。

確度の凡例（✅ と ⬜ は過去の報告書 `docs/xddp-bugs-2026-09-05.md` の凡例と同じ意味。🔶 を足す）:
- ✅ 確かめた: 両側のコードを読んで食い違いを確認した、またはスクリプト・テストを実行して再現した。
- 🔶 推論: LLM の振る舞いに依存する等、コードからは確定できない。推論である旨と根拠を書く。
- ⬜ 未確認: この監査では確かめていない。

#### 3.2.3 検証

監査者の指摘は、別の検証者が両側のファイルを読み直して確かめる（監査者の結論を前提にしない）。「段階2b」と印を付けた候補（3.2.2）は検証しない（確度は監査者の判断のまま残す）。段階2b を行うかの判断の材料に使うだけで、修正の根拠にはしないため。
検証で「食い違いではない」とされた指摘は報告書から外さず、「検証で否定」として理由とともに残す（人が見直せるようにする）。

**抜き取り確認（見落としの確認）:** 検証者は、監査者が「食い違いなし」とした約束から、領域ごとに2件以上（書く側・読む側の数が多いものを優先。2件未満の領域は全件）を選び、監査者の検索語を使わずに独立に検索し直して、書く側・読む側の漏れが無いかを確かめる。
漏れが見つかったら報告書に書き、その領域の監査をやり直すかを人に尋ねる。

**再現:** スクリプト・テストを実行して再現するのは検証者だけとする。リポジトリのファイル（`test-fixtures/` を含む）と監査用の worktree（3.2.4）は変えず、書き込みが要る場合はセッションのスクラッチのディレクトリにコピーして行う。

#### 3.2.4 実行方法

ワークフロー（エージェントの並列実行）で行う。

- **構成:** 監査5体（A1〜A5）＋検証（指摘の数に応じて1〜3体）で、10体未満とする。
- **対象リビジョン:** 段階2a を始める時点の HEAD とする。PLAN-20261103-domain-refs-shared-knowledge は段階3 にまとめる（7. の 3.）ので、その実装を待たない。PLAN-20261102-cochange-knowledge・PLAN-20261102-impact-hypotheses も後に回す（7. の 4.）ので、その実装を待たない。メインのセッションが `git worktree add {スクラッチ}/audit-{rev} {rev}` で対象リビジョンを別のディレクトリに出し、監査者・検証者はそのディレクトリだけを読む。統合が終わったら worktree を消す。報告書の行番号・ファイル数は対象リビジョンの値とする。
- **監査の間の変更の凍結:** A2 の開始から統合の終わりまで、知識ハブの約束（A1〜A5）に触れるプランを実装しない（worktree で読む状態は変わらないが、実装すると監査の結果が古くなるため）。PLAN-20261102-cochange-knowledge・PLAN-20261102-impact-hypotheses は後に回す（7. の 4.）ので、この間にも実装しない。
- **段取り:** ファイル数が最も少ない A2 を先に1体で行い、トークンの実績と指摘の質（確認した約束の一覧の粒度を含む）を人に報告する。人が続けると決めたら（必要なら手順・入力を直して）、残りの4体を並列で行う。手順・入力を直した場合は、A2 をやり直すかも人が決め、実行の記録に残す。
- **監査者に渡す入力:** 領域名・主な約束・監査用の worktree のパス・最初に読むファイルの一覧（3.2.2 の検索語で得た一覧と対象リビジョン）・約束の種類（3.2.1）・手順と確度の凡例と境界の規則（3.2.2）・出力の書式（3.2.5 の「確認した約束の一覧」の表と、指摘ごとの項目）。
- **ツール:** 監査者は読み取りだけ（Read・Grep・Glob）。Bash を使うのは、検証者が再現する場合だけ（3.2.3）。
- **統合:** メインのセッションが行う。重複の除去、担当外の指摘の担当の領域への寄せ、「段階2b」と印を付けた候補の段階2a の指摘からの分離（3.2.5 の「段階2b の候補」へ置く）、重大度の付与（3.2.5）、報告書の執筆。
- **トークン:** 事前に見積もれない（読むファイルの量が領域によって違う）。A2 の実績から残りを見積もって人に示し、実行後に実績を報告書に記録する。
